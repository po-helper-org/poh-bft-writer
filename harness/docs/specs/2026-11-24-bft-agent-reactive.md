# Реактивный ИИ-агент правок БФТ: одно замечание — одна правка, точечная перерисовка, две модели

Статус: проект (2026-11-24), к ADR-0021. Решения владельца — в конце.

## Что хотим

1. **Одно обращение — одна обработка.** Каждое замечание (или своё указание) — отдельная задача
   со своим итогом и откатом, а не пачка на весь документ.
2. **Без перерисовки всего документа.** Меняются только затронутые разделы — на сервере и на
   странице: без перезагрузки, без прыжка прокрутки, правка подсвечивается на месте.
3. **Быстрая модель для локальных правок** — Haiku: секунды на замечание.
4. **Светящаяся точка у «Комментариев»** → подсказка «Проведите полное ревью требований для
   согласованности» + «Отправить» → **полная модель** проверяет согласованность всего документа.
5. **Модели — в настройках портала.** Полная — внешний агент полного ревью, выделенный под БФТ.

## Замеры (сервер, zayavka-8, 42 КБ)

| Шаг | Время |
|---|---|
| `bft-lint.py` | 145 мс |
| `bft-html-export.py` (весь документ) | 330 мс |
| проверки портала (canon-check) | < 100 мс |
| модель, весь документ на входе (сейчас) | 20–60 с |

Узкое место — модель и объём входа, а не рендер. Значит, реактивность даёт **маленький вход и
быстрая модель**, а перерисовка на странице — только видимая часть задачи.

## Устройство

### 1. Очередь «одно замечание — одна задача»

- `POST bftRevise` принимает одно замечание → задача в очереди заявки (`revisions.json`, как сейчас,
  поле `kind: 'local' | 'review'`). Пачка из «Комментариев» = N задач.
- Очередь исполняется **по одной, по порядку**: каждая правка ложится на результат предыдущей
  (фрагмент «найти» берётся из актуального текста). Параллельно — нет: две правки одной таблицы
  дали бы конфликт.
- У каждой задачи — свой итог (внесено / уже так / вопрос / не внесено), свой откат, свой
  статус в колонке: «в очереди → правит → проверяет → готово».
- Откат — не только последней: копия до каждой задачи; откат задачи из середины = обратная
  правка «заменить новое на старое», если тот фрагмент с тех пор не менялся; иначе — «откатить
  нельзя: поверх легла правка N».

### 2. Локальная правка (Haiku): маленький вход

- Раздел замечания известен (`[Риски]`, `[Функциональные требования* · ФТ-2]`) → модель получает
  **только этот раздел** (+ заголовок документа и шапку-цель для смысла), а не 42 КБ.
  Нет раздела («Документ») — разделы, где встречается цитата замечания; не нашлось — весь документ.
- Ответ — тот же формат «найти → заменить» + отчёт по одному пункту. Фрагмент ищется в разделе;
  уникальность — в разделе.
- Проверки после правки — по всему документу (быстро), сравнение с исходным: новая ошибка →
  второй круг с ней, затем отказ без изменений (как сейчас).
- Ожидаемо: вход 1–4 тыс. токенов вместо 15 тыс. → Haiku 3–8 с на замечание.

### 3. Точечная перерисовка

**Сервер.** Правка знает, какие разделы `##` изменились (смещения правок → границы разделов).
Экспорт страницы — целиком (330 мс, дешевле, чем поддерживать второй рендер), но в ответ
статуса уходят **только изменённые разделы**: `GET bftReviseSection?session&rev=…` → `{sections:
[{id: "sec-6", html}], docRev}`. Диаграмма plantuml пересобирается, только если менялся
«План демонстрации».

**Страница.** Колонка агента получает «готово» → берёт HTML изменённых разделов и заменяет в DOM
узлы от `<h2 id="sec-N">` до следующего `<h2>`; изменённый блок подсвечивается 2 с.
Скрипт страницы ревью после замены перекрашивает точки `[УТОЧНИТЬ]` и счётчики (вызов его
`render()`/`paintDots()` — сделать их доступными через `window.bftReview`). Прокрутка не
прыгает, открытые «Комментарии» не теряются. Хэш документа (`DOC_REV`) обновляется на месте —
комментарии, отправленные агенту, закрываются, неотправленные остаются.

### 4. Полное ревью согласованности (полная модель)

- **Точка** у «Комментариев» светится, когда после последнего ревью были локальные правки
  (`revisions.json`: есть `local` новее последнего `review`). Нажатие → подсказка «Проведите полное
  ревью требований для согласованности» + «Отправить».
- Задача `review`: полная модель получает **весь документ + список локальных правок с момента
  прошлого ревью** и проверяет сквозную согласованность: ID и связи (БТ↔ПТ↔ФТ), план демонстрации
  ↔ требования, риски ↔ зависимости, «Якоря истины», открытые вопросы ↔ маркеры. Ответ — те же
  правки «найти → заменить» + список «что согласовал». Проверки шаблона — как у сборки.
- После ревью точка гаснет; итог ревью — отдельной карточкой в колонке.

### 5. Модели в настройках

«Настройки → Портал» (`models.json`, ADR-0012) получают два поля:

| Поле | По умолчанию | Сейчас настроить |
|---|---|---|
| Локальные правки | Haiku: `requesty / anthropic/claude-haiku-5-5` (ключ на сервере есть) | так и оставить |
| Полное ревью | модель полного БФТ | **агент полного ревью** (внешний шлюз агентов) |

Локальная модель — любой провайдер dsh (как модели чата и полного БФТ). Полное ревью — либо
провайдер dsh, либо **подключение к агенту полного ревью** через шлюз агентов (Responses API,
Bearer-ключ агента). Адрес шлюза, имя агента и ключ — только в окружении сервера
(`server.env` → `harness/.env`, переносит `deploy-server.sh`; ключ вводит владелец), в репозитории
их нет.

**Как контейнер портала достучится до агента.** Шлюз агентов слушает только loopback хоста.
Как у шлюза источников (ADR-0015): точный `location` в nginx — один путь к одному агенту и
только метод ответа; ключ проверяет сам шлюз. Разовый шаг владельца — `install-nginx-bft.sh`
(адрес и агент — из окружения сервера). Остальные агенты и их MCP порталу по-прежнему недоступны.

## Риски

- **Агент под БФТ — агент с инструментами** (файлы, shell, навыки), а в документе — текст заказчика.
  Отдать ему документ = дать тексту заказчика шанс скомандовать агенту на сервере (prompt
  injection). Нужен профиль **без инструментов на канале API** — см. решения.
- Haiku слабее на канонических таблицах: правка ломает шаблон → второй круг → отказ без изменений.
  Итог видно в карточке; полное ревью добирает согласованность.
- Очередь по одному: 10 замечаний × 5 с ≈ 1 мин — но каждое видно сразу, документ меняется
  по ходу.

## Решения владельца

1. **Агент полного ревью:** отдельный агент без инструментов на канале API (те же инструкции и
   навыки, что у агента БФТ) — рекомендую; или агент БФТ как есть.
2. **Доступ из портала к агенту:** nginx `location` на одного агента (рекомендую) — разовый sudo-шаг.
3. **Ключ агента** — владелец кладёт в окружение сервера.
