# Конвейер БФТ: запрос → сбор → верификация → validated

Модуль БФТ превращает абстрактный запрос в полноценную оценку инициативы.
Доменные состояния — не механика коробки, а ценность для продукта; Коробка
носит их как состояния воркфлоу (Temporal — implementation, см. ADR-0001):

| Состояние | Что происходит | Маппинг на старые состояния |
|---|---|---|
| **запрос** | Неформализованный ввод заказчика; fast-скоринг фиксирует вводные, контакты (Заказчик/PO/Техлид), источники, открытые вопросы | `preparing` |
| **сбор** | ИИ-агент + методология poh-bft-writer: fast → deep, персоны, требования, границы, How-to-demo, матрица; светофор качества | `working` |
| **верификация** | Диалоги с людьми: сотрудники, PO-руководители, заказчики. Каждое требование подтверждается, договорённость фиксируется. Ожидания расщеплены по адресатам | `waiting_po` → `waiting_employee / waiting_po / waiting_customer` |
| **validated** | Требования собраны и описаны; договорённости зафиксированы; границы исполнителей прописаны (кто реализует, кто предоставляет); открытые вопросы перечислены | `accepted` |

Следующий этап — системные требования к исполнению — **вне этого модуля**:
validated БФТ передаётся дальше как контракт.

**Критерий validated — проверяемый чек-лист** (проверяется кодом в светофоре
+ подтверждениями людей): все требования описаны (нет `[УТОЧНИТЬ]`), каждая
договорённость имеет подтверждение соответствующего адресата, у каждого
требования прописан исполнитель и тип (реализовать/предоставить), открытые
вопросы перечислены явно (их наличие не блокирует validated — блокирует
неявность).

**Типология задач декомпозиции** — чек-лист полноты Трекера (ADR-0004):
сборочные (агент: fast, deep, разведка, матрица, вайрфрейм, HTML),
верификационные (люди: интервью, согласование, подтверждение границ, custdev),
коммуникационные (сценарий: написать → ждать N дней → напомнить → эскалировать),
сессионные (запись каждой агентной сессии — накопление контекста).

**Три поверхности, не одна:** конвейер — чип/режим на PO-доске плагина
(4 колонки), доска PO — плагин (9 стадий документа, как есть), доска
сотрудников — Трекер (Backlog → В работе → Ждёт ответа → Готово, swimlane по
типу, фильтр `bft:<slug>`). Конвейер и стадии документа — разные оси:
конвейер про инициативу, стадии про артефакты документа.

**Масштаб 100+/сутки** держат: fast — параллельные сессии Харнесса (ограничены
токен-бюджетом z.ai), deep/верификация — очереди Temporal (воркер не тонет:
инициативы в ожидании людей не занимают слотов), Трекер — обычная БД.

## Considered Options

- Конвейер как колонки Трекера — трекер стал бы источником истины состояний,
  дублируя Коробку; рассинхрон гарантирован. Отклонено: зеркало, не истина.
- Оставить механические состояния коробки (`preparing/working/…`) — теряли
  связь с продуктом; переименование дешёвое, домен важнее механики.

## Consequences

- Переименование/расщепление состояний Коробки — правка вендоренного `box/`
  с прогоном 28 контрактных эталонов (S1).
- В карточке указания появляется адресат из плана верификации;
  неразобранные ожидания видны на доске сотрудников как задачи «Ждёт ответа».
- PO-доска плагина получает режим «Конвейер» (4 колонки) поверх 9 стадий —
  без ломки существующих вьюх.
