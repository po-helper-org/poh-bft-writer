# ADR-0014: Публикация портала заказчика на сервере — /bft/ за Authentik

Статус: принято (2026-11-18)

## Контекст

Портал заказчика (ADR-0007, ADR-0012) работал только локально. Нужен общий
сервис: заказчик или продакт приходит, отправляет запрос и получает БФТ по
конвейеру портала. Адрес — `https://browser.harness.aleksishmanov.ru/bft/`.

- На этом пути жил виджет Element «Управление требованиями» (poh-widget-bft,
  127.0.0.1:8626).
- Полный БФТ ищет по Jira и Confluence МТС с правами PO (ADR-0013), и каждая
  заявка тратит деньги на модель.
- На сервере порты 3080/3081/3456 заняты, клон `poh-bft-writer` ведёт
  автодеплой `main`, sudo — только у владельца.

## Решение

- **Вход — Authentik**, как у остальных приложений хоста: открытый доступ
  раскрыл бы выдержки корпоративных систем и бюджет модели.
- **/bft/ отдан порталу**, виджет «Управление требованиями» с пути снят (его
  сервис не трогаем; откат — `install-nginx-bft.sh --rollback`).
- **Портал под префиксом.** dsh строит адреса относительно `<base href="./">`;
  наши плагины тоже: все ссылки, запросы и редиректы — относительные,
  кука администратора — с путём из `PORTAL_PUBLIC_URL`. nginx срезает `/bft`.
  Локальная проверка — эмулятор `docker-compose.subpath.yml` (127.0.0.1:3090/bft,
  обманки 418 на `/api/` и `/` вне префикса).
- **Отдельная папка на сервере** `~/Projects/poh-bft-portal`, проект compose
  `poh-bft-portal`, `docker-compose.server.yml`: портал 127.0.0.1:3082,
  приёмник входа источников 127.0.0.1:3083, трекер 127.0.0.1:3084 (только для
  сида). Выкладка — `harness/deploy-server.sh` (закоммиченный HEAD, сборка на
  сервере; `--keys` — ключи моделей из локального `.env` без вывода).
- **nginx — разовый шаг владельца** `harness/deploy/install-nginx-bft.sh`
  (sudo; `nginx -t` или откат vhost и сниппета).
- **Трекер наружу не публикуется**: пустой `TRACKER_PUBLIC_URL` — заказчику
  «#N» без ссылки.
- **Источник данных на сервере — служебный токен моста Hermes** (ADR-0013,
  дополнение 2026-11-18): `harness/deploy/issue-sources-token.sh` на сервере
  выпускает токен `bft-portal` (только четыре инструмента чтения), пишет его
  в `harness/.env` как `DATA_SOURCES_TOKEN_PO_HQ` без вывода и пересоздаёт
  `customer-web`. Контейнер ходит в мост через публичный
  `https://harness.aleksishmanov.ru/mcp` (VPN и 127.0.0.1 хоста ему
  недоступны), nginx не меняется. Прежнее OAuth-подключение
  администратора (полный токен штаба в томе `customerdata`) портал при
  первом запуске со служебным токеном сам удаляет и отзывает — отдельного
  шага миграции нет; проверка — строка «прежнее OAuth-подключение удалено»
  в `docker compose logs customer-web`. Туннель
  `ssh -L 3083:127.0.0.1:3083 harness-mts` и OAuth администратора остались
  запасным путём (и способом для локального портала).

## Последствия

- Токен в `.env` сервера переживает выкладку (`deploy-server.sh` не трогает
  `.env`); смена токена — повторный запуск `issue-sources-token.sh`.
- Обновление сервера — `harness/deploy-server.sh` после коммита; автодеплой
  `main` портал не затрагивает, пока ветка не влита.
- Пять e2e-сценариев ждут публичную ссылку трекера: на серверной конфигурации
  они по замыслу не проходят, локально проходят.
