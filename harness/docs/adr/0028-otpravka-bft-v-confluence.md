# ADR-0028: Отправка собранного БФТ в Confluence — детерминированно, процессом Temporal

Статус: принято (2026-11-24). Дополняет ADR-0015 (шлюз источников только на чтение),
ADR-0019 (поиск Confluence), ADR-0022 (жизненный цикл на Temporal), ADR-0026 (боковые
панели страницы БФТ). Use case — в спеке `harness/docs/specs/2026-11-23-bft-lifecycle-temporal.md`,
сценарий 8.

## Контекст

Готовый полный БФТ живёт в портале: страница `customer-form.bftFast`, выгрузка .docx/.pdf/.md.
Дальше PO руками переносит его в Confluence — копирует, чинит таблицы, ищет, куда положить,
грузит схемы. Навык `/bft-deliver` делает это агентом через MCP, но в портале агента нет,
а у портала доступ к Confluence только на чтение (ADR-0015). Записи в Confluence не было нигде.

Нужно: кнопка на странице БФТ, понятный выбор родительской страницы, ход отправки по шагам,
который не теряется при перезагрузке, повторная отправка без дублей и история, по которой
владелец видит, прошло ли всё.

## Решение

1. **Преобразование — скрипт, без модели** (`customer-form/src/confluence-storage.ts`).
   Markdown навыка → storage-формат Confluence (XHTML) по стандарту отгрузки
   (`commands/bft-deliver.md`, `bft_standards.md`): заголовок страницы — H1
   `[БФТ] <slug>: <Название>`; frontmatter, граница BFT-HEAD-END и служебные блоки PO не
   публикуются; «Общая информация» остаётся (блок корпоративного шаблона); заголовки →
   h2…h6, таблицы канона → таблицы с шапкой; PlantUML → PNG-вложение `<ac:image>` (ЗМ-015),
   не отрендерилась — исходник в Expand с `[УТОЧНИТЬ]`; Jira `…/browse/KEY-1` → макрос Jira
   (ЗМ-009); `<details>` → Expand; сверху — панель «опубликовано из портала» и оглавление.
   Одинаковый вход → одинаковое тело байт в байт: времени отправки в теле нет, версия и дата —
   из frontmatter документа.
2. **Публикация — workflow `ConfluencePublish`** (`bft-flow/src/publish.ts`), один на отправку:
   `bft-<taskId>-confluence-<n>`. Активности исполнителя публикации (очередь `bft-confluence`):
   `confluenceRender` → `confluenceUpsertPage` → `confluenceAttach` → `confluenceFinish`; итог в
   трекер и хронику — активность портала `confluenceAnnounce` (очередь `bft-portal`, не дошла —
   отправка всё равно удалась, в ходе — предупреждение).
   Повторы: сеть, 5xx, 409, 429 — до 5 раз с паузой 10 с … 2 мин; отказ, который повтором не
   лечится (401, 403, нет родителя, чужая страница с тем же названием, документ изменился во
   время отправки), — тип `ConfluenceRejected`, без повторов. Ход — query `progress` (шаги,
   статусы, причина); упавшая отправка — `Failed` в Temporal UI с той же причиной, что видит
   пользователь. Атрибут поиска `BftTaskId` — все отправки заявки одним фильтром.
3. **Отдельно от `BftLifecycle`.** Отправка не меняет стадию заявки; цикл получает две записи
   хроники (`note`: «отправка начата», «опубликовано: ссылка»). Дочерним workflow её не
   делали: отправку запускает человек, когда угодно, в том числе после передачи заявки, и
   её история не должна раздувать историю цикла.
4. **Идемпотентность.** `confluence-publish.json` в папке заявки хранит `pageId`, родителя,
   номер прогона и sha256 загруженных вложений. Повторная отправка обновляет ту же страницу
   (новая версия, при смене родителя — перенос); страница из состояния удалена — ищем по
   названию в пространстве родителя и берём только свою (метка `bft-<slug>`), чужую —
   отказ. Вложение с тем же sha256 второй раз не грузится. Итог пишется и в `confluence.json`
   (тот же файл, что у MCP `bft_record_publication`), и комментарием в задачу трекера.
5. **Выбор родителя — без модели, детерминированно** (`rankParents`). Кандидаты: куда уже
   публиковали из портала (+4), родитель похожего БФТ, найденного поиском (+3, предков
   отдаёт только ключ публикации), страницы из материалов и разведки заявки (+2), выдача
   поиска по названию и системам заявки (+1…2 по месту), «БФТ/требования» в названии (+1).
   ТОП-5, каждый — с причиной. Поиск — существующий read-only шлюз (ADR-0019). Своя страница —
   поиском по названию, вставкой ссылки (`viewpage.action?pageId=`, `/spaces/KEY/pages/ID`,
   `/display/KEY/Title`) или номера; короткая `/x/…` — честное «скопируйте полный адрес».
6. **Запись — отдельный процесс с отдельным ключом.** Сервис `confluence-publisher` — образ
   портала, команда `node …/customer-form/lib/confluence-worker.js`, общий с порталом том
   файлов заявок. Только у него `CONFLUENCE_PUBLISH_TOKEN` (владелец вводит на сервере:
   `harness/deploy/set-confluence-publish-key.sh`); адрес `CONFLUENCE_PUBLISH_URL` (из
   `server.env`) знают оба, для Cloud ещё `CONFLUENCE_PUBLISH_USER`. На сервере Confluence
   доступен только через VPN хоста, а файрвол не пускает контейнеры к портам хоста, поэтому
   исполнитель — в сети хоста (`network_mode: host`), Temporal для него опубликован на
   `127.0.0.1:3089`; корпоративный Confluence подписан внутренним УЦ — исполнителю подключено
   хранилище сертификатов хоста (`NODE_EXTRA_CA_CERTS`). Портал с ИИ-агентами ключа записи не
   видит (только признак «задан» для «Ключи и доступы», ADR-0030); предков страниц для ТОП-5 он
   спрашивает у исполнителя коротким workflow `ConfluenceLookup`. Шлюз источников и его белый
   список не меняются. Ключ не попадает ни в историю Temporal, ни в ответы, ни в журнал.
7. **Интерфейс** (`confluence-publish-page.ts`): вкладка «⇪ В Confluence» в рейке боковых
   панелей (без рейки — кнопка под «Скачать»), панель справа: «Уже опубликовано»,
   поиск/ссылка, ТОП-5, «Отправить»; затем четыре шага с отметками, ссылка на страницу,
   ошибка текстом и «Повторить» / «Выбрать другую страницу». При открытии страницы портал
   спрашивает ход у workflow: идёт отправка — панель открыта сразу.

## Рассмотренные варианты

- **Дать шлюзу инструменты записи.** Шлюз — общий канал чтения для чата и разведки;
  запись в нём открыла бы её и агентам. Отдельный ключ в одном месте проще отозвать.
- **Агент `/bft-deliver` в портале.** Модель на каждую отправку, недетерминированная разметка,
  а сам перенос таблиц — механика, которой модель не нужна.
- **Публиковать markdown (`representation: wiki`/`markdown`).** Таблицы с `|` в ячейках и
  схемы картинкой так не собрать; storage — единственный формат с `<ac:image>` и макросами.
- **Синхронный маршрут без Temporal.** Отправка — минуты (рендер схем, .pdf, вложения); рестарт
  портала посреди неё потерял бы ход, а владелец не видел бы, что произошло.

## Последствия

- В контуре появляется право записи в Confluence — ровно в `confluence-publisher` (~150 МБ
  в покое, до 768 МБ во время отправки: pandoc, weasyprint, plantuml).
- Temporal на сервере опубликован на `127.0.0.1:3089` (только loopback).
- Ручные правки опубликованной страницы перезаписываются повторной отправкой — это сказано на
  самой странице (панель сверху) и в панели портала.
- Нет ключа — кнопка есть, панель подбирает страницы, а «Отправить» объясняет, что добавить.
- Temporal недоступен — отправить нельзя (сообщение), всё остальное в портале работает.

- `customer-form/test/confluence-publish.test.mjs`: детерминизм (дважды, CRLF), структура
  страницы, схемы картинкой и без рендерера, разбор ссылок, ТОП-5 при перестановке
  кандидатов, повторная отправка на двойнике REST Confluence (та же страница, вложения не
  грузятся второй раз), своя/чужая страница по названию, отказы с повтором и без.
- `bft-flow/test/publish.test.mjs` (`BFT_FLOW_E2E=1`): workflow на локальном Temporal —
  шаги по порядку, 502 повторён, 403 не повторяется, query у завершённого workflow.
