# ADR-0012: Минимальный контур — портал до БФТ-документа

Статус: принято (2026-11-12)

## Контекст

Коробка выросла до 11 сервисов (портал, harness-web, коробка на Temporal,
Matrix/Element, трекер, разбор материалов, Кортекс, LLM-двойник), а основной
путь заказчика до БФТ-документа так и не собран целиком. Владелец сузил
фокус до одного сценария:

1. Заказчик отправляет требования.
2. Требования фиксируются (заявка в трекере).
3. Собирается bft-fast.
4. Собирается bft-deep.
5. Документ БФТ скачивается в .docx / .md / .pdf.
6. Заказчик видит свою заявку.
7. Видны все заявки.

## Решение

- **В запуске по умолчанию** — пять сервисов: `customer-web` (портал),
  `tracker` + `postgres` (Vikunja — заявки, вложения, «все заявки»),
  `context-ingest` (голос и документы заказчика), `cortex` (память
  организации). Плюс одноразовый `tracker-init`.
- **Профиль `legacy`** — коробка (`box-worker`, `box-mcp`, `temporal`),
  Matrix/Element, `harness-web`. Определения и тома не удалены:
  `./start.sh --legacy` или `docker compose --profile legacy up -d`.
- **bft-deep собирается в портале** — фоновым прогоном навыка по документу
  bft-fast, как сейчас собирается bft-fast; коробка для этого не нужна.
- **Настройки — внутри портала за паролем**: ключи провайдеров и плагины
  через штатные «Настройки» dsh, без правки `.env` и конфигов.
- **Кортекс остаётся**: раздел «Чьи зоны затрагивает и к кому обращаться».

## Последствия

- `start.sh` ждёт здоровья портала и печатает его адрес; сид Matrix — только
  с `--legacy`.
- Плагин harness-web (раздел «Требования» PO) работает только с коробкой и
  уходит вместе с ней.
- Порядок работ: bft-deep в портале → выгрузка .docx/.md/.pdf → страницы «моя
  заявка» и «все заявки» → настройки за паролем → сквозная отладка шагов 1–7.

## Сделано (2026-11-12)

- **Шаг 4 — bft-deep в портале** (`customer-form/src/bft-deep.ts`). «Да, согласен»
  на первичных требованиях запускает фоновую сборку на модели чата
  (`ctx.llm` + `agentDefaultModel`; `PORTAL_DEEP_PROVIDER/MODEL` — явный выбор).
  Шапка — из bft-fast без границы и «Критичных требований», канон — модель по
  эталону навыка (`golden_deep_document.md`), блок «Продолжить» — дословно из
  эталона. Гейт — `bft-lint.py`, до трёх попыток с ошибками линтера модели;
  страница ревью — `bft-html-export.py`. Состояние — `deep.json` рядом с
  документом. Вкладка «Документ БФТ» после согласования сама показывает сборку,
  затем полный БФТ (`?view=fast` — первичные требования); сбой — причина и
  «Собрать заново». Документ и страница уходят вложениями в заявку.
- **Шаг 5 — выгрузка** (`customer-form/src/export.ts`): .md как есть, .docx —
  pandoc, .pdf — pandoc → HTML → WeasyPrint (в образе `pandoc weasyprint
  fonts-dejavu-core`). Для заказчика без frontmatter, «Общей информации» и
  промтов PO. Ссылки — под заголовком документа и во вкладке Information.
- **Шаг 7 — «Все заявки»** (`/api/customer-form.requests`): заявки портала со
  статусом трекера, состоянием первичных требований и полного БФТ, ссылками на
  документ и выгрузку. «Смотреть все обращения» ведёт сюда, а не на доску
  Vikunja (заказчику без входа она не видна).
- Вкладка «Документ БФТ» больше не размножается: адрес постоянный, новую версию
  даёт счётчик внутри вкладки.

- **Настройки за паролем — штатные «Настройки» dsh** (`customer-form/src/admin.ts`).
  Ядро 0.2 пускает браузер единственным принципом `owner`: гостевой принцип
  с политиками `remoteAccess` есть только у LiveShare через relay, а маршруты
  плагинов не-владельцу отвечают 403 — сделать заказчика гостем можно только
  глубоким патчем ядра. Поэтому разделение — в портале:
  - вход `/api/customer-form.admin` по `ADMIN_PASSWORD` (генерирует
    `start.sh`, лежит в `harness/.env`) → HttpOnly-кука с HMAC пароля,
    30 дней; смена пароля гасит все входы;
  - администратору клиент показывает интерфейс dsh целиком: «Ещё → Настройки»
    («Модели» — ключи провайдеров поверх переменных окружения, «Встроенные
    плагины»), «Плагины»; заказчику сайдбар скрыт, клавиша настроек
    заблокирована;
  - на узле методы записи (`credentials/set|unset`, `settings/*` кроме
    чтения, `pluginManager/*` с изменением, `pluginMarket/setIndexes`,
    `account/startSignIn|signOut`, `terminal/*`, `job/kill`) перекрыты
    точными Fetch-маршрутами: они проверяются раньше перехватчика шлюза.
    С кукой администратора вызов уходит шлюзу как есть, без неё — отказ
    `portal/admin-only`.
  - Ключ, введённый в «Моделях», хранит `dsh-credentials` в томе `/data` —
    переживает перезапуск и пересборку. Правки плагинов и модели пишутся в
    `cordis.patch.yml` профиля, который пересборка образа засевает заново
    из `customer.patch.yml`: они живут до следующей пересборки.

- **Сквозной прогон шагов 1–7 на живой модели** (2026-11-12, Anthropic
  Claude Haiku 5.5; ключ введён в «Настройки → Модели», модель по умолчанию —
  `PORTAL_PROVIDER/PORTAL_MODEL` в `.env`). Заявка и первая форма — сразу,
  bft-fast — ~30 с после «Согласую», bft-deep — 16 с, `bft-lint` с первой
  попытки; выгрузка .docx/.pdf/.md, «Все заявки». Найдено и исправлено:
  вопрос о приёмке модель давала выбором одного варианта (промпт: только
  свободный текст); хвост «Открытые вопросы (в чат, не в документ)» в каноне
  (вырезается при сборке, вопросы и так стоят `[УТОЧНИТЬ]` в ячейках); .md
  отдавался со служебным для PO (теперь тот же текст, что в .docx/.pdf);
  обещание «3–6 минут» — «от минуты до пяти».

- **Схема сценария приёмки картинкой** в .pdf/.docx: `plantuml` (Debian,
  с JRE) в образе портала, рендер локальный — текст требований наружу не
  уходит (публичный сервер PlantUML отвергнут). Каждый блок ```plantuml → PNG
  рядом с документом; не отрендерился — остаётся кодом. В .md — исходник.
  Кэш выгрузки версионирован (`export-v2`): старые документы пересобираются.

- **Модели — в «Настройках → Портал»** (`customer-form/src/models.ts`,
  `client/settings.tsx`): раздел штатных «Настроек» dsh, только
  администратору. Модель чата заказчика и модель полного БФТ («как у чата»
  по умолчанию) — из каталога dsh, только провайдеры с ключом. Выбор лежит в
  томе (`/data/customer-form/models.json`); модель чата узел применяет через
  `agentDefaultModel.saveSelection` при сохранении и при каждом старте —
  пересборка засевает профиль заново, выбор администратора переживает и её.
  Порядок для чата: выбор администратора → `PORTAL_PROVIDER/MODEL` → первый
  ключ окружения; для полного БФТ: `PORTAL_DEEP_PROVIDER/MODEL` → выбор
  администратора → модель чата. Модель чата трогается, только если её выбор
  изменился; не применилась (например, её задаёт оверлей e2e) — выбор не
  запоминается. Ключ и модель меняются без `.env` и перезапуска.

Известно: «Все заявки» без постраничности (сотни тестовых заявок); при
открытии портала клиент готовит раздел заявок и закрывает окна, открытые в
первую секунду.
