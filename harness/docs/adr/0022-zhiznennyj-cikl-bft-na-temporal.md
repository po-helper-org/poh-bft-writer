# ADR-0022: Жизненный цикл БФТ — один долгий workflow Temporal на заявку

Статус: предложено (2026-11-23). Возвращает процессный слой ADR-0001 в
минимальный контур ADR-0012; дополняет ADR-0005 (конвейер), ADR-0018 (форма
вопросов), ADR-0021 (точечные правки). Подробности — спека
`harness/docs/specs/2026-11-23-bft-lifecycle-temporal.md`.

## Контекст

После ADR-0012 цикл БФТ живёт в портале кусками, и у каждого куска своё
состояние и свой механизм:

| Кусок | Где состояние | Механизм ожидания / повтора |
|---|---|---|
| Диалог и заявка | сессия dsh, `tickets` трекера | нет |
| Сценарий приёмки | `demos.json` | нет |
| Первичные требования | `fastProgress` в памяти + файлы заявки | нет, рестарт теряет ход |
| Полный БФТ | `deep.json` | «Собрать заново» руками |
| Форма вопросов | `/data/bft-forms/<id>.json` | `setTimeout` 2 мин + скан при рестарте |
| Правки ИИ-агента | `revisions.json` | нет |
| Статус для людей | колонки трекера, `bft-manager` | руками |

Впереди — рассылка вопросов по почте, отслеживание доставки, ответы письмом,
напоминания и эскалация через дни. Это ровно то, чего нет в портале:
таймеры, переживающие рестарт, повторы, одна история событий на заявку.
Ответить на вопрос «что произошло с БФТ #7 и почему он сейчас ждёт» сегодня
можно только чтением пяти файлов и логов.

## Решение

1. **Одна заявка — один workflow `BftLifecycle`**, `workflowId = bft-<taskId>`.
   Стартует при регистрации заявки, живёт до «Согласован» / «Отменён».
   Любое взаимодействие (чат, согласования, правки, ответы формы, письма,
   смена статуса в трекере) приходит в него событием — signal или update — и
   остаётся в истории. Workflow — источник истины о **стадии** заявки;
   трекер, «Управление БФТ», Инбокс — проекции.
2. **Документы — в файлах, в истории — ссылки.** Тексты БФТ, формы, письма
   хранятся как сейчас (папка заявки); в историю идут `ArtifactRef`
   (путь, sha256, ревизия). Лимиты Temporal (2 МБ на payload, 50 К событий)
   не задеваются; персональные данные в истории — только адреса и имена.
3. **Раунды согласования.** Полный БФТ → форма → рассылка → ответы →
   пересборка — один раунд. Раунд закрывается `continueAsNew` с переносом
   состояния: история каждого «прогона» короткая, а код можно менять между
   раундами без `patched()`-зоопарка.
4. **Тяжёлое — дочерними workflow**: `BriefBuild` (fast), `DeepBuild`,
   `Revision` (точечные правки ADR-0021), `Outreach` (один адресат: письмо →
   ждём → напоминаем → эскалируем). Видно по отдельности, ретраи и таймауты
   свои.
5. **Руки остаются в портале.** Активности, которым нужна модель портала
   (`ctx.llm` dsh), файлы заявки и трекер, исполняет сам портал — он
   регистрируется воркером очереди `bft-portal` (только активности).
   Workflow-код — отдельный сервис `bft-flow` (TypeScript, общий с порталом
   словарь типов), очередь `bft-flow`. Почта — активности `bft-flow`
   (SMTP/IMAP или почтовый шлюз организации), без модели.
6. **Входящие от людей проходят через портал.** Открытая форма, ответы,
   письма проверяются порталом (лимиты ADR-0018, сверка ключа), а в workflow
   уходит уже проверенное событие. Temporal наружу не публикуется; Temporal
   UI — только администраторам за Authentik.
7. **Переход — «теневой режим» сначала.** Workflow сначала только записывает
   события, которые портал уже производит, и отдаёт хронику; управление
   (таймеры, сборки, рассылка) переходит к нему по шагам. Ни один шаг не
   требует остановки приёма заявок.

## Рассмотренные варианты

- **Оставить портал, дописать таймеры и журнал.** Ещё одна самописная
  очередь поверх `setTimeout` и файлов; почтовые сценарии на днях ожидания
  потребовали бы своей устойчивой к рестарту машины состояний. По сути —
  повторить Temporal хуже.
- **Вернуть Коробку (Python, `box/`) как есть.** Модель «итерации и указания
  людям» не совпадает с тем, как теперь собирается БФТ (fast/deep/форма в
  портале на TypeScript); пришлось бы дублировать сборку в Python или гонять
  её через HTTP. Берём из Коробки опыт (одна инициатива — один workflow,
  проекция `stage`, ADR-0005), не код.
- **Workflow-код внутри процесса портала.** Песочница workflow Temporal
  собирается своим бандлером; внутри плагина dsh это хрупко, а рестарт
  портала (выкладка) остановил бы и оркестрацию. Отдельный сервис проще и
  переживает выкладку портала.
- **Один workflow на всю систему / на заказчика.** Теряем «одна заявка — одна
  история», который и нужен владельцу.

## Последствия

- В контур по умолчанию возвращаются `temporal` (своя БД в существующем
  postgres) и `bft-flow`; это ~400–600 МБ памяти — лимиты обязательны, сервер
  тесный.
- Портал становится одновременно клиентом Temporal (стартует, шлёт события,
  читает статус) и воркером активностей. Его рестарт приостанавливает только
  активности; ожидания и таймеры продолжаются.
- Хроника заявки (вкладка «Жизненный цикл» в портале, строка статуса в
  Инбоксе и «Управлении БФТ») читается из workflow (query + история).
- Трекер перестаёт быть источником статуса: колонку двигает активность
  workflow; ручной перенос в «Управлении БФТ» — событие в workflow.
- Изменения кода workflow — через `continueAsNew` на границе раунда и
  `patched()` внутри раунда; тест повтора истории (replay) — обязательный в CI.

## Сделано: шаг 0 (2026-11-24)

- **`bft-flow/`** — workflow `BftLifecycle` (`bft-<taskId>`), чистая `reduce`
  стадий (`src/reduce.ts`), queries `status` и `timeline`, атрибуты поиска
  `BftStage`, `BftTaskId`, `BftRound`, `BftWaitingFor`, `BftUpdatedAt`.
  Namespace `bft` (хранение закрытых циклов — `BFT_RETENTION_DAYS`, 365) и
  атрибуты заводит сам воркер при старте. Бандл workflow — при сборке образа.
  Тест цикла на dev-сервере Temporal: `BFT_FLOW_E2E=1 npm test`.
- **Контур по умолчанию**: `temporal` (БД `temporal*` в общем postgres),
  `temporal-ui`, `bft-flow`. Выкладка собирает `bft-flow` каждый раз.
- **Портал — клиент**: новая заявка → `signalWithStart` её цикла
  (`customer-form/src/lifecycle.ts`); заявки, заведённые раньше, догружаются при
  старте (событие `registered` с постоянным eventId — без дублей);
  `GET /api/customer-form.lifecycle?session=` — статус и хроника. Нет
  `TEMPORAL_ADDRESS` или Temporal недоступен — портал работает как раньше.
- **Temporal UI** — `/bft-temporal/` за Authentik, только группе
  администраторов: `map $authentik_groups` (уровень http, `if` в location
  сработал бы до входа), остальным — 403 портала. Ставит
  `install-nginx-bft.sh` (шаг владельца с sudo).

Отличия от спеки: одно событие `event` с полем `kind` вместо отдельного
signal на каждый вид — портал и почтовый поллер шлют одно и то же, схема — в
`bft-flow/src/events.ts`. Воркер активностей в портале появится на шаге 2,
вместе с первой активностью: на шагах 0–1 цикл работу не запускает.
