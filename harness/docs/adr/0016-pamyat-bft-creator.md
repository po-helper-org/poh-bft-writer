# ADR-0016: Память агента bft-creator — базовый контекст для /bft

Статус: принято (2026-11-19). Дополняет ADR-0011 (Кортекс) и ADR-0013/0015
(источники данных).

## Контекст

/bft опирался на две вещи: Кортекс (ADR-0011) и разведку по Jira/Confluence
(ADR-0013, ADR-0015). На сервере Кортекс был подключён к шаблону poh-cortex —
11 узлов методологии, ни одного знания об организации. Карта контекста каждой
заявки была пустой: «Память по этой теме ничего не знает». Полный БФТ писался
со слов заказчика и находок Jira/Confluence — с чистого листа, без того, что
организация уже знает о своих системах, процессах, доменах и терминах.

Знание об окружении есть, но разбросано: прошлые итоговые БФТ, словарь
терминов владельца, IT-карта, заметки агентов. Требование владельца:

- у /bft — свой агент **bft-creator** со своей, выделенной памятью;
- /bft остаётся коробочным решением, без прямых зависимостей на агентов вокруг
  него; в память идут только точечные источники, которые указал владелец:
  **словарь, IT-карта, прошлые БФТ**;
- заказчик видит блоки из памяти, как и раньше (контуры проверки, зоны).

## Решение

- **Память bft-creator — vault poh-cortex** на сервере (`BFT_MEMORY_DIR`, вне
  репозитория, история — локальный git без remote: там корпоративные данные).
  Кортекс коробки читает его как `CORTEX_VAULT` — тот же сервис, только на
  чтение; без памяти — клон шаблона, как раньше.
- **Нексусы памяти**: из шаблона включены `landscape` (системы и интеграции) и
  `processes`; добавлены `domains` (границы команд, партнёры, заказчики),
  `glossary` (термины) и `bft-archive` (итоговые БФТ прошлых заявок).
- **Наполнение — `harness/cortex/bft_memory.py`** (стандартная библиотека, в
  образе Кортекса). Знает только файлы, не их авторов:
  - `glossary` — словарь JSON `{термин: {meaning, deleted?}}` → узел на термин;
    повторный импорт удаляет исчезнувшие термины;
  - `doc` — один markdown (IT-карта) → один узел;
  - `bft` — итоговые БФТ → `bft-archive`: суть из канона (строки «ЧТО ДЕЛАЕМ»,
    «ПРОБЛЕМА», SMART «S»), разделы и текст для поиска;
  - `curated` — готовые узлы (разбор прошлых БФТ на системы, процессы, домены,
    людей, термины) → NEXUS; дубли по `node_id` сливаются: aliases, источники и
    факты объединяются, CP растёт, если факт подтверждён несколькими БФТ;
  - `check` — гейт poh-cortex.
  Всё, что ложится в память, проходит фильтр: IP-адреса, почты, телефоны,
  длинные токены и строки «пароль: …» вырезаются — память видит заказчик и
  модель. Импорт идемпотентный: неизменённый узел не переписывается.
- **Первичное наполнение** — разбор итоговых БФТ на узлы по единой
  спецификации (что извлекать: системы, процессы, домены и контрагенты, люди —
  только рабочая роль и зоны, термины; чего нельзя: требования самого БФТ,
  контакты, адреса). Разбор лежит на сервере (`BFT_MEMORY_CURATED`) и
  применяется тем же `curated`.
- **Ответ Кортекса** (`POST /brief`) — три новых раздела рядом с прежними:
  `areas` (домены и контрагенты), `glossary` (термины словаря, которые есть в
  тексте запроса: аббревиатура — целым словом и тем же регистром, слово —
  основой; псевдоним из одного русского слова не считается) и `precedents`
  (прошлые БФТ по теме). Поиск — по Нексусу, aliases ищутся через теги;
  оглавления и методология шаблона в ответ не попадают.
- **Портал**: карта контекста (`context_map.md`) получает разделы «Домены и
  контрагенты», «Термины», «Прошлые БФТ по теме»; узлы по теме отбираются по
  заголовку и aliases. Карта уходит в полный БФТ как «Карта контекста (память
  организации — указатель, не фактбаза)». Страница первичных требований — как
  была (контуры проверки и зоны из памяти).
- **Установка** — `harness/deploy/install-bft-memory.sh` на сервере без sudo:
  vault, импорт в контейнере без сети (источники — только на чтение), гейт,
  история, `CORTEX_VAULT`, пересоздание `cortex`, таймер `systemd --user`
  `bft-memory-refresh` (раз в сутки — тот же импорт). Пути источников —
  `BFT_MEMORY_*` в `harness/deploy/server.env` (в git не попадает).

## Живой E2E

`harness/e2e-bft-live.sh` на сервере: Playwright проходит путь заказчика с
настоящей моделью — обращение, вопросы, сценарий приёмки, первичные
требования, «Да, согласен», полный БФТ (`customer-form/e2e/live/`). Затем
`harness/e2e-bft-live-check.py` проверяет по файлам заявки:

- Кортекс читает память bft-creator (не демо), карта контекста непустая:
  системы и хотя бы один термин или прошлый БФТ;
- разведка по Jira/Confluence дала находки;
- полный БФТ использует знание из памяти, которого нет в словах заказчика
  (не меньше двух имён систем, доменов, терминов из карты);
- полный БФТ собран, в последней попытке нет ERROR.

Обращение для прогона — приватный файл на сервере (`BFT_E2E_REQUEST_FILE`):
оно должно быть в домене, который знает память, а предметную область
организации в публичный репозиторий не пишем.

## Почему не память агентов напрямую

Заметки агентов — их рабочая память: правила связи, адреса, личные заметки
владельца, лимит в несколько тысяч знаков на профиль. Подключить их — значит
сделать /bft зависимым от чужого формата и показать заказчику то, что для него
не предназначено. Отдельная память в формате poh-cortex: каждый узел с
источником, CP и свежестью; что в неё попадает — решает владелец списком
источников.

## Последствия

- Качество контекста = качество памяти: разбор новых итоговых БФТ — тот же
  `curated`; словарь, IT-карта и архив БФТ обновляются таймером.
- Записи из /bft в память пока нет (Кортекс только на чтение): согласованный
  полный БФТ в архив добавляет владелец списком `BFT_MEMORY_BFT`.
- Блоки из памяти видны заказчику; люди в памяти — только ФИО, роль и зоны.
