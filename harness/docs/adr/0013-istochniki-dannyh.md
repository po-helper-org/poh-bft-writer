# ADR-0013: Источники данных — Jira и Confluence как dsh-плагин

Статус: принято (2026-11-13)

## Контекст

Полный БФТ (bft-deep, ADR-0012) опирался только на слова заказчика и Кортекс.
Связанные эпики, задачи и страницы требований в корпоративных Jira и
Confluence модель не видела, и «Зависимости», «Риски», «Якоря истины»
оставались `[УТОЧНИТЬ]` там, где ответ уже лежит в Confluence. Цель —
повысить качество и точность сбора данных из корпоративных ресурсов.

Доступ к Jira и Confluence МТС уже есть у MCP штаба агентов PO
(`https://harness.aleksishmanov.ru/mcp`, коннектор claude.ai «MTS PO штаб»).

## Решение

- **Отдельный dsh-плагин `data-sources`** (пакет в корне репозитория, как
  `bft-manager`). Источники — список в его `cordis.patch.yml`; первый —
  «MTS PO штаб». Другим плагинам он отдаёт службу `dataSources`
  (`ctx.provide`): `available`, `status`, `search`, `recon`.
- **Не штатный `dsh-mcp-client`.** Тот знает только статические заголовки и
  публикует агенту ВСЕ инструменты сервера, а у штаба есть запись
  (`jira_create_issue`, `confluence_update_page`, `shell`, `send_message`…).
  Плагин — свой клиент Streamable HTTP с белым списком только чтения:
  `confluence_search`, `confluence_get_page`, `jira_search`, `jira_get_issue`.
- **OAuth по спецификации MCP**: метаданные ресурса → сервер авторизации →
  динамическая регистрация клиента → authorization code + PKCE (S256) →
  access/refresh-токены. Подключает администратор в «Настройках → Источники
  данных» (раздел штатных «Настроек» dsh, только с кукой администратора
  портала). Токены и секрет клиента — `/data/data-sources/<id>.json`
  (права 600), наружу не отдаются, обновляются сами.
- **Возврат из окна входа — `http://127.0.0.1:3081/callback`.** Сервер штаба
  пускает только loopback-адреса с путём ровно `/callback`, а маршруты dsh
  живут под `/api`. Плагин держит отдельный приёмник на этом пути; compose
  публикует порт только на 127.0.0.1 хоста; без state начатого входа
  приёмник ничего не делает. Следствие: подключать источник нужно из
  браузера на той же машине, где запущен портал.
- **Где используется — разведка перед полным БФТ.** После «Да, согласен»
  портал просит модель составить 3–5 поисковых запросов по заявке, ищет по
  Confluence и Jira, сливает и ранжирует находки (эпики и истории выше
  ошибок; без совпадения слов запроса и инциденты — вон; Confluence и Jira
  поровну), дочитывает лучшие и пишет карту находок `sources.md`. У каждой
  находки — готовая ссылка для БФТ: `[Jira KEY](url)` / `[Confluence:
  название](url)` — голые ключи и адреса bft-lint не пропускает (LN001/LN002).
  Карта идёт модели как указатель, не фактбаза: факт из находки — только
  если она про предмет заявки, со ссылкой; в «Якорях истины» — ранг R2. Карта уходит вложением в заявку
  (`<slug>-istochniki.md`). Источник не подключён или не ответил — полный
  БФТ собирается как раньше.
- **Агенту чата заказчика инструменты источников не даются.** Токен — доступ
  PO (scope `staff`); отдать его любому посетителю портала значило бы
  открыть ему Jira и Confluence с правами PO. В документ попадает только
  отобранное и со ссылками.

## Последствия

- Новый порт 3081 (только 127.0.0.1) у `customer-web`.
- Разведка добавляет к сборке полного БФТ до ~1,5 минуты (лимит 90 с).
- Следующие источники (прямой Jira/Confluence по токену, другие MCP)
  добавляются строкой в конфиг плагина, если у них OAuth по спецификации MCP.
