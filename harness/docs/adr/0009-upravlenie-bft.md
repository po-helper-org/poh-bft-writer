# bft-manager: «Управление БФТ» для Product Owner поверх Vikunja

PO открывает портал (:3080) и не может перейти к своим запросам и БФТ:
на главной есть только композер заявки. Нужна страница со всем беклогом,
фильтрами и статусами. При этом единственный движок оркестрации — Vikunja
(ADR-0004): dsh — место работы ИИ-агентов, Vikunja — трекер прогресса, и от
UI в dsh могут отказаться в пользу работы прямо в Vikunja. Поэтому страница
не хранит ничего своего: всё читает из трекера и всё пишет в него.

## Решение

Отдельный dsh-бандл `bft-manager/` (узел + клиент), подключён в профиль
портала после `customer-form`. Отдельный, а не внутри `customer-form`:
это поверхность PO, а не заказчика, и её можно подключить и в харнесс :3081.

**Модель в Vikunja.** Обе воронки — канбан-виды квартального проекта
«БФТ …» с фильтром по лейблу; статус = колонка вида:

| Вид | Фильтр | Колонки |
|---|---|---|
| «Запросы» | `labels in <запрос>` | Создан → Ожидает PO → Проработка БФТ → Оценка → В работу: влёт этого квартала / в следующий квартал → Отменено |
| «БФТ-требования» | `labels in <бфт>` | Backlog → Взято в аналитику → Первичный БФТ → Ожидает согласования → Утвержден заказчиком → Отменен |

Виды, колонки и лейбл «бфт» узел создаёт при первом обращении (идемпотентно):
у нового вида колонкой по умолчанию становится первый статус, «колонка
выполнено» снимается — «Отменено» и «Утвержден» задачу не закрывают.
Сотрудники видят те же доски в UI Vikunja и могут двигать карточки там.

**Запрос ↔ БФТ.** Запрос — корневая задача (её заводит портал заказчика,
заказчик следит за ней по ссылке). Переход в «Ожидает PO» требует
ответственного (исполнитель Vikunja, один) и сразу прикрепляет к запросу
задачу «Проработка БФТ: …» отношением `subtask` (у проработки запрос —
`parenttask`): новую — в Backlog доски БФТ с тем же ответственным — или
существующую, если PO выбрал «Прикрепить к существующему БФТ». Так несколько
запросов сходятся в одно БФТ-требование. Ответственных узел берёт из
`/projects/{id}/projectusers` — как поиск исполнителя в Vikunja; команду
PO/аналитиков заводит `tracker/seed.py` (`TRACKER_TEAM`, пароль —
`TRACKER_TEAM_PASSWORD` из start.sh).

**SLA «сколько висит в статусе».** Перемещение между колонками в Vikunja не
меняет даже `updated` задачи. Поэтому каждый переход со страницы пишет в
задачу комментарий-отметку `🔀 Статус: «A» → «B»` (её же видит PO в карточке);
момент входа в статус — дата последней отметки с текущей колонкой, в первой
колонке без отметки — дата создания. Карточку двигали в UI Vikunja без
отметки — показываем «≥ N» от последнего изменения. Тон метки: до 3 суток —
норма, 3–7 — внимание, больше недели — просрочка; финальные статусы SLA не
копят.

**Страница.** Кнопка в левом верхнем углу главной (слой `shell.overlay`,
как страницы poh-bft-plugin) → «Новая заявка» / «Управление БФТ».
Страница адресуема: `#bft` — входящие запросы, `#bft/board` — доска.
Компоненты — примитивы DSH UI 0.1.7 (Button, Menu, SegmentedTabs,
SegmentedControl, Pill, Tag, Input, Modal), цвета — токены темы `--dsw-alias-*`;
Web Awesome не понадобился — всё нашлось в DSH UI.

- **Входящие запросы** — список: название, #номер, статус, сколько в статусе,
  ответственный, прикреплённые БФТ со статусами; фильтры по статусу (чипсы
  со счётчиками, по умолчанию «В работе у PO» — без финальных), по
  ответственному (запоминается в браузере — PO сразу видит свои) и поиск по
  названию/#номеру; сверху — дольше всех висящие. «⋯» — смена статуса.
- **Доска БФТ** — колонки воронки; на карточке дни в статусе (полоса слева при
  просрочке), ответственный, число запросов, отметка «.html», если шаблон БФТ
  приложен. Перетаскивание или «⋯» — смена статуса.
- Клик по запросу или карточке — задача в Vikunja (новая вкладка); «Vikunja ↗»
  в шапке — тот же вид в трекере.

Токен Vikunja 2.x живёт минуты: клиент трекера перелогинивается по 401.

## Considered Options

- Страница внутри `customer-form` — смешивает поверхность заказчика и PO; там
  же параллельно идёт работа над микрофоном.
- Статусы лейблами (`статус:оценка`) — нет порядка и доски в Vikunja, смена
  статуса = снять/повесить два лейбла.
- Отдельные проекты «Запросы» и «БФТ» — против модели «проект = квартал»
  ADR-0004; связи между проектами работают, но архив квартала разъезжается.
- Время входа в статус в своей таблице/файле — второй источник истины рядом
  с Vikunja.

## Consequences

- Портал :3080 без авторизации (ADR-0007 rev5): страницу PO видит любой, кто
  открыл портал. Контур — публикация порта на 127.0.0.1/LAN; разделение ролей
  — отдельная задача.
- Первая загрузка читает комментарии задач не в первой колонке (8 запросов
  параллельно), дальше — кэш узла; обновление раз в минуту и по кнопке.
- `customer-form/host.ts` (`Backlog`) не перелогинивается по 401 — после
  истечения токена заявки портала не создаются до рестарта контейнера.
