01Главная диаграмма: два слоя и шов

02Поток демо-сценария (8 шагов HowToDemo)

  1. Установка. install.sh спрашивает режим: UI (Docker, автономно) или CLI (скиллы IDE-агента, как раньше). Режимы независимы — проверяется plugin/test-dual-mode.sh.
  2. Подъём UI. cd harness && ./start.sh: генерирует секреты (POSTGRES_PASSWORD, BOX_TOKENS: ui+agent), docker compose up -d, ждёт healthchecks, вытаскивает из логов ссылку ?token=…, открывает браузер и пишет её в harness/.last-url.
  3. Онбординг (первый запуск). 5 слайдов: что это → как вводить → что будет за минуту → доска и статусы → провайдер только Z.AI + ключ + «Проверить» (тестовый вызов). Ключ → harness/.env через host-API плагина → подсказка перезапустить harness-web. «Пропустить» честно предупреждает: без ключа fast не работает.
  4. Интейк — дефолтный экран. Строка ввода: текст, 🎤 голос (Web Speech, дисклеймер приватности), 📎 файлы/фото/PDF (upload → workspace/uploads/<ts>-<slug>/; аудио → whisper.cpp локально), 🔗 ссылки (фиксируются как «Источники»).
  5. Fast-скоринг ≤ 1 мин. Сессия dsh + скилл bft-fast на glm-5-turbo: письмо + personas.csv + requirements.csv + документ-шапка; email-роли Заказчик / PO / Техлид — авторитет в frontmatter contacts:; нераспознанное → открытый вопрос, не заглушка.
  6. Сайдбар «БФТ требования». Верхняя секция — карточки указаний процесса (адресат, суть, дедлайн, действия по типу; бейдж-счётчик на кнопке раздела), ниже — топ последних запросов со статусами; внизу — кнопка «Доска запросов». Кнопка «Запустить проработку» на карточке fast → POST /api/start (явная, без автостарта).
  7. Доска. 9 стадий документа (To Do → FAST-DONE → DEEP-REVIEW → DEEP-DONE → OKR-* / BFT-CANCELED) + чип состояния процесса (waiting_po, working, accepted…). Клик → детальный экран.
  8. Детальный экран. Полная форма БФТ-требований + таймлайн итераций процесса + светофор качества + temporal_url (профиль debug).

03Разделение ответственности (ADR-0001)

СлойОтвечает заНе отвечает за (сознательно)
dsh · интерактив Онбординг, интейк, мини-чат fast, агентные сессии (руки), карточки указаний, доска и документы Долгими состояниями, таймерами «ждать ответ N дней», последовательностями — оркестрации в харнессе нет и не будет
box-mcp · шов Единственная точка связи: MCP агентам, HTTP плагину, Bearer-изоляция, контракт 1.0.0 Бизнес-логикой — только транспорт и авторизация
Temporal · процесс Состояние каждой инициативы, итерации, таймеры, ожидания людей, ретраи — переживает рестарт Интерактивом с человеком напрямую; сессии dsh — расходные исполнители указаний
Сценарии Подписи последовательностей активностей воркфлоу («написать → согласовать → ждать → эскалировать») Отдельным слоем оркестрации — второй оркестратор это то, от чего уходим

04Гибридные исполнители (ADR-0003): кто делает работу

КОРОБКА ПИШЕТ

Deep-итерации пакета БФТ: box-worker сам зовёт LLM (z.ai), светофор качества кодом, ретраи. Контур отлажен 28 контрактными эталонами — не ломаем.

АГЕНТЫ ДЕРЖАТ ИНСТРУМЕНТЫ

Разведка Jira/Confluence (/bft-recon), доставка (/bft-deliver), правки файлов — по указанию, сессией dsh с handoff-черновиком; результат — submit.

ЧЕЛОВЕК РЕШАЕТ

approve_plan, decide, согласования, ответы: карточка в сайдбаре → кнопка → /api/submit. Мозг всегда коробка: агентные исходы — вход итерации, не замена светофора.

08Полосы реализации

Полоса А · Каркас риск: Docker+dsh не проверен апстримом

  • вендор box/ + перенос ADR
  • Dockerfile harness-web (мульти-стадия: сборка плагина → профиль → dsh web)
  • compose целиком + start.sh (секреты, токен-ссылка)
  • гейт: acceptance.sh зелёный, панель плагина монтируется

Полоса Б · Люди

  • онбординг: 5 слайдов + ключ → .env + проверка
  • интейк: ввод (текст/голос/файлы/ссылки) + upload-API
  • мини-чат fast + контакты + карточка результата + «Запустить проработку»
  • гейт: HOWTODEMO шаги 3–5 руками

Полоса В · Процесс

  • сайдбар: секция указаний + бейдж + submit
  • доска: чип состояния; detail: таймлайн + temporal_url
  • руки: handoff-сессии по указаниям, результат → submit
  • первые сценарии согласования активностями воркфлоу
  • гейт: полный HowToDemo 1–8

09Глоссарий (выжимка)

ТерминСуть
Процесс ≠ СессияПроцесс — Temporal-workflow, владелец жизненного цикла. Сессия — чат dsh, расходный исполнитель одного хода. «Сессия процесса» — оксюморон.
УказаниеЕдиница работы процесса, адресованная человеку или агенту; в UI — карточка действия; ответ — submit.
Интейк → fastФорма ввода → быстрый прогон bft-fast: фиксация, не глубина. Глубина — процесс.
Стадия ≠ Состояние процессаСтадия — положение документа из девяти на доске. Состояние — фаза инициативы в коробке. Не путать.
Рука / МозгРука — исполнитель указания (агент или worker). Мозг — коробка: решения и состояния всегда у неё.
Шовbox-mcp: единственная точка связи интерактивного и процессного слоёв.
