# bft-fast Letter Corrections — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans (inline, chosen — edits are small and tightly coupled on one canonical format; a single context keeps them consistent). Steps use checkbox (`- [ ]`) syntax.

**Goal:** Заложить в fast-lane навыка `bft-fast` реальные правки PO к письму (кейс GDSLV-1569, пушкинская карта): WHY-вперёд Цель, гибрид-формат открытых вопросов, блок «Документация», таблица-вложение по флагу `--table`, US-иды вне тела письма.

**Architecture:** `resources/letter_format.md` — единый источник канона формата письма. Остальные файлы (`commands/bft-fast.md`, `SKILL.md`, `extraction_schema.md`, `golden_letter.md`) приводятся к нему. `requirements_table.md` не меняется по содержанию, только помечается как опциональный (флаг). Никаких тестов (markdown-навык) — верификация = grep/read на соответствие канону.

**Tech Stack:** Markdown skill files. Нет сборки, нет автотестов.

## Global Constraints

- Язык файлов — деловой русский, как в существующих ресурсах. Голос — по `bft-writer/resources/writing_style.md` (без эмодзи, без раздутого bold, без тире-связок, без AI-примет).
- Zero-hallucination сохраняется: не выдумывать URL, ФИО, департаменты, сроки. Нет данных — короче/пометка, не догадка.
- docx-канон (`bft-writer/*`, `review_feedback.md`) НЕ трогать — правки только в `skills/bft-fast/*` и `commands/bft-fast.md`.
- Коммиты не делать до явной просьбы PO (правило харнесса важнее «frequent commits»). В конце — предложить коммит.

## Канон (единый источник — вставлять дословно)

### CANON-1 — Шаблон письма (5 блоков; таблица по флагу)

```
Цель: <драйвер/контекст: для эпика X, почему — закон/бизнес/требование>. <что делаем, одно предложение>.

How to demo:
1. <шаг от лица роли-приёмщика; дизамбигуация «X, не Y» в скобках; без внутренних US#N/story-ид>
2. …

Открытые вопросы:
* <вопрос / блокер / решение — одна развилка на строку> (<владелец или «кто уточнит, срок» — если есть>)
* …

Границы: <in-scope сущности> (<out-of-scope> — не входят в зону БФТ).

Документация:
* <указатель одной строкой, или [подпись](URL) где URL известен>
* …
```

Порядок блоков фиксирован: `Цель` → `How to demo` → `Открытые вопросы` → `Границы` → `Документация`. Опц. тир `Дополнительно, если возможно:` и операционные заметки — под «Границами», как раньше (не выдумывать, если пусто). Вложение-таблица — только при `--table`, отдельным блоком ПОСЛЕ письма, не в теле.

### CANON-2 — Открытые вопросы (гибрид)

Строка = сам вопрос / блокер / решение / зависимость, кратко (одна развилка на строку). Владелец НЕ обязательный префикс: указывается в скобках в конце строки, только если известен — как ответственный/исполнитель или «кто уточнит + срок». Плоский список, без группировки по ФИО, без чекбоксов. Допустимы блокеры и зависимости как строки (не только «вопросы»). Неатрибутированная строка — просто без скобок. Не изобретать технические развилки, которых не было на встрече.

Пример-эталон (реальный кейс, вставить в правило дословно):
```
* Релиз не выкатываем, пока не стабилизирован переход с PayBox на Live.Процессинг (блокер)
* Блокирует ли ограничение выпуск GDSLV-1374 (Даня + Катя уточнят у юристов к 29.07)
* Что делаем в смешанных заказах — один билет по пушке, один обычный
* Если заказ по Пушкинской карте — каталог ресторанов всё равно отправляем?
* Откуда и как подтягивать признак оплаты Пушкинской картой (тех. реализация)
```

### CANON-3 — Цель (WHY вперёд)

1-2 строки. Вести с драйвером/контекстом: если фича — под-требование эпика, якорить на эпик и вести с «почему» (юр./бизнес-драйвер, напр. «появилось требование от юристов — …, чтобы не нарушать закон»). Затем «что делаем» одним предложением. Всё из Summary; нет данных о драйвере — короче, не выдумывать.

### CANON-4 — US-иды вне тела

В теле письма нет frontmatter, меток пайплайна, идентификаторов `СТ-*`/`ФТ-*`/`US#N`/story-номеров. Ссылка на родительский эпик (`GDSLV-1374`) допустима как якорь; внутренние user-story/US-номера — нет.

### CANON-5 — Документация

Блок после «Границ». Пункты-указатели на источники (Confluence основной истории, JIRA-эпик, смежные истории). Где URL известен — кликабельная markdown-ссылка `[подпись](URL)`; URL неизвестен — просто человекочитаемая подпись, НЕ выдумывать URL. Нет источников — блок не выводить (без пустого блока).

### CANON-6 — Таблица-вложение по флагу

Генерится только при явном `--table`. Дефолт — только письмо (самодостаточно для пересылки). При `--table` — отдельным блоком после письма: персоны + таблица БТ/ПТ/ИТ/ФТ/НФТ (правила `requirements_table.md` без изменений).

### CANON-7 — Хвост deep-fork

Закрывающая строка о фоновом deep — одна простая строка ВНЕ пересылаемого тела, без внутренностей пайплайна (swarm-субагенты, «3 оси», «тяжелее»). При `--no-deep` — строка о ручной развилке.

### CANON-8 — Durable-урок (блок в letter_format.md)

Компактный блок «Уроки правок PO» со ссылкой на реальный кейс (GDSLV-1569, пушкинская карта), 4-5 буллетов: WHY-вперёд Цель; гибрид-вопросы (блокеры/решения, владелец опц.); +Документация; таблица по флагу; US-иды вне тела.

## Revision 2 — CSV-пивот вложения (правки PO 2026-07-22)

Решения PO после ревью: вложение-таблица = **всегда-вкл `.csv`-файл(ы)**; инлайн-markdown и флаг `--table` (Revision 1) **удалить** (реверт). Разделитель — запятая.

### CANON-CSV-1 — Два файла, всегда

`/bft-fast` всегда пишет два csv в `{docs_path}/{epic_slug}/`, без флага:
- **`personas.csv`** — контекст о стейкхолдерах. Колонки: `ФИО,Роль,Департамент`. Неизвестно → `[роль не подтверждена]` / `[не указано]`.
- **`requirements.csv`** — их требования. Колонки: `ID,ASIS (сейчас),TOBE (после),Связанные,Источник (цитата)`. Порядок строк БТ→ПТ→ИТ→ФТ→НФТ.

Содержание/грунтование — по существующим правилам `requirements_table.md` (zero-hallucination: строка ← цитата; ASIS без реплики → `[ASIS не озвучен]`; без приоритетов/обогащения; «Связанные» — только ID). Новых колонок нет (приоритет/критичность запрещены — обогащение вне fast-lane).

### CANON-CSV-2 — Сериализация

- Кодировка: **UTF-8 с BOM** (Excel корректно открывает кириллицу).
- Разделитель: **запятая** `,`.
- Кавычки: **RFC-4180** — ячейку с `,`, `"` или переносом строки обернуть в `"..."`; внутренние `"` удвоить (`""`). Пустая «Связанные» → пустое поле.
- Первая строка — заголовок с именами колонок.

### CANON-CSV-3 — Emit

- Письмо → в чат (чистые 5 блоков, как в Revision 1). **Инлайн-таблицы в чате нет.**
- Записать `personas.csv` + `requirements.csv`. Нет доступа к папке → рядом с источником, пометка `[УТОЧНИТЬ путь копии]`.
- В чат — одна строка: `Вложение: <path>/requirements.csv (N требований), <path>/personas.csv (M персон)`.

### Правки (реверт `--table` + csv)

- `commands/bft-fast.md`: убрать `--table` (сигнатура/параметр/пример/формат/самопроверка/этапы); FORMAT — убрать инлайн-markdown вложение, описать csv; этап 5 assemble — сериализация csv; этап 6 emit — запись двух csv + строка-ссылка.
- `skills/bft-fast/SKILL.md`: description (csv вместо `--table`), этап 4 assemble (csv всегда), этап 6 emit (два csv + строка).
- `skills/bft-fast/resources/requirements_table.md`: убрать `--table`-пометку; «Форма вывода» → два csv + CANON-CSV-2; правила полей/грунтования без изменений.
- `skills/bft-fast/resources/letter_format.md`: убрать 3× `--table`; вложение = два csv всегда; «Канал вывода» + durable-урок.
- `examples/`: `golden_table.md` → `golden_personas.csv` + `golden_requirements.csv`; `golden_table_precision.md` → `golden_personas_precision.csv` + `golden_requirements_precision.csv`; старые `.md` удалить (ссылок нет).
