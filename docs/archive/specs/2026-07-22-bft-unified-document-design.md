## 1. Контекст и проблема

Текущий v2-поток: `/bft-fast` отдаёт письмо в чат + таблицу требований и **авто-форкает** фоновый `/bft-deep`; `bft-deep-swarm` генерирует **полный канон MTS практически с нуля** из seed; `/bft-deliver` публикует канон в Confluence+JIRA.

Боль:
1. Полный БФТ (выход deep) детальный и корректный, но **тяжело читается** — нет краткого верхнего слоя.
2. Deep **не расширяет формат bft-fast** — это отдельный документ, сгенерированный заново, а не надстройка над шапкой.
3. Нет механизма подхватить брошенный БФТ: если дошли до fast-стадии и забыли — продолжить неоткуда.

## 2. Цель и не-цели

**Цель.** Один документ БФТ, растущий в два такта:
- `bft-fast` собирает **читаемую шапку** (Цель, How to demo, Границы, Открытые вопросы, первичная таблица критичных требований), создаёт **Confluence-страницу (черновик)** и оставляет внизу **открытое поле** — раскрывающийся блок с самодостаточным промтом+контекстом для доведения до полного БФТ.
- `bft-deep` (ручной запуск позже) берёт этот документ за основу, **сохраняет шапку дословно** и **дописывает полный канон MTS ниже**, в область открытого поля. Не переписывает с нуля — обогащает.

**Не-цели.**
- Не меняем 3 оси обогащения по существу (ценность / what-if / границы) — только точку, куда пишется результат.
- Не меняем zero-hallucination дисциплину и высоту БФТ.
- Не вводим новые навыки. Правки — в существующих `bft-*`.

## 3. Сводка принятых решений

| Узел | Решение |
|---|---|
| Структура документа | **Стек**: шапка (формат bft-fast) сверху как TL;DR + полный канон MTS ниже. Шапка — отдельный слой НАД каноном, не входит в фиксированный порядок MTS. |
| Публикация Confluence на fast | **Сухой прогон → «ок» PO → запись** (как `/bft-deliver`). Сохраняет правило «внешняя запись только после явного ок». |
| Открытое поле | **Видимая раскрывающаяся секция** (`<details>` / макрос Expand) с **кодовой секцией** = самодостаточный промт + весь контекст. Human-liftable, работает из чистой сессии. |
| Запуск deep | **Ручной позже** (после ответов PO на вопросы шапки). Авто-форк по умолчанию убран. |
| Пересечение с deliver | deliver **обновляет существующую** страницу (pageId из frontmatter), без дубля; плюс JIRA-эпик + дочерняя «краткое описание» + связи. |
| Судьба письма в чат | **Сохраняется** (пересылаемый артефакт). Confluence-шапка добавляется, письмо не заменяется. |

После `/bft-deep`: секция `## ⏳ Полный БФТ — в проработке` (и её `<details>`) **заменяется** полным каноном MTS; frontmatter `stage: deep`, `status` и верхняя строка-статус обновляются; шапка (всё выше строки-границы) сохраняется дословно.

Пост-deep вид ниже строки-границы — стандартный канон MTS (`bft_standards.md`, порядок разделов ЗМ-005):

```
Бизнес описание → Общая информация → Заинтересованные стороны → История изменений →
Дополнительные материалы → Проблема которую решаем → Изменение в UJM →
План демонстрации (акторы + PlantUML) → Бизнес-Требования (Вводные/вопросы + Ценность/БТ) →
Пользовательские требования (ПТ) → Требования к интерфейсам (ИТ) + Макеты →
Функциональные требования (ФТ) → Нефункциональные требования (НФТ) →
Зависимости → Риски → Ревью требований → Якоря истины
```

**Демаркация шапки и канона.** Граница — HTML-комментарий-маркер `<!-- ═══ ГРАНИЦА ШАПКИ … ═══ -->`. Всё выше — шапка (слой TL;DR, формат bft-fast). Всё ниже — канон MTS. Deep находит маркер, сохраняет префикс байт-в-байт, заменяет суффикс. Маркер устойчив к ручной правке шапки PO.

**Связь ID.** ID в критичной таблице шапки (`БТ-1`, `ПТ-1`, …) === ID в каноне. Шапка = скелет на цитатах; канон разворачивает тот же ID в типизированную таблицу (БТ: Ценность/…; ФТ: Приоритет/…; и т.д.). Deep сохраняет нумерацию шапки, добавляет новые ID при обогащении.

## 5. Открытое поле — спека

Раскрывающийся блок (`<details>` в `.md`, макрос **Expand** в Confluence) в конце шапки. Внутри — кодовая секция (fenced ` ```text `) с портативным промтом. Шаблон, `<…>` заполняются fast из реальных данных (грундинг обязателен — контекст не выдумывать):

```text
Ты — обогатитель БФТ (роль bft-deep-swarm, «Обогатитель»). Перед тобой документ БФТ,
у которого собрана только ШАПКА (Цель, How to demo, Открытые вопросы, Границы, критичные
требования на цитатах). Доведи его до ПОЛНОГО БФТ по корпоративному шаблону MTS,
НЕ ПЕРЕПИСЫВАЯ и НЕ ЗАТИРАЯ шапку.

ЧТО СДЕЛАТЬ:
1. Шапку выше сохрани дословно. Вместо блока «⏳ Полный БФТ — в проработке» построй ниже
   полный канон MTS: Бизнес описание → Проблема → Изменение в UJM → План демонстрации
   (акторы + PlantUML) → Бизнес-Требования (Вводные/вопросы + Ценность/БТ) → Пользовательские (ПТ)
   → Интерфейсы (ИТ) → Функциональные (ФТ) → Нефункциональные (НФТ) → Зависимости → Риски
   → Ревью требований → Якоря истины.
2. Обогати по 3 осям: ценность (зачем инвестировать), «что если» (стресс How-to-demo),
   явные границы (что не входит).
3. ID из шапки сохраняй (БТ-1 в шапке = БТ-1 в каноне); критичную таблицу разверни в
   типизированные таблицы канона.
4. Zero-hallucination: факт без источника → [УТОЧНИТЬ у {кого}], не выдумывай. Высота БФТ:
   без API-контрактов, схем БД, кода — только результат и приёмка.

КОНТЕКСТ ЭТОГО БФТ:
- epic_slug: <slug>
- Источник Summary: <path|URL источника>
- Confluence: <URL страницы | не опубликовано>
- pin_commit (репо poh-bft-writer): <hash>
- Индекс воркспейса: .bft/index/ (если пуст/устарел — сначала /bft-index)
- Открытые вопросы: см. раздел «Открытые вопросы» в шапке выше.

КАК ЗАПУСТИТЬ:
- Если установлен poh-bft-writer: /bft-deep <путь-к-этому-документу>
- Иначе: скопируй ВЕСЬ этот документ в Claude Code и выполни инструкцию выше.
```

**Назначение.** Confluence застрял на fast-стадии, про него забыли — любой PO открывает блок, копирует промт, вставляет в свой Claude Code, доводит до финала. Работает даже если исходная сессия оборвалась.

**Правила.**
- Контекст в промте — только грундированные факты (пути, ключи, hash реальны; неизвестное → `[УТОЧНИТЬ]`/«не опубликовано», не выдумка).
- `pin_commit` — тот же hash, что fast зафиксировал на прогоне (детерминизм deep).
- В Confluence блок оборачивается в макрос **Expand**; кодовая секция — макрос **Code** (или `<ac:structured-macro ac:name="code">`), чтобы промт копировался как есть.

## 7. bft-deep — изменения

**Роль-сдвиг.** Не «генерируй канон из seed», а «**читай документ, сохрани шапку+границу, обогати канон НИЖЕ**».

**Поведение.**
- **Вход:** сам документ. Приоритет — локальный `<docs_path>/<epic_slug>/<epic_slug>.md`. Нет локально, но есть Confluence → `confluence_get_page` по `pageId` из аргумента/поиска. Нет ни того ни другого → работать как раньше (seed=Summary/письмо), но тогда сначала собрать шапку по формату §4.
- **Сохранение шапки:** префикс до строки-границы копируется байт-в-байт. Deep не редактирует Цель/How to demo/Границы/вопросы/критичную таблицу шапки (кроме синхронизации ID при обогащении — по согласованию, иначе не трогать).
- **Обогащение:** заменяет `## ⏳ Полный БФТ — в проработке` + `<details>` полным каноном MTS (3 оси → `/bft-draft` → канон-структура). ID из шапки переиспользуются.
- **Открытое поле после deep:** снимается (задача доведена) ИЛИ превращается в слим-блок «продолжить/уточнить» (по согласованию на ревью спеки; дефолт — снять «⏳ в проработке», оставить компактный «уточнить/переобогатить» промт).
- **Выход:** обновляет **ту же** Confluence-страницу (`confluence_update_page` по `pageId`, сухой прогон превью → «ок» → запись) + локальный `.md`; frontmatter `stage: deep`, `status`, `version++`, `synced`. Стоп на валидированном черновике (`/bft-deliver` не вызывается).

**Файлы.**
- `commands/bft-deep.md`: инструкция — сначала прочитать документ и найти границу шапки; emit — update той же страницы (dry-run+ok), не создавать новую.
- `skills/bft-deep-swarm/SKILL.md`: принцип 1 (есть основа) уточняется — основа = документ-с-шапкой, не голый seed; границы — добавить «обновляет существующую Confluence-страницу после ок PO», снять «не пишет в Confluence» (частично — теперь пишет update после ок).
- `skills/bft-deep-swarm/resources/orchestration.md`: стадия 1 (seed) → «прочитать документ, извлечь шапку, зафиксировать границу»; стадия 11 (emit) → «сохранить шапку + вставить канон ниже + update Confluence (dry-run+ok) + обновить frontmatter».
- `skills/bft-deep-swarm/resources/enrichment.md`: 3 оси без изменений; добавить примечание «результат укладывается ПОД шапку, не поверх».

## 8. Confluence-механика

- **fast → create:** `confluence_create_page`, status «Черновик»; захват `pageId`; запись в frontmatter `source` (URL) + `pageId`.
- **deep → update:** `confluence_update_page` по тому же `pageId`; версия страницы инкрементится Confluence автоматически.
- **deliver → update:** тот же `pageId` (см. §9).
- **Идентичность страницы** держится через `pageId`/`source` во frontmatter — единственный источник правды о том, какую страницу трогать.
- **Макросы** (переиспользуем правила `bft-deliver` §«Конвертация ссылок в макросы»): Expand (открытое поле + «Подробный контекст»), Code (тело промта), PlantUML (диаграммы), Jira-макрос (ключи). Ссылки — только на существующие страницы.
- **Дисциплина записи:** каждая внешняя запись (create/update) — только после явного «ок» PO по сухому прогону. MCP недоступен → `[УТОЧНИТЬ: MCP недоступен]`, локальный `.md` всё равно пишется, не эмулировать успех.

## 9. bft-deliver — реконсиляция

- Источник содержимого — тот же документ `<epic_slug>.md` (шапка + канон).
- **Не создаёт дубль** полной БФТ-страницы: читает `pageId`/`source` из frontmatter; есть pageId → `confluence_update_page` (обновить финальной версией); нет pageId (fast не публиковал) → `confluence_create_page` как раньше, затем записать pageId обратно.
- Остаётся: JIRA-эпик (`jira_create_issue`), дочерняя страница «краткое описание запроса», связи (remote links) — как сейчас.
- Правки минимальны: этап сборки превью-3 (страница БФТ) — ветвление create-vs-update по наличию pageId; захват/запись pageId.

## 10. Грундинг, гейты, валидация

- **Шапка** проверяется только на грундинг (каждое утверждение ← источник или вопрос; каждая строка таблицы ← цитата) — существующие гейты fast.
- **Канон** (ниже границы) валидируется полным набором hard-gates MTS (`/bft-validate`) — существующие гейты deep. Строка «Скоуп документа —» не вставляется (ЗМ-014); шапка не считается разделом канона, «Границы» в шапке не нарушают порядок ЗМ-005.
- **ID-консистентность:** гейт — ID критичной таблицы шапки присутствуют в каноне с тем же типом; расхождение (`БТ-1` в шапке, отсутствует/переименован в каноне) — ошибка.
- **Zero-hallucination** и **высота БФТ** (без API/БД/кода) — без изменений.

## 11. Конфиг

Используются существующие ключи `bft-config.md`: `wiki_space`, `bft_parent_page_id`, `docs_path`, `tracker_projects`. ## 13. Edge cases / деградация

- **MCP/VPN недоступен на fast:** документ пишется локально; `pageId: pending`, `source: [УТОЧНИТЬ — не опубликовано]`; открытое поле помечает «Confluence: не опубликовано»; хендофф говорит опубликовать позже.
- **Deep без локального файла, но со страницей:** `confluence_get_page` по pageId → распарсить шапку/границу → обогатить → update.
- **Deep без документа вовсе:** деградация к текущему поведению (seed=Summary), но сначала собрать шапку по §4, потом канон — чтобы форма осталась единой.
- **PO правил шапку вручную:** deep сохраняет префикс до границы как есть (байт-в-байт), не «чинит».
- **Строки-границы нет (старый/чужой документ):** deep не удаляет ничего вслепую — если маркер не найден, работает как «с нуля», добавляя канон в конец и выводя предупреждение.

## 14. Критерии приёмки

1. `/bft-fast <source>` → письмо в чат + локальный `<slug>.md` со стеком (шапка + строка-граница + открытое поле) + (после «ок») Confluence-черновик с pageId в frontmatter.
2. Открытое поле содержит копируемый промт со всеми грундированными полями контекста; вставка в чистую сессию Claude Code позволяет продолжить.
3. `/bft-deep <slug>` → шапка сохранена дословно; ниже — полный канон MTS; ID шапки == ID канона; та же Confluence-страница обновлена (после «ок»); `stage: deep`.
4. `/bft-deliver <epic>` → не создаёт дубль страницы (обновляет существующую по pageId) + JIRA-эпик + дочерняя + связи.
5. Zero-hallucination и высота БФТ сохранены на обеих стадиях; валидация канона зелёная/жёлтая.
6. MCP-деградация честная, без эмуляции успеха.

## 15. Открытые пункты для ревью спеки

- Судьба открытого поля после deep: **снять** vs **слим-«уточнить»** (дефолт — снять «⏳», оставить компактный re-run промт).
- `document_assembly.md` — отдельный ресурс vs расширение `letter_format.md` (дефолт — отдельный, чтобы letter остался про письмо).
- Синхронизация ID шапки при обогащении: deep только читает ID vs может до-нумеровать в шапке (дефолт — читает, новые ID только в каноне).
