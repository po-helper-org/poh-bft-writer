# Раздел «Управление требованиями» в DeepSeek Harness

Как поднять плагин `poh-bft-plugin` в харнессе — по шагам, которые действительно
отработали. Каждая «грабля» ниже — не предположение: на ней сломался первый
локальный прогон.

Что получается в итоге: кнопка в левом меню, сайдбар с очередью БФТ по стадиям,
доска со всеми стадиями и детальная страница, в которой открывается собранная
страница ревью.

## Что нужно заранее

| Что | Зачем | Проверка |
|---|---|---|
| Node.js ^22.19 или ≥24 | требование харнесса | `node -v` |
| pnpm | им собираются обе стороны | `pnpm -v` |
| Backlog.md (`npm i -g backlog.md`) | необязателен: без него в разделе не будет задач, заведённых до первого `/bft-fast` | `backlog --version` |
| Claude Code CLI | чат на детальной странице (правки, вопросы, `/bft-deliver`); без него «В чат» кладёт черновик в композер харнесса | `claude --version`, `claude mcp list` — сервер Jira/Confluence подключён |

## 1. Харнесс

API плагинов у харнесса ещё alpha и меняется между версиями, поэтому версия
закреплена, а не берётся с `main`.

```sh
git clone --filter=blob:none https://github.com/deepseek-ai/deepseek-harness.git harness
cd harness
git checkout --detach 49a606bc5b5934603f22a26957a07dc799ab0291
pnpm install --frozen-lockfile && pnpm build   # первый раз долго
```

## 2. Плагин

```sh
cd /путь/к/poh-bft-writer/plugin
pnpm install
pnpm build      # tsc в lib/ + браузерный бандл lib/client.js
```

`pnpm build` обязан выпустить **оба** артефакта. Серверная половина — вывод tsc,
браузерная — один бандл `lib/client.js`, который собирает tsdown. Проверить, что
пакет вообще пригоден харнессу, можно не поднимая его:

```sh
bash test-contract.sh    # среди прочего: точка входа отдаёт apply, бандл на месте
```

## 3. Профиль харнесса

Штатная `dsh plugin add` может отрапортовать успех, не изменив манифест профиля,
поэтому профиль пишется руками. Два файла в `harness/.dsh-data/profiles/web/`:

`package.json` — какой пакет ставить и в каком порядке грузить бандлы:

```json
{
  "name": "dsh-profile-web",
  "private": true,
  "dependencies": {
    "poh-bft-plugin": "link:/абсолютный/путь/к/poh-bft-writer/plugin"
  },
  "dsh": {
    "profile": {
      "bundles": ["@deepseek-ai/dsh-base", "@deepseek-ai/dsh-web-app", "poh-bft-plugin"],
      "patchReload": "live"
    }
  }
}
```

`cordis.patch.yml` — настройки. Обязателен один параметр: `workspaceRoot`, корень
воркспейса, где лежат `.bft/` и `backlog/`. Это **не** каталог харнесса.

```yaml
- id: bft-requirements
  config:
    workspaceRoot: '/абсолютный/путь/к/воркспейсу'
    entireBaseUrl: 'https://entire.io/ваша-команда'
    # skill-root воркспейса — чтобы bft-config.md рабочего пространства чатов (bft/)
    # знал, где скрипты навыков; тот же путь, что в customSkillDirs ниже
    skillsPath: '.claude/skills'
    # чат с детальной страницы идёт через Claude Code CLI; под launchd PATH свой —
    # абсолютный путь (`which claude`). `off` — выключить, тогда «В чат» кладёт
    # черновик в композер харнесса
    claudeBin: '/Users/<вы>/.local/bin/claude'
    # права CLI: умолчания плагина плюс MCP-сервер Jira/Confluence, которым
    # пользуется Claude Code на этой машине (`claude mcp list`) — без него
    # /bft-deliver из чата не сможет ни прочитать, ни создать эпик и страницу
    claudeArgs: ['--permission-mode', 'acceptEdits', '--allowedTools', 'Bash(python3:*)', 'Bash(backlog:*)', 'Bash(sleep:*)', 'mcp__MCP_DOCKER']
```

Для `/bft-deliver` из чата в корневом `bft-config.md` воркспейса должны быть
`tracker_projects`, `wiki_space`, `bft_parent_page_id` (см. `bft-config.template.md`);
иначе сухой прогон спросит их в чате каждый раз. Копия конфига в `bft/` производная —
править корневой.

Чаты по требованиям раздел открывает в рабочем пространстве каталога документов
(`bft/` при `bft/documentation`) и регистрирует его сам; `sessionPath: ''`
возвращает чаты в текущее рабочее пространство. Подробно —
`plugin/README.md` §«Рабочее пространство чатов».

Чтобы агент мог заводить требования сам (пункт 5 ниже), в тот же файл добавляется
мост к Backlog.md — тогда `task_create` доступен модели как обычный инструмент:

```yaml
- insert:
    - id: backlog-md
      name: '@deepseek-ai/dsh-mcp-client'
      config:
        serverName: backlog
        transport: stdio
        command: backlog
        args: ['mcp', 'start']
        cwd: '/абсолютный/путь/к/воркспейсу'
        env: {}
```

Установка пакетов профиля:

```sh
cd harness/.dsh-data/profiles/web
pnpm install --ignore-workspace
```

> **Грабля.** Без `--ignore-workspace` pnpm считает каталог профиля частью
> воркспейса харнесса и не ставит ничего — молча, с успешным кодом возврата.
> Признак: в `profiles/web/node_modules/` нет ссылки на `poh-bft-plugin`.

> **Обратная грабля.** Если в каталоге профиля уже лежит свой
> `pnpm-workspace.yaml` (харнесс кладёт его сам: `packages: [.]`,
> `autoInstallPeers: false`), флаг не нужен и вреден: `--ignore-workspace`
> заставляет pnpm не читать этот файл, пиры начинают доставляться, и установка
> падает на `@deepseek-ai/dsh-compact` (404 в npm) — пире `dsh-result-only-view`.
> Есть файл — ставьте просто `pnpm install`.

> **Грабля.** Слой профиля **заменяет** конфигурацию пакета целиком, а не
> дополняет её. Задав здесь `workspaceRoot`, вы теряете всё, что объявлял
> `cordis.patch.yml` самого пакета. Поэтому умолчания живут в коде плагина
> (`plugin/src/config.ts`), а увидеть, что раздел получит на самом деле, можно
> так:
>
> ```sh
> cd harness && pnpm dsh --profile web --dump-config   # ищите id: bft-requirements
> ```

## 4. Запуск

```sh
cd harness
DSH_HOME="$PWD/.dsh-data" pnpm dsh web --no-open --port 3082
```

Ссылку с токеном харнесс печатает сам. При первом открытии он показывает два
окна — уведомление о тестировании и запрос API-ключа; раздел требований работает
и без ключа (`Configure later`), ключ нужен только чату с моделью.

> **Грабля.** Харнесс не подхватывает плагин на живую. После `pnpm build` или
> правки `cordis.patch.yml` его нужно перезапустить.

Дальнейшие обновления до последнего `main` — одной командой из корня чекаута:
`bash update.sh --check` (что отстало) и `bash update.sh --workspace <воркспейс>`
(обновить чекаут, собрать плагин, положить навыки, перезапустить, дождаться 200) —
[`dsh-plugin-update.md`](dsh-plugin-update.md).

## 5. Что должно получиться

1. Харнесс поднялся без ошибок про плагин.
2. В левом меню внизу — кнопка **«Управление требованиями»**.
3. По ней открывается сайдбар: поиск и группы по стадиям, ближе к финалу выше.
4. Внизу сайдбара — **«Открыть доску требований»**, она открывает полноэкранную
   доску со всеми семью колонками (`To Do`, `NEED-CUSTDEV`, `FAST-DONE`,
   `DEEP-REVIEW`, `DEEP-DONE`, `OKR-ADDED`, `BFT-CANCELED`). Все семь должны
   быть в `backlog/config.yml → statuses` воркспейса.
5. Задачи, заведённые агентом через MCP Backlog, появляются в `To Do`.
6. Клик по требованию в сайдбаре раскрывает карточку: стадия, чего не хватает до
   следующей, ссылки, ветка контекста, блок «Последняя сессия» — состояние, давность
   и «Открыть чат». У строк, по которым из раздела уже работали, — точка состояния
   сессии и давность справа.
7. Клик по карточке на доске открывает детальную страницу — слева собранная
   страница ревью в рамке, справа стадия, ссылки и чат с Claude Code: поле
   «Что сделать по этому БФТ» → **«В чат»** запускает ход прямо здесь, поток
   виден в чате, документ на время работы накрыт анимацией и перечитывается по
   завершении. Документа нет — кнопка **«Создать документ»** тем же путём
   запускает `/bft-fast` с источником из задачи; после хода задача сама переходит
   в `FAST-DONE` и получает ссылку на страницу ревью (см. `plugin/README.md`
   §«Доска пишется по факту артефактов»). Для этого `backlog` и `claude` должны
   быть видны процессу харнесса — под launchd свой PATH, надёжнее абсолютные
   `backlogBin` и `claudeBin` в строке профиля.
8. В «Настройки → Плагины» есть карточка **«Требования»**: ссылка на форму сбора,
   ссылка на таблицу, промт синхронизации. После ссылки на форму в шапке панели
   загорается **«+»**, на доске — **«Добавить»**.

Как этим пользоваться шаг за шагом, со скриншотами каждого шага —
[`plugin-playbooks/`](plugin-playbooks/README.md).

## Если не поднялось

**`invalid plugin, expect function or object with an "apply" method`** — точка
входа пакета (`main`) не отдаёт `apply`. Харнесс при этом не стартует целиком, а
не отключает один раздел. Ловится `bash plugin/test-contract.sh`.

**Раздел есть, но пустой** — почти всегда `workspaceRoot` указывает не туда.
Сверьтесь с `pnpm dsh --profile web --dump-config`: там видно, какой путь раздел
получил на самом деле. Полный разбор настроек плагин печатает сам
(`describeConfig`).

**Требования есть, задач доски нет** — либо `backlog` не в `PATH` процесса
харнесса, либо доску выключили (`BFT_BACKLOG_BIN=off`). Отсутствие бинаря не
ошибка: очередь просто остаётся такой, какой была бы без доски.

**Чат на детальной странице пишет «Чат Claude Code выключен в профиле» или ход
сразу падает с `spawn … ENOENT`** — `claudeBin` не задан абсолютным путём или
задан `off`. Под launchd PATH процесса — `/usr/bin:/bin:/usr/sbin:/sbin`,
`claude` из `~/.local/bin` там нет.

**`/bft-deliver` из чата отвечает «MCP недоступен»** — CLI не получил инструменты
Jira/Confluence. Две причины: в `claudeArgs` профиля нет `mcp__<сервер>` (имя —
из `claude mcp list`, в этой установке `MCP_DOCKER`), либо сервер не стартует из-под
харнесса — узел дописывает спавну `/usr/local/bin`, `/opt/homebrew/bin`,
`~/.local/bin`, но команда сервера может лежать ещё где-то. Сухой прогон в чате
показывает, что нашлось: «MCP жив: `jira_get_all_projects` вернул …».

**Кнопка есть, но панель пустая или в консоли ошибка загрузчика** — не собран
браузерный бандл. `exports["./client"]` смотрит на `lib/client.js`; вывод tsc
(`lib/client/index.js`) туда не годится, в нём остаются голые спецификаторы вроде
`react`, которые браузер не разрешает.

## Соседний режим

Плагин не отменяет работу навыками: `.claude/skills` подключаются в харнесс как
нативный skill-root, и `/bft-*` вызываются прямо в чате без всякой сборки.
Включать можно оба режима сразу — что они не мешают друг другу, проверяется
машинно: `bash plugin/test-dual-mode.sh`.

В `cordis.patch.yml` профиля это две строки:

```yaml
- id: skill-filesystem
  name: '@deepseek-ai/dsh-skill-filesystem'
  disabled: false
  config:
    customSkillDirs:
      - '/абсолютный/путь/к/воркспейсу/.claude/skills'
- id: tool-skill
  name: '@deepseek-ai/dsh-tool-skill'
  disabled: false
```

> **Грабля.** В профиле `web` и `skill-filesystem`, и `tool-skill` выключены по
> умолчанию. Не включив обе строки явно (`disabled: false`), вы получите заданный
> `customSkillDirs`, который ни на что не влияет: сам инструмент `skill` при этом
> не существует.
