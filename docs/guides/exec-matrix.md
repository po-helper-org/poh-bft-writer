# Матрица исполнения: договориться с командами и видеть, где ошиблись

Для сложной бизнес-функциональной инициативы одного БФТ мало: работу делают витрина, бэкенд,
аналитика, поддержка — у каждой команды свой план, руководитель и уровень зрелости. Декомпозиция
в Jira живёт внутри команд и стыки между ними не показывает. Матрица исполнения — простой
документ поверх БФТ: **кто** (команда и человек), **что** и **где** делает на каждом стыке и **по
какому критерию** другая команда принимает результат. Команды договариваются по ней на старте, а
дальше по строкам видно, кто где исполнил и где ошибся.

## Поток

```
/bft-deep <epic>                     ← матрица строится только по deep-БФТ
/bft-matrix <epic> <итоги старта>    → <epic>-matrix.md + <epic>-matrix.html
  открыть страницу, комментировать мышью, «Скопировать промт» → в чат агенту
  повторять, пока PO не устроит качество; встреча-старт: команды согласуют версию
/bft-deliver <epic> --matrix         → гейт 23 и проверки → сухой прогон → «ок» → дочерняя страница БФТ
/bft-matrix <epic> --status EX-02 возврат "…"   ← по ходу исполнения
/bft-deliver <epic> --matrix         → та же страница обновляется
```

## Что на странице

- **Сводка исполнения** — по каждой команде: строк, принято, сдано, в работе, заблокировано,
  возвраты сейчас и всего, согласие. Клик по команде оставляет в матрице её строки.
- **Матрица** — строки EX-NN; статус со знаком: ✓ принято, ◐ сдано, ↩ возврат, ⊘ заблокировано,
  ◔ в работе, ○ не начато. ФТ-N ведёт на строку требования на странице БФТ.
- **Чеклисты точек паузы** — старт, стыковка, приёмка, запуск, после запуска; до 9 пунктов.
- **Журнал возвратов** — тип несоответствия, корневая причина, урок.
- Комментарий по выделению адресуется строке (`[Матрица исполнения · EX-03]`), промт заканчивается
  командами проверки (гейт 23) и пересборки страницы.

## Правила, на которых всё держится

1. У строки **один поставщик** (команда и человек) и **проверяющий из другой команды**.
2. Критерий отвечает «да/нет», у него есть **доказательство** — с чем поставщик придёт сдавать.
3. Каждое ФТ, ИТ, НФТ БФТ **покрыто** строками от всех нужных команд; решили не делать — «N/A: причина».
4. **Высота БФТ**: что видит потребитель, а не эндпоинты и поля — контракт у СА.
5. Согласованная матрица **без `[УТОЧНИТЬ]`**, и каждая команда приняла её текущую версию.
6. Возврат — **запись в журнале**; урок становится пунктом чеклиста паузы.
7. Зрелость команды задаёт **режим чеклиста**: C — READ-DO (по шагам), A — DO-CONFIRM (сверка).

Все семь проверяет гейт 23 (`bft-matrix-lint.py`), коды — `skills/bft-writer/resources/hard_gates.md`.

## Откуда взята форма

Готового открытого шаблона «матрицы стыков между командами» нет; форма собрана из практик, у
каждой взято своё (исследование 14.10.2026):

| Практика | Что взяли |
|---|---|
| RACI / RAM (PMBOK), RACI-VSL | один подотчётный на строку; отдельный проверяющий (Verifier) |
| ICD, NASA SE Handbook 6.3 | стык — требования к обеим сторонам; документ согласуется и служит мерой приёмки |
| Team API (Team Topologies) | карточка команды в «Участниках» |
| OpenFastTrace | требование объявляет, какие команды обязаны его покрыть, — проверка покрытия |
| Production Readiness: Mercari (MIT), GitLab | доказательство у каждого пункта, N/A только с причиной, глубина по зрелости, ревьюер от другой команды |
| WHO Surgical Safety Checklist, Checklist Manifesto | точки паузы, READ-DO / DO-CONFIRM, короткие списки |
| Google LCE, AWS ORR | пункты чеклиста растут из реальных сбоев → журнал возвратов и урок |
| DSM, LeSS | карта стыков; ведущая команда при взаимной зависимости |
| SAFe ROAM | состояние рисков стыков |
| Pact / OpenAPI | зелёная проверка контракта — вид доказательства, но не содержание строки |

Чего сознательно нет: задач команд (это Jira), ролей C/I из RACI (шум), тяжёлого
документооборота ICD и отдельного инструмента трассировки (Doorstop, StrictDoc) — результат
уходит в Confluence, а проверку держит лёгкий линтер по образцу `bft-lint.py`.
