# Обновление bft-writer в DeepSeek Harness

Как довести установленный в харнесс bft-writer до последнего `main` на GitHub — и как
понять, что он отстал. Написано для ИИ-агента так же, как для человека: команды точные,
проверки машинные, «готово» — только после HTTP 200.

Одна команда на всё:

```bash
bash update.sh --check                       # что устарело — ничего не меняет
bash update.sh --workspace /путь/к/воркспейсу   # обновить и перезапустить
```

В Claude Code то же самое — `/bft-update` (команда `commands/bft-update.md`).

## Что именно устаревает

В харнессе живут две половины bft-writer, и обновляются они по-разному:

| Половина | Где лежит | Как попадает новая версия |
|---|---|---|
| **Плагин** `poh-bft-plugin` — раздел «Управление требованиями» | `plugin/` чекаута `poh-bft-writer`; профиль харнесса ссылается на него (`link:`), грузит собранный `lib/` | `git pull` в чекауте → `pnpm build` → **перезапуск харнесса** (на живую плагин не подхватывается) |
| **Навыки** `/bft-*` | копия `skills/` и `commands/` в `.claude/` воркспейса, подключённого к харнессу как skill-root (`customSkillDirs`) | `install.sh` из корня воркспейса; харнесс читает `SKILL.md` при сборке каталога навыков |

Обновить одно и забыть другое — типичный источник рассинхрона: навык уже пишет
`-fast.html`, а раздел ещё не умеет ставить по нему `FAST-DONE`, или наоборот. Поэтому
`update.sh` всегда ставит навыки **из того же чекаута**, из которого собран плагин
(`BFT_WRITER_SRC`), а не клонирует их отдельно.

## Как скрипт находит харнесс

1. `DSH_HOME` — из окружения живого процесса `dsh web` (`ps eww`), а не из шелла: у
   launchd своё окружение, и `~/.dsh` в шелле может быть профилем соседнего проекта.
   Нет процесса — `$DSH_HOME`, затем `~/.dsh`. Явно: `--dsh-home`.
2. Профиль — `web` (`--profile`). В нём `node_modules/poh-bft-plugin` обязан быть
   ссылкой на `plugin/` **этого** чекаута; ссылается на другой — скрипт откажется и
   назовёт путь: обновлять надо тот чекаут, иначе `git pull` здесь ничего не изменит в
   харнессе.
3. Воркспейс с навыками — `workspaceRoot` из строки `bft-requirements` в
   `cordis.patch.yml` профиля. Явно: `--workspace`.
4. Перезапуск — launchd-агент с `dsh-harness` в имени (`launchctl kickstart -k`). Иначе
   `--restart-cmd '<команда>'` или `--no-restart` и перезапуск руками.

## Что делает `--check`

Ничего не меняет, печатает отчёт и возвращает `1`, если что-то отстало:

- чекаут против `origin/main`: на сколько коммитов отстаёт, на какой ветке, есть ли
  незакоммиченные изменения;
- `plugin/lib` собран из текущих исходников или старше их;
- навыки воркспейса совпадают с чекаутом байт в байт (каждый `SKILL.md` и каждая
  команда контура из списка `COMMANDS` в `install.sh`);
- харнесс отвечает на `--url` (по умолчанию `http://127.0.0.1:3082/`).

Пример:

```
харнесс:    DSH_HOME=/…/harness-ui/.dsh-data, профиль web
ok    профиль грузит плагин из этого чекаута: /…/poh-bft-writer/plugin
воркспейс:  /…/ishmanov-cortex
чекаут:     5d48684 (main, 2026-09-12); origin/main 5d48684 (2026-09-12); отстаёт на 0, впереди на 0
ok    чекаут на последнем main
ok    plugin/lib собран из текущих исходников
FAIL  навыки в /…/ishmanov-cortex/.claude отстают от чекаута
ok    харнесс отвечает 200 на http://127.0.0.1:3082/
```

## Что делает обновление

По порядку, каждый шаг — гейт для следующего:

1. **Чекаут.** Дерево должно быть чистым и на `main` — иначе стоп: это чекаут
   разработчика, и решать, что делать с его правками, должен человек (`git stash`,
   `git checkout main`). Затем `git pull --ff-only origin main`.
2. **Плагин.** `pnpm install --frozen-lockfile` и `pnpm build` в `plugin/` — обязаны
   появиться оба артефакта, `lib/index.js` (tsc) и `lib/client.js` (tsdown). Потом
   `plugin/test-contract.sh`: точка входа отдаёт `apply`, бандл на месте, стадии и
   обратная запись в Backlog.md работают на настоящих эталонах. Провал — харнесс **не
   перезапускается**: несобранный плагин роняет его целиком, а launchd перезапускает в
   цикле («живой агент, мёртвый порт»). `--skip-tests` снимает гейт, `--no-plugin` —
   пропускает половину.
3. **Навыки.** `install.sh` из корня воркспейса с `BFT_WRITER_SRC=<чекаут>` и
   `BFT_WRITER_AGENT=1` (`.claude/`, без вопросов в терминале). После — та же проверка
   совпадения, что в `--check`. `--no-skills` пропускает.
4. **Перезапуск и проверка.** Команда перезапуска, затем опрос `--url` до `200` (до
   минуты), затем новые строки `/tmp/dsh-harness-ui.log` на `invalid plugin`. Последняя
   строка вывода — «Готово: bft-writer <коммит> в харнессе».

После перезапуска у харнесса новый токен доступа: открытая вкладка получит 401/403,
ссылка со свежим токеном — в последней строке `/tmp/dsh-harness-ui.log`.

## Для ИИ-агента

Запрос «обнови bft-writer в харнессе» / «последняя ли версия стоит?»:

1. `bash update.sh --check` из корня чекаута, который грузит харнесс (скрипт сам
   проверит, что это он). Пересказать отчёт: что отстало.
2. Отстало — `bash update.sh --workspace <корень>`. Не запускать из чата самого
   харнесса: перезапуск убьёт и его, и сессию, из которой позвали.
3. Ветка не `main` или грязное дерево — не обходить, спросить человека.
4. Отчитываться строкой «Готово: …» из вывода; `FAIL` — процитировать причину и
   остановиться. Разбор типовых поломок — [`dsh-plugin-setup.md`](dsh-plugin-setup.md)
   §«Если не поднялось».

## Если профиль ссылается не на этот чекаут

Так бывает после установки «по гайду» в один каталог и разработки в другом. Варианты:
обновлять тот чекаут (`bash <его путь>/update.sh`), либо перевести профиль на этот —
`package.json` профиля, `link:` на `plugin/` нужного чекаута, `pnpm install` в каталоге
профиля, перезапуск (см. [`dsh-plugin-setup.md`](dsh-plugin-setup.md) §3).
