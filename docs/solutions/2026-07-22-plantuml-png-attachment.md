# PlantUML-диаграммы публиковались в вики сырым кодом вместо картинки

## Ситуация

PlantUML-диаграммы раздела «План демонстрации» после отгрузки в Confluence/JIRA показывались
читателю как блок кода `@startuml … @enduml`, а не как отрендеренная диаграмма. Пространство
назначения работало без плагина PlantUML; тот же дефект всплывал и в других опубликованных
документах.

## Причина

Правило отгрузки оборачивало диаграмму в макрос `plantuml`, который рендерится только при
установленном плагине вики. Плагина не было — макрос оставался мёртвым блоком. Хуже того,
fallback-инструкция прямо предписывала «оставить кодом»: инструмент штатно выдавал
нерендерящийся результат и считал это нормой.

## Решение

Дефолтный путь больше не зависит от плагина (`plantuml_render: image` в конфиге):

1. Пре-рендер `@startuml … @enduml` в PNG (`plantuml -tpng`, docker или PlantUML-сервер).
2. Загрузка PNG вложением страницы; fallback — прямой REST-вызов вложений изнутри окружения.
3. В тело страницы (storage) — `<ac:image>` с ссылкой на вложение.

Порядок строгий: создать страницу → загрузить вложение → обновить тело (вложение прикрепляется
только к существующей странице). Макрос `plantuml` остался опциональным путём (`macro`/`auto`
при подтверждённом плагине). Тихий fallback «оставить кодом» удалён: если рендерера нет —
честный маркер `[УТОЧНИТЬ]`, голый код как финал недопустим.

## Как проверить

Собрать документ с UML-диаграммой, отгрузить в пространство без плагина PlantUML, открыть
страницу: диаграмма отображается картинкой-вложением, сырого `@startuml` на странице нет.

## Уроки

- Не полагаться на плагины чужого пространства: рендерить заранее и вкладывать картинку.
- Тихий fallback «оставить как есть» превращает дефект в штатное поведение — такой fallback
  надо запрещать явно, с маркером для ручной доработки.
