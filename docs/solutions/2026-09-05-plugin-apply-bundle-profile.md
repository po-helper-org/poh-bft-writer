# Раздел харнесса не поднимался из-за трёх дыр в упаковке плагина

## Ситуация

Раздел «Управление требованиями» для харнесса не поднимался вовсе. Локальный прогон в настоящем
харнессе нашёл три независимые причины: точка входа не отдавала `apply` (оболочка отвечала
invalid plugin и не стартовала целиком), браузерного бандла не существовало (экспорт смотрел на
вывод tsc с голыми спецификаторами, которые браузер не разрешает), слой профиля заменял
конфигурацию пакета целиком, а не дополнял её.

## Причина

Плагин собирался как node-библиотека, а не как браузерный бандл; контракт оболочки (функция или
объект с методом `apply`) и семантика слоя профиля не были зафиксированы тестом.

## Решение

- Точка входа — объект с `apply`.
- Сборка бандла по рецепту самой оболочки (конфиг `tsdown.config.ts`), вывод — адресуемый
  браузерный бандл.
- Обязательное поле профиля задано, умолчание перенесено в код (задавая одно поле профилем,
  теряли другое).
- Заодно: метод чтения документа не отдавал признак вида, и клиент показывал бы markdown сырым
  текстом.

Закреплено контрактным тестом с тремя новыми шлюзами (точка входа отдаёт `apply`, бандл лежит по
адресу из экспортов и зовёт загрузчик оболочки, бандл не требует ничего вне таблицы модулей),
прогнанными негативно на настоящих дефектах. Ядро вынесено в чистые функции с портом — ядро
проверяется без воркспейса и харнесса.

## Как проверить

```bash
pnpm test
bash plugin/test-contract.sh
bash plugin/test-dual-mode.sh
```

Плюс подъём в настоящем харнессе: старт без ошибок → кнопка в меню → очередь → доска →
детальная страница с документом ревью.

## Уроки

- Контракт упаковки плагина (apply, бандл по адресу, отсутствие внешних требований) — на
  контрактный тест, прогнанный негативно на реальном дефекте.
- Слой профиля у оболочек часто «заменяет», а не « merge-ит» конфигурацию: умолчания держать в
  коде.
- «Плагин поднимается» проверяется только живым подъёмом в целевой оболочке; юнит-тесты этого
  не видят.
