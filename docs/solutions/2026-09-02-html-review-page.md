# Владелец ревьюил документ сырым markdown вместо страницы ревью

## Ситуация

До этого правки обсуждались по сырому markdown-файлу: диаграмма плана демонстрации — блок кода,
идентификаторы требований не кликабельны, точки уточнения приходится искать глазами по всему
документу.

## Причина

Инструмента локального просмотра сгенерированного документа не было; экспорт в вики — отдельная
тяжёлая стадия отгрузки, её нельзя включать в цикл правок.

## Решение

Команда `/bft-html <эпик>.md`: рядом с исходником собирается самодостаточный чёрно-белый
HTML-файл для ревью до и вместо чтения сырого markdown. Ключевое:

- PlantUML-блок плана демонстрации конвертируется в отрендеренную Mermaid-диаграмму (по
  Actor-диалекту, который стандарт уже требует для диаграмм навыка).
- Каждый идентификатор требования становится якорем в месте первого определения; все поздние
  упоминания — ссылками на него.
- Правая панель — оглавление из фактических заголовков; левый ящик — все точки уточнения с
  контекстом, клик прыгает и подсвечивает место.
- Комментарий по точке или по любому выделению сохраняется локально и собирается в готовый
  промт для следующего прохода глубокой проработки.
- Подвал показывает фактический результат линтеров по исходному документу, а не зашитый статус.

## Как проверить

```bash
python3 skills/bft-writer/scripts/bft-html-export.py <эпик>.md
```

Открыть HTML в браузере: диаграмма рендерится, якоря уникальны и ведут на первые определения,
комментарий сохраняется и собирается в промт.

## Уроки

- Цикл правок владельца должен идти по читаемой поверхности (страница с якорями и точками
  уточнения), а не по исходнику; экспорт в вики — не её замена.
- Комментарии ревью сразу копятся в промт для следующего прогона: правка не теряется между
  форматами.
- В статусе страницы показывать фактический прогон линтеров, а не константу.
