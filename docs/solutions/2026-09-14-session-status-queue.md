# Очередь требований не показывала, где агент работает, а где ждёт владельца

## Ситуация

Стадия требования говорит о документе, а не о работе: при пяти параллельных требованиях владелец
не видел, где агент ходит, где ждёт его, а где сессия оборвалась два дня назад, и в каком чате
это было.

## Причина

Журнал работы не знал об идентификаторе и состоянии сессии; чаты, открытые из раздела, не
записывались; перезапуск харнесса посреди хода оставлял записи «выполняется» навсегда.

## Решение

- У отрезка работы появились идентификатор сессии, состояние (ход идёт / простой / провал /
  исчез) и давность последней активности. Чат, открытый из раздела, записывается подкомандой
  привязки.
- Узел слушает события агента и сессий; на старте всё «выполняющееся» становится «проваленным» —
  харнесс перезапустили посреди хода. Записи идут через одну очередь: события приходят пачками.
- Клиент: точка состояния и давность в строке очереди и на карточке доски; блок последней
  сессии с названием чата и кнопкой «Открыть чат» — тот же чат, та же история. Живой список
  сессий харнесса сильнее записи журнала; чат удалён — подсказка начать заново.
- Чаты по требованиям живут в отдельном рабочем пространстве: настройка пути с умолчанием
  «родитель каталога документов»; выход за пределы отвергается. Конфиг для этого пространства
  — копия корневого с пересчитанными путями; уже лежащий не трогается. Раскладку скиллов
  плагин не угадывает — только из настройки.

## Как проверить

```bash
pnpm test
bash plugin/test-dual-mode.sh
```

## Уроки

- Стадия документа и состояние работы — разные вещи; очереди нужны оба, иначе владелец гадает,
  чего ждёт зависшая строка.
- Перезапуск сервиса обязан переводить «выполняющиеся» записи в «проваленные» — иначе они висят
  вечно.
- Сравнение «живой источник сильнее журнала» предотвращает кнопки в никуда (удалённый чат).
