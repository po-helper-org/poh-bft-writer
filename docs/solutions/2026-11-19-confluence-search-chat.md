# Заказчик просил «найди документ» — агент чата искать не умел

## Ситуация

В чате портала /bft заказчик пишет «найди регламент по ремонту» или даёт ссылку на страницу
Confluence. Агент заказчика отвечал, что не может, или пересказывал документ по догадке;
ссылка на Confluence в материалах падала с «нужен вход». Требования собирались без документа,
на который заказчик опирается.

## Причина

`web_fetch` у модели портала выключен (ADR-0017), а ссылки портал читал как публичные
страницы через `ctx.web` — без входа Confluence отвечает 401. Read-only доступ к Confluence
у портала был (шлюз источников, ADR-0015), но им пользовалась только разведка перед полным БФТ.

## Решение

- Служба `dataSources` получила `searchConfluence` и `readConfluencePage` поверх уже
  разрешённых `confluence_search` / `confluence_get_page` — нового доступа нет.
- Агенту заказчика — `search_confluence` (список: название, пространство, ссылка; выбор формой)
  и `attach_confluence_page` (страница — материал заявки `S…`, `.md` в задаче, раздел
  «Приложено заказчиком» в карте находок полного БФТ).
- Ссылки Confluence в сообщении читаются через шлюз, хост сверяется с ответом шлюза.
- Шлюз недоступен — модели только «поиск сейчас недоступен», она просит ссылку или файл.

## Как проверить

```bash
cd customer-form && npm test
```

```bash
bash harness/e2e-customer.sh e2e/confluence.spec.ts
```

E2E с двойниками модели и шлюза (`customer-form/e2e/sources-double.mjs`): «найди документ» →
список → выбор → страница в задаче; запрос со словом «недоступ» — честный отказ.

## Уроки

- Узкий доступ уже есть — расширяй его службу, а не открывай второй канал к тому же источнику.
- Инструменты пресета не видят глобальных служб: адаптер службы кладётся в общий реестр узла.
- Последнее user-сообщение у модели dsh может быть служебным снимком runtime-контекста —
  двойник модели должен искать последнюю реплику заказчика.
- Результат MCP `tools/call` — объект `{content: [...]}`; массив вместо него даёт пустой текст.
