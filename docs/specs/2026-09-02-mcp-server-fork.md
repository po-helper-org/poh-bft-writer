# poh-bft-mcp: развилка «кто генерирует текст» — решение

Спека закрывает **первый пункт** DoD прототипа из issue #9: «Решена развилка sampling vs
собственный вызов модели — с обоснованием». Issue прямо говорит, что всё остальное от неё
зависит, поэтому она закрывается до строчки кода сервера.

Сервер `poh-bft-mcp` живёт **отдельным репозиторием**: issue задаёт границу «не трогать
существующие `skills/` и `commands/` — они остаются каноном контента, сервер их
переиспользует, а не форкает». Здесь — только решение и его следствия.

## Развилка

MCP-сервер своей модели не имеет. Текст БФТ кто-то должен сгенерировать:

- **(а) sampling** — сервер просит модель у клиента (`sampling/createMessage`). Ключ и
  бюджет остаются у клиента, сервер не платит и не хранит секретов. Цена — модель выбирает
  **хост**, а поддержка sampling у хостов неравномерна.
- **(б) собственный вызов** — сервер держит свой вызов Claude API и возвращает готовый
  артефакт. Работает на любом клиенте, включая тот, что sampling не умеет вовсе. Цена —
  ключ и бюджет на стороне сервера.

## Решение

**Гибрид с приоритетом собственного вызова.** Собственный вызов — основной путь и
дефолт; sampling — опциональный режим для организаций, которые не дают серверу держать
ключ. Не наоборот.

### Почему не sampling-first

**Решает не вкус, а собственный критерий приёмки из того же issue:** «артефакты
`bft_fast` побайтово соответствуют текущим golden-эталонам (`skills/bft-fast/examples/`) —
переезд не деградирует качество».

Побайтовое совпадение требует контроля над моделью и параметрами вызова. При sampling
модель выбирает хост: клиент вправе подставить любую модель, свой системный промт и свои
настройки. Один и тот же эпик, начатый с мобильного и продолженный из IDE, пойдёт через
две разные модели — а это ровно тот сценарий, который issue называет главным
пользовательским смыслом сервера. **Критерий приёмки недостижим в sampling-first по
построению**, и обнаружилось бы это на последнем шаге прототипа, а не на первом.

Три довода помельче, в ту же сторону:

1. **Поддержка sampling неравномерна, и хуже всего там, где сервер нужнее.** Целевой
   сценарий issue — «накидать вариант с телефона». Мобильный клиент — наименее
   предсказуемая часть матрицы поддержки.
2. **Репозиторий уже пинит модель постадийно.** `/bft-fast` объявлен рассчитанным на
   Haiku (`skills/bft-fast/SKILL.md` §«Резолв конфига»): проход спроектирован как
   раскладка сказанного по формам, без исследования. При sampling пин становится
   пожеланием: спецификация даёт попросить модель, но решает хост.
3. **Гейты уже машинные.** `bft-lint`, `bft-style-lint`, `bft-ground-lint`,
   `bft-recon-lint`, `bft-env-lint` — скрипты, которые сервер запускает у себя и чей код
   возврата не зависит от того, чья модель писала текст. Это снимает часть риска
   собственного вызова: качество проверяется не доверием к модели, а теми же линтерами.

### Чем платим

Ключ и бюджет на стороне сервера — это реальная цена, и её надо назвать вслух:
мультитенантность, лимиты на пользователя, аудит расхода. Вопрос 5 issue
(«мультитенантность и секреты») из-за этого решения становится обязательным к проработке
в прототипе, а не опциональным.

### Когда включается sampling

Режим `sampling` включается конфигом сервера, когда организация не разрешает серверу
держать ключ. Тогда:

- пин модели передаётся хосту как **пожелание**, а не требование;
- побайтовое соответствие эталонам **не гарантируется** и не проверяется — вместо него
  работают машинные гейты (структура, лексика, грундинг);
- это записывается в артефакт прогона, чтобы расхождение с эталоном потом не выглядело
  регрессией сервера.

Хост не поддерживает sampling и своего ключа нет → сервер отвечает честной ошибкой, а не
деградирует в генерацию «по памяти»: это прямо нарушило бы принцип нулевого допуска к
галлюцинациям.

## Модели по инструментам

Значения — из справочника Claude API на дату этой спеки; перед реализацией сверить
заново, модели и цены меняются.

| Tool | Модель | Почему |
|---|---|---|
| `bft_state` | вызова модели нет | чтение состояния по ключу `(проект, эпик)` — это выборка, а не генерация |
| `bft_fast` | `claude-haiku-4-5` | пин уже задан репозиторием: раскладка сказанного по формам без исследования. $1 / $5 за 1M токенов (вход / выход) |
| `bft_context_pack` | `claude-opus-5` | сборка контекста — это рассуждение по разнородным источникам, самая дорогая ошибка здесь стоит дешевле неверного БФТ. $5 / $25 за 1M |
| `bft_deep` (когда дойдёт) | `claude-opus-5` | аудит с шестью срезами и adversarial-разбором |

Общие параметры вызова: адаптивное мышление (`thinking: {type: "adaptive"}`) для аудита и
сборки контекста; стриминг для длинных выходов, чтобы не упираться в таймаут запроса.
`bft_fast` — самый частый и самый дешёвый вызов, он же кандидат номер один на кеширование
префикса: системный промт и стандарты стабильны от прогона к прогону, меняется только
входной Summary.

## Что НЕ переезжает на сервер

Пункт 6 DoD — записать явно:

| Что | Почему остаётся на месте |
|---|---|
| `skills/` и `commands/` | Канон контента. Сервер их **читает** и отдаёт как MCP-ресурсы и промты; форк канона означал бы два расходящихся набора правил — ровно та болезнь, которую лечил issue #25 |
| Линтеры | Остаются скриптами репозитория. Сервер их запускает, а не переписывает: гейт, переписанный на сервере, разойдётся с локальным |
| Публикация в JIRA/Confluence | В прототипе — только сухой прогон, без записи. Граница задана самим issue |
| STOP-паузы | Инвариант качества, не деталь реализации. На сервере выражаются elicitation либо «tool вернул превью, следующий вызов = согласие» — вопрос 4 issue, открыт |
| `/bft-html` | Локальный рендер для ревью в браузере. Файл рядом с документом полезен именно локально |

## Что дальше

Открытые вопросы 1, 3, 4, 5, 6, 7 issue #9 остаются открытыми — они про транспорт,
хранилище состояния, human-in-the-loop, секреты, сбор контекста без воркспейса и
совместимость. Решённая развилка задаёт им рамку, но не отвечает за них.

Оставшиеся пункты DoD (работающий сервер с срезом `bft_state` / `bft_context_pack` /
`bft_fast`, прогон одного эпика с двух клиентов, побайтовая сверка с эталонами,
инструкция подключения на три клиента) требуют самого репозитория `poh-bft-mcp` и
живого рантайма — из этого репозитория они не закрываются.

## Родственный issue #10

`sa-helper` — та же задача доступности для СТ-требований. Issue #10 сам говорит, что
**исполняется отдельным методом**: форк sa-helper адаптируется под себя. Решение выше
переносимо как рассуждение (тот же критерий воспроизводимости, та же развилка), но
код и репозиторий — не отсюда.
