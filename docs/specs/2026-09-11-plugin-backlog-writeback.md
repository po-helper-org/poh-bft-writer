# Плагин: стадия и ссылка на страницу ревью пишутся в Backlog.md после `/bft-fast`

## Симптом

Сценарий в харнессе: PO выбирает задачу в сайдбаре раздела «Управление требованиями»,
нажимает «Создать документ», в композер ложится `/bft-fast PO-11 «…»`, PO отправляет.
Ожидание — три следствия одного прогона:

1. рядом с документом появилась страница ревью `{slug}-fast.html`;
2. задача доски Backlog.md перешла в `FAST-DONE`;
3. к задаче прикреплена ссылка на страницу.

Факт (прогон PO-11, 2026-09-11): в `bft/documentation/ai-harness-ticketland-php/` лежат
`letter.md` и `ai-harness-ticketland-php.md` (deep-форк), ни `-fast.md`, ни `.html`;
задача `PO-11` — `status: To Do`, `references` пусто, `updated_date` 2026-09-02.

## Диагноз

Три ожидания — три разные дыры, ни одна не закрыта в `main` (`e215f3c`) и ни в одной
ветке.

| Ожидание | Причина |
|---|---|
| `.html` не собран | Харнесс читает только `SKILL.md` (skill-filesystem; `.claude/commands` не читает). Шаг «`python3 … bft-html-export.py`» есть только в `commands/bft-fast.md` (§«Страница ревью — по умолчанию»); в `skills/bft-fast/SKILL.md` этап 6 `emit` его не содержит. В рабочем воркспейсе к тому же стоит старый снимок навыка без HTML вовсе. |
| Статус не обновился | Никто не пишет. Плагин доску только читает (`task list --plain`, `reader.ts` → `withBacklog`); навыки про Backlog.md не знают (grep по `skills/`, `commands/` — ноль совпадений). Конвенция воркспейса (`bft-needed-list/docs/upravlenie-bft-trebovaniyami.md`): «`FAST-DONE` — PO вручную после `/bft-fast`». |
| Ссылка не прикреплена | Тот же ноль. Хуже: плагин сливает задачу доски с эпиком **только по равенству id и слага** (`reader.ts`, `withBacklog`), а `PO-11` ≠ `ai-harness-ticketland-php` — в очереди будут две строки: задача без документа и документ без задачи. Issue #28 это и фиксировал: «настоящий ИИ-агент в харнессе не гонялся». |

Отдельно — среда, в которой симптом снят. Живой харнесс грузит не этот плагин:
`harness-ui/.dsh-data/profiles/web/package.json` ссылается на `dsh-plugin-bft` из
`ishmanov-cortex/harness-ui-plugins/` (прототип, из которого портирован `poh-bft-plugin`),
а навыки берёт из `ishmanov-cortex/.claude/skills`, где `bft-fast` пишет `letter.md`, а в
`bft-writer/scripts/` лежит только `bft-render-html.py`. У прототипа те же дыры: стадию
он берёт из доски, ссылку — из `references` задачи, и ни то ни другое никто не заполняет.

## Что решает спека

Плагин становится **единственным, кто двигает доску по факту артефактов**. Навык пишет
файлы, плагин их видит и приводит Backlog.md в соответствие: стадия — по составу файлов
эпика (`stage.ts` уже это умеет), ссылка — на собранную страницу. PO больше не ходит
руками за `backlog task edit`, а задача и документ перестают жить двумя строками.

Границы:

- доска остаётся необязательной: `backlogBin=off` или нет бинаря — плагин работает как
  сейчас, стадия из артефактов;
- плагин **не запускает** `/bft-fast` и ничего не отправляет в чат — как и раньше, Enter
  жмёт PO;
- плагин не переписывает документ: frontmatter, H1 и состав файлов — собственность
  навыков.

## Шаг 0. Окружение

Без него правки плагина не проверить на живом харнессе. **Выполнен 2026-09-12**: харнесс
на 3082 грузит `poh-bft-plugin` (симлинк `harness-ui-plugins/poh-bft-plugin`, источник
истины — `harness-ui-ops/config/bft-plugin.cordis.yml`), навыки в воркспейсе обновлены
`install.sh`, раздел открывается, `PO-11` виден из доски, `ai-harness-ticketland-php` — из
артефактов, отдельной строкой (та самая развилка шага 1).

1. Профиль харнесса переключить на `poh-bft-plugin`. В
   `harness-ui/.dsh-data/profiles/web/package.json` заменить `dsh-plugin-bft` на
   `"poh-bft-plugin": "link:/абсолютный/путь/к/poh-bft-writer/plugin"` в `dependencies` и
   в `dsh.profile.bundles`; `pnpm install` в каталоге профиля — **без**
   `--ignore-workspace`, если у профиля есть свой `pnpm-workspace.yaml` (харнесс кладёт
   его сам, с `autoInstallPeers: false`): флаг заставляет pnpm игнорировать этот файл,
   и установка падает на `@deepseek-ai/dsh-compact` (404 в npm) — пире
   `dsh-result-only-view`, которого без файла pnpm пытается доставить;
   `pnpm build` в `plugin/`; перезапуск харнесса. В `cordis.patch.yml` профиля строка
   `id: bft-requirements` уже есть — добавить `entireBaseUrl` либо `BFT_ENTIRE_REQUIRED=0`
   в окружение, иначе раздел не стартует (см. `plugin/README.md` §«entire.io обязателен»).
2. Обновить навыки в рабочем воркспейсе: `cd <воркспейс> && bash <poh-bft-writer>/install.sh`
   (выбор 1, `.claude/`). После этого `bft-html-export.py` появляется в
   `.claude/skills/bft-writer/scripts/`.

## Шаг 1. Доска одним вызовом и связка задача ↔ эпик

**Данные доски.** `backlog task list --type bft --json` (Backlog.md ≥ 1.51; ответ
`schemaVersion: 1`, `kind: task-list`) отдаёт за один вызов (~0,2 с) всё, что нужно: `id`,
`title`, `status`, `type`, `references[]`, `updatedAt`. Это снимает сразу три вещи из
первой редакции плана: разбор `--plain` по регуляркам, по одному `task view` на задачу ради
ссылок и утечку задач без типа (в рабочем воркспейсе их 18 — `PO-1`, `PO-1.1`, …;
`parseTaskList` фильтровал тип «только если он в строке есть», прототип такие строки
отбрасывал). Фильтр по типу делает сам CLI, точно по полю. Разбор `--plain` остаётся
запасным путём для CLI без `--json`. Статус вне канона (`In Progress`, `Done`) — задача не
из процесса БФТ, как и раньше, не показывается.

**Связка.** Новый чистый модуль `plugin/src/epic-link.ts`. Признаки, по убыванию
надёжности; первый сработавший — ответ:

1. **ссылка задачи** (`references`) ведёт внутрь `docsPath` — первый сегмент после него и
   есть слаг. Нормализация терпит префикс репозитория, `./`, `.bft`/`bft` (перенос
   `normalizeDocsRef` прототипа). Это durable-связь: её плагин и записывает сам (шаг 2), так
   что все остальные признаки нужны только для первого раза;
2. **слаг равен id** без учёта регистра — конвенция плагина: черновик «Создать документ»
   передаёт навыку `epic_slug` = идентификатор задачи строчными (`po-11`), и документ
   плагин-сценария всегда лежит в `<docsPath>/po-11/`. Прототип ждал ровно этого
   («документ ищется по идентификатору требования»);
3. **H1 документа** `# [БФТ] <slug>: <Название>`: либо `<slug>` в H1 равен id (так модель
   писала вчерашний deep-документ PO-11), либо название совпадает с названием задачи после
   снятия префикса «БФТ:» (регистр, пробелы и кавычки не считаются) — черновик диктует
   название дословно, поэтому совпадение штатное, а не случайное.

Эвристик по времени создания и журналу работы нет намеренно: две задачи, начатые подряд,
они бы перепутали, а перепутанная ссылка хуже отсутствующей. Не связалось — две строки, как
сейчас, и PO добавляет ссылку рукой (`backlog task edit PO-N --add-ref …`), после чего
работает признак 1.

**Слитая запись** в `BftTask`: `id` — идентификатор задачи, новое поле `slug` — каталог
эпика (нет документа — нет поля), стадия — старшая из двух по `CANON_ORDER`
(`stageSource` говорит, чья взяла; `Cancelled` доски терминален и старше всего), `missing` —
всегда по артефактам (что чинить до следующей стадии документа), `links.html` — из
артефактов, название — из H1, когда документ есть. Задача без документа и документ без
задачи остаются отдельными строками. Клиент по-прежнему знает только `id`: `findDocument`
и `handoff` сами переводят id в каталог.

## Шаг 2. Обратная запись в Backlog.md

Порт уже есть — `runCommand` в `ports.ts`. Новый модуль `plugin/src/backlog-writer.ts`:

- `planBacklogEdits(tasks): BacklogEdit[]` — чистая функция: для каждой связанной задачи
  сравнивает стадию по артефактам со стадией доски и ссылку на страницу с `references`;
  расхождения нет — правки нет;
- `applyBacklogEdits(edits, config, ports)` — по одному вызову на задачу:
  `backlog task edit <id> [-s <stage>] [--add-ref <docsPath>/<slug>/<file>.html] --plain`.

Проверено на Backlog.md 1.51: `--add-ref` не дублирует уже записанную ссылку, `-s` вне
`statuses` конфига отклоняется с ошибкой — опечатку CLI не проглотит.

Инварианты:

- стадия двигается **только вверх** по `CANON_ORDER`, вниз — никогда (конвенция «синк
  не понижает»);
- `Cancelled` не трогать ни в какую сторону;
- писать только при расхождении — повторный `reconcile` без изменений на диске ничего
  не вызывает;
- `backlogBin` не задан, `off` или бинаря нет — молчаливый no-op, как у чтения;
- ошибка CLI — строка в лог и в `missing` задачи («доска не обновлена: …»), не падение
  скана.

Что плагин выводит сам и куда переводит:

| Артефакты | Стадия | Ссылка |
|---|---|---|
| `{slug}-fast.md` + `{slug}-fast.html` | `FAST-DONE` | `…/{slug}-fast.html` |
| `{slug}.md` со `stage: deep` (html/страница/эпик неполны) | `DEEP-REVIEW` | `…/{slug}.html`, если есть |
| то же + `{slug}.html` + `pageId` + `jira` | `DEEP-DONE` | `…/{slug}.html` |

`REVIEW-DONE` и `DEEP-WORK` по артефактам не выводятся — их по-прежнему ставит PO.
Проход через них плагин не имитирует: конвенция «по одному шагу» описывает работу PO, а
не запись факта; факт «fast собран» один, и стадия у него одна.

## Шаг 3. Триггеры и черновик

- **Скан.** `reconcile()` = скан → план → запись → повторный скан. Подкоманда `list` зовёт
  его: обновление панели приводит доску в порядок, даже если событие ниже пропущено
  (перезапуск харнесса посреди прогона). Подкоманды `task`, `findDocument`, `handoff` —
  только чтение.
- **Событие агента.** В `plugin.ts` подписка `ctx.on('agent/status', …)` (серверное
  событие харнесса, `AgentStatus = 'idle' | 'running'`,
  `packages/core/agent/src/runtime-types.ts`; плагин уровня композиции получает все агенты):
  `idle` запускает `reconcile()` с дебаунсом ~1,5 с — агент заканчивает ход несколькими
  инструментами подряд.
- **Черновик.** `handoff {id}` для задачи **без документа** возвращает черновик создания,
  а не «продолжи работу»: `/bft-fast` с явным источником (описание, критерии приёмки и
  заметки задачи из `task view --json`, дословно, плюс указание прочитать задачу
  `backlog task view <id> --plain`), названием дословно и `epic_slug` = id строчными.
  «Создать документ» на детальной странице и «Работать в чате» в превью зовут один и тот
  же `handoff`; клиент шаблонов больше не держит. Заодно в журнале открывается отрезок
  (`startWork`), а `reconcile`, подняв стадию, закрывает его итогом
  «FAST-DONE, страница `<путь>`» — следующий заход стартует с записанного итога.
- **Панель.** Пока открыта — тихое обновление списка раз в 30 с (`load({silent: true})`):
  вернувшись из чата, PO видит новую стадию без клика по «Обновить».

## Шаг 4. Страница ревью и источник — навык

Не плагин, но без него `FAST-DONE` недостижим по определению стадии.

- `skills/bft-fast/SKILL.md`, этап 6 `emit`: сразу после сохранения `.md` —
  `python3 <skills_path>/bft-writer/scripts/bft-html-export.py <путь к .md>` (без
  `--no-html`); провал — строка о причине, не остановка. Перенос этапа 7 из
  `commands/bft-fast.md`; харнесс читает только `SKILL.md`.
- `skills/bft-fast/SKILL.md`, этап 1 `resolve-source`: новая форма источника —
  идентификатор задачи Backlog.md (`PO-11`): источник = описание, критерии приёмки и
  заметки задачи (`backlog task view <id> --plain` или инструмент `task_view`); задачи нет
  — ошибка, не эмуляция. То же — в описании `<источник>` в `commands/bft-fast.md`.

## Что не решается здесь

- Прототип `dsh-plugin-bft` в `ishmanov-cortex` не дорабатывается: после шага 0 харнесс
  грузит `poh-bft-plugin`, прототип остаётся историей.

  их можно вывести честно.
