# Плагин: стадия и ссылка на страницу ревью пишутся в Backlog.md после `/bft-fast`

## Симптом

Сценарий в харнессе: PO выбирает задачу в сайдбаре раздела «Управление требованиями»,
нажимает «Создать документ», в композер ложится `/bft-fast PO-11 «…»`, PO отправляет.
Ожидание — три следствия одного прогона:

1. рядом с документом появилась страница ревью `{slug}-fast.html`;
2. задача доски Backlog.md перешла в `FAST-DONE`;
3. к задаче прикреплена ссылка на страницу.

Факт (прогон PO-11, 2026-09-11): в `bft/documentation/ai-harness-ticketland-php/` лежат
`letter.md` и `ai-harness-ticketland-php.md` (deep-форк), ни `-fast.md`, ни `.html`;
задача `PO-11` — `status: To Do`, `references` пусто, `updated_date` 2026-09-02.

## Диагноз

Три ожидания — три разные дыры, ни одна не закрыта в `main` (`e215f3c`) и ни в одной
ветке.

| Ожидание | Причина |
|---|---|
| `.html` не собран | Харнесс читает только `SKILL.md` (skill-filesystem; `.claude/commands` не читает). Шаг «`python3 … bft-html-export.py`» есть только в `commands/bft-fast.md` (§«Страница ревью — по умолчанию»); в `skills/bft-fast/SKILL.md` этап 6 `emit` его не содержит. В рабочем воркспейсе к тому же стоит старый снимок навыка без HTML вовсе. |
| Статус не обновился | Никто не пишет. Плагин доску только читает (`task list --plain`, `reader.ts` → `withBacklog`); навыки про Backlog.md не знают (grep по `skills/`, `commands/` — ноль совпадений). Конвенция воркспейса (`bft-needed-list/docs/upravlenie-bft-trebovaniyami.md`): «`FAST-DONE` — PO вручную после `/bft-fast`». |
| Ссылка не прикреплена | Тот же ноль. Хуже: плагин сливает задачу доски с эпиком **только по равенству id и слага** (`reader.ts`, `withBacklog`), а `PO-11` ≠ `ai-harness-ticketland-php` — в очереди будут две строки: задача без документа и документ без задачи. Issue #28 это и фиксировал: «настоящий ИИ-агент в харнессе не гонялся». |

Отдельно — среда, в которой симптом снят. Живой харнесс грузит не этот плагин:
`harness-ui/.dsh-data/profiles/web/package.json` ссылается на `dsh-plugin-bft` из
`ishmanov-cortex/harness-ui-plugins/` (прототип, из которого портирован `poh-bft-plugin`),
а навыки берёт из `ishmanov-cortex/.claude/skills`, где `bft-fast` пишет `letter.md`, а в
`bft-writer/scripts/` лежит только `bft-render-html.py`. У прототипа те же дыры: стадию
он берёт из доски, ссылку — из `references` задачи, и ни то ни другое никто не заполняет.

## Что решает спека

Плагин становится **единственным, кто двигает доску по факту артефактов**. Навык пишет
файлы, плагин их видит и приводит Backlog.md в соответствие: стадия — по составу файлов
эпика (`stage.ts` уже это умеет), ссылка — на собранную страницу. PO больше не ходит
руками за `backlog task edit`, а задача и документ перестают жить двумя строками.

Границы:

- доска остаётся необязательной: `backlogBin=off` или нет бинаря — плагин работает как
  сейчас, стадия из артефактов;
- плагин **не запускает** `/bft-fast` и ничего не отправляет в чат — как и раньше, Enter
  жмёт PO;
- плагин не переписывает документ: frontmatter, H1 и состав файлов — собственность
  навыков.

## Шаг 0. Окружение

Без него правки плагина не проверить на живом харнессе.

1. Профиль харнесса переключить на `poh-bft-plugin`. В
   `harness-ui/.dsh-data/profiles/web/package.json` заменить `dsh-plugin-bft` на
   `"poh-bft-plugin": "link:/абсолютный/путь/к/poh-bft-writer/plugin"` в `dependencies` и
   в `dsh.profile.bundles`; `pnpm install --ignore-workspace` в каталоге профиля;
   `pnpm build` в `plugin/`; перезапуск харнесса. В `cordis.patch.yml` профиля строка
   `id: bft-requirements` уже есть — добавить `entireBaseUrl` либо `BFT_ENTIRE_REQUIRED=0`
   в окружение, иначе раздел не стартует (см. `plugin/README.md` §«entire.io обязателен»).
2. Обновить навыки в рабочем воркспейсе: `cd <воркспейс> && bash <poh-bft-writer>/install.sh`
   (выбор 1, `.claude/`). После этого `bft-html-export.py` появляется в
   `.claude/skills/bft-writer/scripts/`.

## Шаг 1. Связка задача ↔ эпик

Новый чистый модуль `plugin/src/epic-link.ts`: `linkTasksToEpics(backlogTasks, epics)`.
Признаки связи, по убыванию надёжности; первый сработавший — ответ:

1. **ссылка задачи** ведёт внутрь `docsPath` — первый сегмент после него и есть слаг
   (перенести `normalizeDocsRef`/`epicSlugFromRefs` из `document-source.ts` прототипа:
   они уже терпят префикс репозитория и `.bft`/`bft`);
2. **H1 документа** содержит ключ задачи: `# [БФТ] PO-11: …`. Сейчас `H1_RE` в `reader.ts`
   берёт только название после двоеточия — расширить захватом ключа;
3. **слаг равен id** — текущее поведение, остаётся последним.

Для (1) нужны `references` задачи, а `task list --plain` их не отдаёт — читать
`task view <id> --plain` по каждой задаче типа `bft` (перенести `parse-view.ts`
прототипа; разбор `References:`). Вызовов столько, сколько задач; на доске десятки —
приемлемо, но результат кэшировать на время одного `scan`.

Слитая запись в `BftTask`: `id` — идентификатор задачи, новое поле `slug` — каталог
эпика, стадия — старшая из двух по `CANON_ORDER` (`stageSource` говорит, чья взяла),
`links.html` — из артефактов. Задача без документа и документ без задачи остаются
отдельными строками, как сейчас.

## Шаг 2. Обратная запись в Backlog.md

Порт уже есть — `runCommand` в `ports.ts`. Новый модуль `plugin/src/backlog-writer.ts`:

- `planSync(task): BacklogEdit | null` — чистая функция: сравнивает стадию по артефактам
  со стадией доски и ссылку на страницу со списком `references`; расхождения нет —
  `null`;
- `applySync(edit, ports)` — один вызов
  `backlog task edit <id> -s <stage> --add-ref <docsPath>/<slug>/<file>.html --plain`.

Проверено на Backlog.md 1.51: `--add-ref` не дублирует уже записанную ссылку, `-s` вне
`statuses` конфига отклоняется с ошибкой — опечатку CLI не проглотит.

Инварианты:

- стадия двигается **только вверх** по `CANON_ORDER`, вниз — никогда (конвенция «синк
  не понижает»);
- `Cancelled` не трогать ни в какую сторону;
- писать только при расхождении — повторный `reconcile` без изменений на диске ничего
  не вызывает;
- `backlogBin` не задан, `off` или бинаря нет — молчаливый no-op, как у чтения;
- ошибка CLI — строка в лог и в `missing` задачи («доска не обновлена: …»), не падение
  скана.

Что плагин выводит сам и куда переводит:

| Артефакты | Стадия | Ссылка |
|---|---|---|
| `{slug}-fast.md` + `{slug}-fast.html` | `FAST-DONE` | `…/{slug}-fast.html` |
| `{slug}.md` со `stage: deep` (html/страница/эпик неполны) | `DEEP-REVIEW` | `…/{slug}.html`, если есть |
| то же + `{slug}.html` + `pageId` + `jira` | `DEEP-DONE` | `…/{slug}.html` |

`REVIEW-DONE` и `DEEP-WORK` по артефактам не выводятся — их по-прежнему ставит PO.
Проход через них плагин не имитирует: конвенция «по одному шагу» описывает работу PO, а
не запись факта; факт «fast собран» один, и стадия у него одна.

## Шаг 3. Триггер

- **Событие агента.** В `plugin.ts` рядом с инъекцией `connection` подписаться на
  `ctx.on('agent/status', …)` (серверное событие харнесса, `AgentStatus = 'idle' |
  'running'`, `packages/core/agent/src/runtime-types.ts`): переход `running → idle`
  запускает `reader.reconcile()` с дебаунсом в секунду-две — агент мог закончить ход
  несколькими инструментами подряд.
- **Скан.** `reconcile()` зовётся и в начале `scanWorkspace` по подкоманде `list`:
  обновление панели тоже приводит доску в порядок, даже если событие пропущено
  (перезапуск харнесса посреди прогона).
- **Журнал работы.** После `openChatWithDraft` в `client/index.tsx` звать новую
  подкоманду канала `startWork {id, stage}` — в `bft-reader.ts` метод есть, в `channel.ts`
  подкоманды нет. Открытый отрезок говорит `reconcile`, какую задачу ждать; когда стадия
  поднялась, отрезок закрывается `finishWork` с итогом вида «FAST-DONE, страница
  `<путь>`». Так «Работать в чате» в следующий раз стартует с записанного итога, а не с
  нуля.
- **Клиент.** После `agent/status: idle` инвалидировать `task-cache.ts` и перечитать
  список — иначе панель покажет старую стадию до ручного обновления.

## Шаг 4. Страница ревью

Не плагин, но без неё `FAST-DONE` недостижим по определению стадии.

- Перенести этап 7 из `commands/bft-fast.md` в `skills/bft-fast/SKILL.md`, в этап 6
  `emit`: сразу после сохранения `.md` — `python3 <skills_path>/bft-writer/scripts/bft-html-export.py <путь к .md>`;
  провал — строка о причине, не остановка (та же формулировка, что в команде).
- Опционально, страховка в плагине: ключ конфига `htmlExportScript`; если `reconcile`
  видит `{slug}-fast.md` без `{slug}-fast.html`, собирает страницу сам тем же скриптом.
  Навык, который забыл этап 7, перестаёт держать задачу в `To Do`.

- Документация: `plugin/README.md` §«Откуда берётся стадия» (доска теперь пишется, что

## Оценка

Шаги 1–3 — около дня, шаг 4 — час, шаг 5 — полдня.

## Что не решается здесь

- Прототип `dsh-plugin-bft` в `ishmanov-cortex` не дорабатывается: после шага 0 харнесс
  грузит `poh-bft-plugin`, прототип остаётся историей.
- Автоматический перевод в `REVIEW-DONE`/`DEEP-WORK` — нет факта на диске, по которому
  их можно вывести честно.
