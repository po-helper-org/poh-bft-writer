# Плагин: чат по требованию на детальной странице через Claude Code CLI

## Симптом

PO открывает детальную страницу требования, пишет правку в поле «Что сделать по этому
БФТ» и нажимает «В чат». Ожидание — работа идёт прямо на этом экране: на документе видно,
что он прорабатывается, в чате — что делает модель, по завершении документ обновился, а в
чате остался итог.

Факт (до 2026-09-15): «В чат» собирал черновик, клал его в композер сессии харнесса и
закрывал панель. PO оказывался в чате харнесса, сам жал Enter, работал там и возвращался на
страницу перечитать документ. Ни анимации, ни потока модели, ни автообновления. Отдельно PO
сказал: внутренний чат DeepSeek Harness его не устраивает — на детальной странице все
взаимодействия должны идти через Claude Code CLI. И итог хода нужен коротким: список
внесённых правок и открытые вопросы, без описания процесса (антипример — отчёт из сессии
харнесса на PO-22).

Вторая часть (тот же день): `/bft-deliver` из этого чата отвечал «публиковать нечем» —
`bft-env-lint` не нашёл трекера и вики в `.mcp.json`, коннектор Atlassian Rovo требовал
авторизации, — хотя тот же Docker MCP gateway, что у харнесса, у Claude Code подключён на
уровне пользователя (`MCP_DOCKER`).

## Диагноз

| Ожидание | Причина |
|---|---|
| Чат на странице | Панель — оверлей харнесса; его чат живёт в колонке `conversation`, чужой слот в оверлей не встроить, а окно событий сессии открыто только у текущей. Встраивать чат харнесса — значит либо переключать текущую сессию из-под оверлея, либо рисовать транскрипт по его внутренним снимкам. PO это и не нужно: он хочет Claude Code. |
| Итог длинный | Формат итога задают навыки (общие для любого чата), а рядом с документом отчёт «что и как сделано» дублирует сам документ. |
| `/bft-deliver` «нечем» | Три причины разом: (1) харнесс под launchd живёт с PATH `/usr/bin:/bin:/usr/sbin:/sbin`, и `docker mcp gateway` у дочернего `claude` молча не стартовал; (2) неинтерактивный прогон не получает MCP-инструменты без `--allowedTools mcp__<сервер>`; (3) `bft-env-lint` смотрит только `.mcp.json`, а модель, увидев EN002/EN003, не искала инструменты вовсе. Плюс в корневом `bft-config.md` нет `wiki_space`/`bft_parent_page_id`/`tracker_projects`. |
| Ответ PO на вопрос сухого прогона | Каждое «В чат» заворачивало текст в черновик навыка — «ок» приезжало как «Правка PO к документу: ок» с инструкцией править fast-документ. |

## Что решает спека

Чат по требованию идёт **на детальной странице через Claude Code CLI**: узел плагина
запускает `claude -p`, браузер показывает поток и итог, документ и доска обновляются сами.
Композер харнесса остаётся запасным путём (`claudeBin: off`) и единственным для «Работать
в чате» из превью и «Обновить».

Границы:

- навыки `/bft-*` не меняются: формат итога, подсказка про MCP и правило «правка deep —
  всегда `/bft-deep`» живут в черновике плагина (`handoff.ts`);
- плагин не публикует ничего сам: JIRA и Confluence пишет навык `/bft-deliver` после «ок»
  PO, как и раньше; плагин лишь даёт ему среду и показывает результат;
- один ход по требованию за раз: второй параллельно — отказ `chat-busy`.

## Шаг 1. Узел: прогон CLI и события

`src/claude-chat.ts` — реестр прогонов в памяти узла. `start(taskId, prompt, cwd, {resume |
newSessionId, addDir})` спавнит `claude -p --output-format stream-json --verbose
--include-partial-messages [--resume <id> | --session-id <uuid>] [--add-dir <корень>]
<claudeArgs>` через порт `spawnStreaming` (`ports.ts`; черновик — в stdin), переводит
NDJSON-строки в события `chat-events.ts` (`user`, `init`, `delta`, `assistant`,
`tool-start`/`tool-end`, `result`, `stderr`, `exit`) и копит их в прогоне. `poll(runId,
since)` отдаёт хвост, `stop` убивает процесс, `latestFor(taskId)` — последний прогон
(страница, открытая заново, подхватывает идущий).

Форма stream-json снята с `claude` 2.1.236: `assistant` приходит **по каждому завершённому
блоку**, а не по сообщению, и его текст бывает накопительным — поэтому проекция
(`projectTranscript`) закрывает накопленный поток, не заменяя его текстом блока; текст
блока идёт в строку только когда потока не было.

Порт `spawnStreaming` дописывает PATH (`/opt/homebrew/bin`, `/usr/local/bin`,
`~/.local/bin`) — под launchd без этого не стартуют MCP-серверы CLI. Нет порта (тесты,
среда без CLI) или `claudeBin: off` — чат выключен, канал отвечает `chat-unavailable`.

## Шаг 2. Узел: сессия, журнал, доска

`BftReader.chatStart(id, note)`:

- сессия Claude Code известна до запуска: прошлая по требованию — из журнала работы
  (`sessionKind: 'claude'`, `--resume`), новая — `randomUUID()` (`--session-id`);
  журнал получает `attachSession(…, 'claude', 'running')` сразу;
- что уходит CLI: новая сессия — черновик `handoff(id, note)`; продолжаемая с текстом —
  **текст как есть** (ответ в тот же диалог); продолжаемая с пустым полем — черновик
  следующего шага по артефактам;
- cwd — `sessionWorkspace()` (`bft/`), корень воркспейса — `--add-dir`.

`sessionWorkspace()` теперь перечитывает `bft/bft-config.md` из корневого на каждый вызов
(копия производная; PO дописал `wiki_space` в корне — следующий ход его видит). Корневого
нет — копия из шаблона один раз, дальше не трогается.

По завершении (`chatFinished`): `touchSession(idle|failed)` и `reconcile()` — сверка
доски, как после `agent/status: idle` харнесса, которого у внешнего процесса нет.
`planBacklogEdits` дописывает задаче не только страницу ревью, но и ссылки на эпик JIRA и
страницу Confluence из frontmatter (`jira`, `pageId`) — `--add-ref` повторяемый.

Канал `/bft`: `chatStatus {id}` → `{available, run}`; `chatStart {id, note?}` → `{runId,
status, sessionId}`; `chatPoll {runId, since}` → `{status, events, total}`; `chatStop
{runId}`. Коды: `chat-busy`, `chat-run-not-found` (узел перезапускался),
`chat-unavailable`.

## Шаг 3. Черновик: формат итога и среда

`handoff.ts`:

- `RESPONSE_FORMAT` в конце каждого черновика: «Внесены правки:» списком, «Ссылки:» (JIRA,
  Confluence — если публиковал или менял), «Открытые вопросы:» если есть; вопрос PO — прямо
  в ответе;
- `MCP_ENVIRONMENT` — только черновикам `/bft-deliver` и `/bft-deep`: инструменты
  Jira/Confluence — MCP, искать через ToolSearch, подождать подключения (`sleep 20`) и
  повторить; EN002/EN003 по `.mcp.json` при найденных инструментах — не препятствие;
  значения `wiki_space`/`bft_parent_page_id`/`tracker_projects` из ответов PO — в корневой
  `bft-config.md`;
- правка PO к deep-документу — всегда `/bft-deep <slug>`, даже когда по артефактам дальше
  стояла бы отгрузка: `/bft-deliver` унёс бы правку в Confluence вместо документа.

## Шаг 4. Браузер

`DetailPage.tsx` держит состояние хода (доступность чата, прогон, события, ошибка):
`chatStatus` при открытии, `chatStart` по «В чат» и «Создать документ», опрос `chatPoll`
раз в 700 мс до завершения, затем тихое перечитывание задачи и документа (`silent` — без
«загружаю»). Пока ход идёт — плёнка проработки поверх документа (бегущая полоса и подпись,
`pointer-events: none`). `DetailChat.tsx` рисует транскрипт (свои сообщения, поток,
строки инструментов, ошибки; URL кликабельны), статус, итог с кнопкой «Открыть детальную
страницу» и ссылками JIRA/Confluence из перечитанной задачи, поле ввода с подсказкой и
кнопки «В чат»/«Остановить». Правая колонка ограничена высотой тела (`max-height: 100%`):
у многострочного flex-контейнера строка растёт по содержимому, и без потолка транскрипт
уносил поле ввода за край.

Сессия `kind: 'claude'` в `session-view.ts`: состояние из журнала, список харнесса не
при чём, «Открыть чат» не показывается — подпись «Чат Claude Code — на детальной странице».

## Шаг 5. Профиль харнесса

`claudeBin` — абсолютный путь (PATH launchd), `claudeArgs` — умолчания плагина
(`--permission-mode acceptEdits --allowedTools Bash(python3:*) Bash(backlog:*)
Bash(sleep:*)`) плюс `mcp__<сервер Jira/Confluence>` (в cortex — `mcp__MCP_DOCKER`).
Источник истины — `harness-ui-ops/config/bft-plugin.cordis.yml`, копия в профиле `web`.

## Шаг 6. Проверки

- Юнит (`plugin/test/`): `chat-events` — разбор stream-json (init, delta, блоки, tool
  start/end, result, мусор), проекция (поток и блок, схлопывание инструментов, ошибки,
  выход процесса); `claude-chat` — аргументы CLI, черновик в stdin, `since`, занятость,
  запуск/отказ/падение, остановка, `extendPath`; `bft-reader` — недоступность без порта,
  ход с `--session-id`/`--add-dir`, журнал `claude/running` до первого события, повтор —
  `--resume` и текст как есть, пустое поле — следующий шаг, копия конфига следует за
  корневым; `worklog`/`session-view` — вид сессии; `handoff` — формат итога, среда MCP,
  `/bft-deep` для правки на отгрузке; `backlog-writer` — ссылки на эпик и страницу без
  дублей.
- `plugin/test-contract.sh` — без изменений, проходит.
- Живой прогон в харнессе на служебном эпике `zz-smoke` (каталог и запись журнала удалены
  после): правка fast-документа — поток, анимация, автообновление, итог в формате, повтор
  открытия подхватывает транскрипт; `/bft-deliver` — сухой прогон с живым MCP (проекты
  GDSLV/TLND), вопросы в чат, ответ в ту же сессию. Публикация не запускалась.

## Что не решается здесь

- «Работать в чате» из превью и «Обновить» по-прежнему кладут черновик в композер
  харнесса: PO просил Claude Code только для детальной страницы.
- Реестр прогонов живёт в памяти узла: перезапуск харнесса обрывает идущий ход и очищает
  транскрипт на странице (сессия Claude Code на диске остаётся, `--resume` работает).
- e2e `03-detail-page` — от прототипа, не обновлён.
- Значения `tracker_projects`, `wiki_space`, `bft_parent_page_id` для cortex — у PO: без
  них сухой прогон спрашивает их в чате каждый раз.
