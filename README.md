# poh-bft-writer

Автономный генератор БФТ (бизнес-функциональных требований) для эпиков трекера в
корпоративном формате MTS. Переносимый навык: подключается в любой воркспейс, сам строит
контекст, генерирует БФТ уровня отлаженной методологии po-helper — без внешних зависимостей.

**Функция [манифеста](https://github.com/po-helper-org/.github/blob/main/profile/README.md):**
2 — границы и приёмка. Меряется готовностью требований и числом возвратов от
команд-исполнителей.

## Установка

**Через ИИ-помощника:** скажи «Установи bft-writer в этот репозиторий».

**Через терминал:**
```bash
curl -ksSL https://raw.githubusercontent.com/po-helper-org/poh-bft-writer/main/install.sh | bash
```
Скрипт спросит IDE-агента (Claude Code / Codex / Cline / DevX / Universal) и синкнет
команды и навыки в нужный корень. После установки запусти `/bft-index` — навык проведёт
первичную аналитику воркспейса и построит себе контекст.

## В DeepSeek Harness

Репозиторий работает в харнессе двумя независимыми способами. Один не отменяет
другой, и включать можно оба сразу.

**Способ 1 — навыки как есть.** Харнесс умеет подключать `.claude/skills` как
нативный skill-root, и тогда `bft-writer` и его семейство вызываются прямо в
чате, без всякой сборки. Переписывать ничего не нужно: используются те же
`{навык}/SKILL.md`, что положил `install.sh`. Настраивается строкой в конфиге
профиля харнесса — `@deepseek-ai/dsh-skill-filesystem`, ключ `customSkillDirs`.

> **Грабля.** В профиле `web` и `skill-filesystem`, и `tool-skill` выключены по
> умолчанию. Не включив обе строки явно, вы получите заданный `customSkillDirs`,
> который ни на что не влияет: сам инструмент `skill` при этом не существует.

**Способ 2 — плагин `plugin/`.** Даёт то, чего скиллы дать не могут: раздел
«Управление требованиями» в сайдбаре — очередь БФТ по стадиям с поиском,
превью требования, детальную страницу с собранным HTML-документом и доску.

```sh
cd plugin
pnpm install && pnpm build
```

Дальше пакет подключается в профиль харнесса; обязателен один параметр —
`workspaceRoot` (по строке `id: bft-requirements`). Пошаговая установка, разбор
граблей профиля и что должно получиться на экране —
[`docs/guides/dsh-plugin-setup.md`](docs/guides/dsh-plugin-setup.md). Устройство
раздела, переменные окружения и таблица «артефакты → стадия» —
[`plugin/README.md`](plugin/README.md).

**Что выбрать.** Нужен только запуск `/bft-*` из чата — хватит первого способа,
он бесплатный. Нужна очередь требований и чтение документов в интерфейсе —
второй. Backlog.md плагину не обязателен: без него стадия выводится из
артефактов самого документа, с ним на доске видны и требования, заведённые
агентом до первого `/bft-fast`.

Независимость режимов — не договорённость, а проверка: `bash plugin/test-dual-mode.sh`
убеждается, что установка навыков не тянет плагин, плагин не знает про раскладку
IDE-агента, а команды и навыки работают без него.

## Для ИИ-помощника (bootstrap)
Если пользователь просит «Установи bft-writer»: (1) запусти `curl -ksSL <repo>/install.sh | bash`
или склонируй и запусти `install.sh`, выбрав IDE-агента пользователя; (2) после синка — сразу
запусти `/bft-index` для первичной аналитики воркспейса; (3) покажи MANIFEST-покрытие и предложи
`/bft-fast`.

## HowToDemo

1. «Установи bft-writer» или curl из README → навык в репозитории.
2. Команды `/bft-*` доступны.
3. `/bft-index` проводит первичную аналитику и строит контекст (`.bft/index/`).
4. Полный контур: `/bft-fast → /bft-deep → /bft-deliver` (STOP-паузы, human-in-the-loop), плюс `/bft-html` для ревью в браузере и `/bft-custdev`, когда пробел закрывается только разговором с заказчиком.
5. Единый растущий документ:
   `/bft-fast` — **стенографист**: наружу не ходит (ни JIRA, ни Confluence, ни индекс),
   фиксирует продиктованное PO в правильной форме. Письмо в чат + два csv-вложения +
   локальный документ-шапка `<epic_slug>-fast.md` (Цель = SMART-таблица, How to demo,
   Ограничения и договоренности, Документация, Критичные требования на цитатах,
   Общая информация) + открытое поле
   с промтом для доведения. Сразу после записи собирает страницу ревью `<epic_slug>-fast.html`
   рядом с документом — её и читает PO (`--no-html` отключает). Открытые вопросы уходят
   в чат, не в документ. Рассчитан на Haiku;
   `/bft-recon` — **разведчик**: пока вы читаете письмо, фоновый субагент обходит
   JIRA и Confluence **только на чтение** и кладёт рядом карту находок
   `context_map.md` — что по теме уже описано, с чем пересекается, что раньше
   отклонили, кто вёл тему. В письмо, csv и документ ничего не дописывает: находки
   приходят нотификацией со ссылками, решение за PO (`--no-recon` отключает);
   `/bft-custdev` — **методолог интервью**: когда пробел закрывается не поиском, а разговором,
   собирает скрипт по собранному БФТ — берёт `<epic_slug>.md` со `stage: deep`, если он есть,
   иначе `<epic_slug>-fast.md`. Результат встречи — шесть блоков: для кого, какую проблему
   решаем, как принимается работа, как поймём что решает, кто вовлечён, какое решение видит
   запрашивающий. Запрос, пришедший решением («расширить кафка-топики»), требованием не
   принимается: скрипт ведёт по лестнице вверх до эффекта, а исходную формулировку кладёт
   гипотезой решения с критерием успеха. Вопрос заводится только на пробел, обычно выходит
   6–9 на разговор в 5–10 минут. Рядом со скриптом `<epic_slug>-custdev.md` кладёт страницу
   встречи `<epic_slug>-custdev.html`: один вопрос на экран, вложения по Ctrl+V, промт на
   экране итога — он вместе с транскрибацией возвращается в `/bft-fast` или `/bft-deep`.
   Форкается в фоне после разведки, `--no-custdev` отключает; после `/bft-deep` пересобирается
   вручную по канону;
   `/bft-deep` — **аудитор**: начинает с сетапа окружения (проверяет подключения к трекеру
   и вики, помогает подключить, недоступное честно помечает `UNAVAILABLE`), поднимает индекс
   `.bft/index/`, Confluence, JIRA, git и прошлые артефакты, сначала формирует уточняющие
   вопросы к PO по шести срезам
   (пробел / противоречие / edge-кейс / граница / термин / риск), затем пишет полный документ
   `<epic_slug>.md` с каноном из 11 разделов и обновляет страницу
   (форкается в фоне автоматически, `--no-deep` отключает, либо запускается вручную);
   `/bft-deliver` — JIRA-эпик, **одна** страница Confluence, связи; страницу обновляет, не дублирует (ЗМ-031).
   Форк отключён, упал или про задачу забыли — открой блок «Довести до полного БФТ» внизу
   документа, скопируй промт в Claude Code и продолжи с любой точки.
6. Результат соответствует практикам po-helper: **22 hard gate** (число и состав — `skills/bft-writer/resources/hard_gates.md`, единственный источник правды; из них машинные: 17 — структура, 18 — anti-slop лексика и редактура, 19 — сверка с источником, 20 — карта контекста `/bft-recon`, 22 — скрипт интервью `/bft-custdev`), стиль/голос, Lessons Learned, урезанный канон MTS (ЗМ-016), ранги якорей.

## Проверка шаблона (гейт 17)

Структуру документа проверяет скрипт, а не самоотчёт модели. `<skills_path>` — папка `skills/` установки:
`.claude/skills` (Claude Code), `.agents/skills` (Codex), `.clinerules/skills` (Cline/DevX) или `skills` при запуске
из клона репозитория; переопределяется ключом `skills_path` в `bft-config.md`.

```bash
python3 <skills_path>/bft-writer/scripts/bft-lint.py .bft/documentation/<epic_slug>/<epic_slug>.md
python3 <skills_path>/bft-writer/scripts/bft-style-lint.py .bft/documentation/<epic_slug>/<epic_slug>.md
python3 <skills_path>/bft-writer/scripts/bft-ground-lint.py .bft/documentation/<epic_slug>/<epic_slug>.md --source <входной Summary> --strict
```

Ненулевой код выхода — документ не по шаблону: потеряна строка-граница шапки, пропал раздел
канона, пустая колонка «Источник (цитата)», пустой блок сценария приёмки, строки-заглушки в
таблицах. `/bft-fast` и `/bft-deep` прогоняют линтер перед каждой записью файла и не
сохраняют документ с ошибками. Самотест самого линтера:

```bash
bash <skills_path>/bft-writer/scripts/test-bft-lint.sh
```

Ссылки самих команд и навыков на ресурсы проверяет отдельный линтер — он разворачивает
виртуальную установку всех раскладок `install.sh` и падает, если ссылка не резолвится
хотя бы в одной (корневая `skills/…` после установки не резолвится нигде):

```bash
python3 <skills_path>/bft-writer/scripts/bft-paths-lint.py
```

Подключения к трекеру и вики `/bft-deep` проверяет на стадии сетапа окружения: живой read-only
вызов делает агент, а форму конфига MCP — линтер (объявлены ли трекер и вики, не записан ли
секрет значением вместо ссылки на переменную окружения):

```bash
python3 <skills_path>/bft-writer/scripts/bft-env-lint.py .mcp.json
bash <skills_path>/bft-writer/scripts/test-bft-env-lint.sh
bash <skills_path>/bft-writer/scripts/test-bft-html-export.sh
```

Карту контекста `/bft-recon` проверяет свой линтер (гейт 20) — находка без ссылки
непроверяема, а отсутствие раздела «Что не найдено» выдаёт молчание за пустой результат:

```bash
python3 <skills_path>/bft-writer/scripts/bft-recon-lint.py .bft/documentation/<epic_slug>/context_map.md
bash <skills_path>/bft-writer/scripts/test-bft-recon-lint.sh
```

Скрипт интервью `/bft-custdev` проверяет свой линтер (гейт 22): гипотеза без одного из
четырёх блоков непроверяема, метрика блокера и метрика цели обязаны быть одной метрикой, а
вопрос без пробела-источника тратит время встречи. Форма вопроса выводится предупреждением,
а не отказом — канон методички сам держит закрытые уточнения внутри ячеек:

```bash
python3 <skills_path>/bft-writer/scripts/bft-custdev-lint.py .bft/documentation/<epic_slug>/<epic_slug>-custdev.md
bash <skills_path>/bft-writer/scripts/test-bft-custdev-lint.sh
bash <skills_path>/bft-writer/scripts/test-bft-custdev-export.sh
```

## Быстрый старт

1. `cp bft-config.template.md bft-config.md`, заполни (или оставь пусто — автодетект).
2. `/bft-index` — построить контекст.
3. `/bft-fast <источник> <epic>` — зафиксировать сказанное. Дальше `/bft-deep <epic>` и `/bft-deliver <epic>`.
4. Скрипт CustDev-интервью собирается сам после разведки — вместе с `/bft-fast`. Канон собран (`/bft-deep` отработал) — пересобрать по нему: `/bft-custdev <epic>`. Разбор прогона целиком — в разделе ниже.

## Пример: `/bft-custdev` от пробела до уточнённого БФТ

Прогон целиком, на живых артефактах. Эпик — раздел закрывающих документов в личном кабинете
юрлица; после `/bft-fast` в документе осталось пять точек `[УТОЧНИТЬ]` и пять ячеек
`[ASIS не озвучен]`. Такой пробел закрывается не поиском, а разговором.

### 1. Запуск

`/bft-fast` форкает подготовку в фоне после разведки, поэтому обычно команда не нужна.
Руками — когда форк отключён флагом, упал, документ правили, или `/bft-deep` собрал канон
и скрипт пора пересобрать по нему:

```
/bft-custdev lk-closing-docs
```

Читаются артефакты эпика: `<epic>-fast.md` (обязателен), `personas.csv`,
`requirements.csv` и `context_map.md`, если разведка уже отработала. Ни один из них на
запись не открывается.

```
.bft/documentation/lk-closing-docs/
├── lk-closing-docs-fast.md        ← вход: документ и его пробелы
├── personas.csv                   ← вход: кто участники и что решают
├── requirements.csv               ← вход: где [ASIS не озвучен]
├── lk-closing-docs-custdev.md     ← выход: скрипт интервью
└── lk-closing-docs-custdev.html   ← выход: поверхность встречи
```

### 2. Что интервью обязано принести

Шесть блоков. Известное берётся из fast-документа с источником, неизвестное помечается
пробелом — и только пробел порождает вопрос:

| Блок | Что уже знаем |
|---|---|
| Для кого | `[пробел]` |
| Какую проблему решаем | `[пробел]` |
| Как принимается работа | `[пробел]` |
| Как поймём, что решает | `[пробел]` |
| Кто вовлечён | Марина Гущина, Сергей Дорохов |
| Какое решение видит запрашивающий | Раздел «Документы» в ЛК |

Блоки «приёмка» и «измерение» главные: без них БФТ писать не из чего.

### 3. Запрос пришёл решением — поднимаем до проблемы

Запросы приходят решением, услышанным где-то от кого-то, а не проблемой:

| | Плохо | Хорошо |
|---|---|---|
| Запрос | Расширить кафка-топики для получения информации | Вывести КИНО на VibeApp, чтобы заработать деньги |
| Почему | это решение: неизвестно, чья боль, как принимать и чем мерить | назван носитель, эффект и по чему считать |

Скрипт такой запрос требованием не принимает. Лестница вверх: что произойдёт, если не
сделать → кто заметит первым → что делает вместо этого → по чему поймём, что помогло.
Исходная формулировка уезжает в блок 6 как гипотеза решения с критерием успеха.

Вопросы помечены исходом, который закрывают, и порядок в скрипте — по исходам:

| # | Вопрос | Что хотим узнать | Кому | Пробел |
|---|---|---|---|---|
| В-4 | Что вы откроете и увидите, чтобы сказать «готово»? (Приёмка) | Точка приёмки | Марина Гущина | блок «Как принимается работа» · `[пробел]` |

Пробел без вопроса — ошибка гейта 22 (`CD006`): документ делал бы вид, что встреча его
закроет.

### 4. Встреча по `<epic>-custdev.html`

Страницу открывают локально и показывают на разговоре. **Один вопрос на экран** — текст,
что хотим узнать, кому, поле ответа, «Назад / Пропустить / Далее», полоса прогресса.
Ctrl+Enter ведёт дальше, не отрывая рук от клавиатуры.

Слева рейка: «Материалы» (гипотеза, «что унести» с отметкой пробелов, участники) и «Email
Agenda». Справа выезжает список вопросов с отметками — прыжок к любому без прохода по всем.
Промт и выгрузка ждут на экране итога.

К каждому вопросу прикладываются файлы: кнопкой, перетаскиванием или Ctrl+V со скриншотом
из буфера — на доске и на экране информации часто больше, чем участник успевает
проговорить. Файлы уходят на диск вместе с ответами и перечислены в промте по вопросам.

Ключ ответа — хэш текста вопроса, а не номер строки: пересобрали скрипт после правки
документа, и уже данные ответы остались на своих вопросах.

### 5. Письмо участникам

Вкладка «Email Agenda» отдаёт готовое приглашение, собранное из целей интервью и
дополнительных гипотез: цель встречи, вопросы к обсуждению с разбивкой по адресатам,
тайминг одной цифрой. Внутренние маркеры (`← пробел`, слаг эпика, `[кому?]`) в письмо не
попадают — оно уходит наружу. Текст правится прямо в панели, кнопки копируют его или
открывают в почтовом клиенте; адреса заполняет PO.

### 6. Возврат ответов — новой команды нет

Экран итога собирает готовый текст для чата: пары «вопрос → ответ» с автором, что не
проверили, и правила для следующего прогона.

```
Внеси в lk-closing-docs-fast.md результаты CustDev-интервью по скрипту от 2026-09-07.

Ответы:
8. [Дополнительная гипотеза Г-2] Расскажите, что происходит с документом от закрытия
   периода до момента, когда клиент может его забрать?
   → «Период закрывается первого числа, документы формируются пакетом и подписываются
     до пятого. Раньше пятого их нет физически» (Сергей Дорохов)

Не проверено, до этого не дошли: 22 вопроса основного скрипта.

Правила: ответ участника — цитата-источник требования; закрывай [УТОЧНИТЬ] только тем,
что прозвучало; опровергнутую гипотезу не правь молча, вынеси вопросом в чат.
```

Промт вместе с транскрибацией уходит в чат, принимает его повторный `/bft-fast <epic>` — или
`/bft-deep`, если канон уже собран. Кнопка «Скачать ответы» на том же экране отдаёт `<epic>-custdev-answers.md`
как архив встречи.

### 7. Что меняется в документе

Ответ участника становится цитатой-источником требования, и закрытый им `[УТОЧНИТЬ]`
получает нормальный якорь вместо маркера. В этом прогоне:

| Показатель | До интервью | После |
|---|---|---|
| Строк требований | 6 | 9 |
| `[ASIS не озвучен]` | 5 | 3 |
| `[УТОЧНИТЬ]` в шапке | 5 | 3 |

Из ответа Сергея Дорохова выросли ИТ-2 (признак «формируется») и НФТ-2 (документ доступен к

## Команды

| Команда | Роль | Артефакт |
|---|---|---|
| `/bft-index` | Context Builder | `.bft/index/` (пакеты знаний) |
| `/bft-deliver` | Deliverer | публикация: JIRA Эпик + **одна** страница Confluence + связи |
| `/bft-html` | Ревью в браузере | `<epic>.html` рядом с документом — диаграмма, якоря на ID, панель `[УТОЧНИТЬ]`, комментарии → промт. **Обычно вызывать не нужно:** страницу собирают сами `/bft-fast` и `/bft-deep` (ЗМ-033), команда — ручная пересборка |
| `/bft-fast` | Fast lane | письмо + csv-вложения + документ-шапка `<epic>-fast.md`. Наружу не ходит: ни JIRA, ни Confluence, ни индекс — публикует `/bft-deliver` |
| `/bft-recon` | Разведка контекста | `context_map.md` — карта находок JIRA/Confluence со ссылками |
| `/bft-custdev` | Методолог интервью | скрипт интервью `<epic>-custdev.md` + страница встречи `<epic>-custdev.html`. Собирается по свежайшему документу эпика: `deep`, если есть, иначе `fast` |
| `/bft-deep` | Deep swarm | тот же документ, обогащённый каноном |

**Внутренние.** `/bft-draft` (генератор текста канона) и `/bft-validate` (прогон 22 гейтов) вызываются оркестрацией `/bft-deep`, руками их запускать не нужно; отдельный запуск `/bft-validate` остаётся возможным, когда нужно перепроверить готовый документ.

Пошаговый пайплайн v1 (`/bft-context-gen`, `/bft-problem`, `/bft-concept`, `/bft-debate`) снят — см. `docs/archive/README.md`.

## Как это работает

Пайплайн якорится на `.bft/index/` — само-генерируемый набор markdown-пакетов
(архитектура, домен-правила, решения, глоссарий, стейкхолдеры, реестр якорей). `/bft-index`
собирает их из локальных доков, кода (через serena MCP) и трекера (JIRA/Confluence MCP,
опционально). Каждый факт в БФТ прослеживается до источника; неизвестное помечается
`[УТОЧНИТЬ]`, не выдумывается.
