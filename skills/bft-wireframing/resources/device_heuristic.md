# Рамка кадра: browser или mobile

Один документ может использовать обе — сценарий про сайт-витрину рисуется
в браузере, соседний про мобильное приложение того же продукта — в телефоне.
Решение принимается **на уровне сценария**, не на уровне всего документа.

## Порядок проверки (первое совпадение решает)

1. **Явное указание в тексте.** Сценарий или блок «Ограничения и договоренности»
   называет платформу прямо: «мобильное приложение», «в браузере», «на сайте»,
   «в личном кабинете», «приложение iOS/Android» → по названному.
2. **Контекст продукта в разделе «Требования к интерфейсам\*».** Там уже может
   стоять строка контекста (платформа/браузеры/адаптив) — она сильнее догадки
   по формулировке отдельного сценария.
3. **Природа действия.** Действия вида «просматриваю уведомление на телефоне»,
   «сканирую QR», «получаю push» — mobile без дополнительных сигналов. Действия
   вида «открываю панель управления», «смотрю сводку/дашборд», «настраиваю
   пороги и лимиты» — типичный внутренний back-office, browser.
4. **Не определяется ни по одному признаку → browser.** Панели управления,
   отчётность и административные интерфейсы (обычный профиль продукта в БФТ
   этого репозитория) чаще живут в браузере; мобильный форм-фактор — исключение,
   которое называют явно, а не подразумевают.

## Что не считается сигналом

Слово «приложение» само по себе не означает mobile — веб-приложение тоже
«приложение». «Личный кабинет», «панель», «дашборд», «консоль» — почти всегда
браузер, даже если у них есть адаптивная вёрстка под телефон: адаптив — это
про то же самое browser-окно на узком экране, не про отдельный мобильный кадр
с системными жестами и tabbar.

## Смешанный сценарий

Если один сценарий явно проходит через оба контура (например, действие в
браузере и последующее push-уведомление на телефоне) — это два отдельных
блока `wireloom-storyboard` (browser и mobile) под одним сценарием, каждый
описывает свою часть пути, а не один блок с кадрами разных рамок вперемешку.
