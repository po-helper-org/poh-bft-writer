# Карта инициативы в Backlog.md — стандарт второго этапа blueprint (backlog_rules.md)

Карта ложится на согласованную историю и отвечает на три вопроса:
- что увидят люди;
- что делает каждая команда;
- как это работает.

Все её данные хранятся в проекте [Backlog.md](https://github.com/MrLesk/Backlog.md): задачи, подзадачи и документы — markdown-файлы в git. Агент ведёт их CLI `backlog`. Страница карты и архив проекта собираются из этих файлов детерминированно, без ИИ (`scripts/bft-backlog-build.py`).

Эталон — `examples/bartello-restart-blueprint/`. Проверка — `scripts/bft-backlog-lint.py`.

## Путь

1. **Исследование** — прочитай БФТ целиком и согласованную историю `<epic>-story.md`.
2. **Проект** — `bft-backlog-init.py <epic>-story.md` создаёт папку `<epic>-blueprint/` — проект Backlog.md (префикс задач `bp`, без git) с документами «Карта» и «История».
3. **Бэклог** — команды и вопросы в «Карту», задачи «Что делаем», карточки «Как это работает», требования к экранам — всё через CLI `backlog` по правилам ниже.
4. **Разметка** — метки этапа, вида и слоя, исполнитель-команда, критерии приемки, ссылки на документы. Линтер `bft-backlog-lint.py` даёт 0.
5. **Сборка** — `bft-backlog-build.py <проект>` собирает IDEF0 карточек из «Параметров», страницу `<epic>-map.html` и архив `<epic>-blueprint.zip`. Распакованный архив — тот же проект со скриптами и правилами в `.blueprint/`: агент продолжает работу там.

Файлы задач и документов руками не правь. Метаданные, связи и история меняются командами `backlog task create|edit`, `backlog doc create|update`. Нет CLI (`npm i -g backlog.md`) — пиши файлы ровно в том виде, в каком его пишет CLI: форма — в эталоне, линтер её сверяет (`BL005`).

## Что где лежит

| Слой карты | В Backlog.md | Признак |
|---|---|---|
| Шаги пути | этапы документа «История» и «Итог» | метка `stage:A` … `stage:стало` |
| Что видят | документ «История»; требования к экранам — документы `screens/` | заголовок «F3 · Название экрана» |
| Что делаем | задача | метка `stage:…`, без метки `layer:` и без родителя |
| Как это работает | подзадача задачи «Что делаем» | метки `stage:…` и `layer:…` |
| Команды и вопросы | документ «Карта» | таблицы «Команды» и «Вопросы» |

Задачи без метки `stage:` на карте не показываются. Это обычная работа проекта: план реализации, баги, спайки. Линтер считает их «вне карты».

## Документы «Карта» и «История»

«Карта» начинается скрытым паспортом — HTML-комментарием, в Backlog.md он не виден:

```md
<!-- bft-map
epic_slug: bartello-restart
source_doc: bartello-restart.md
source_stage: deep
source_rev: 000000000000
version: 1
revised: 2026-10-18
status: Черновик
-->
# Карта: Перезапуск акции Bartello

## Команды

| ID | Команда |
| --- | --- |
| gds | GDS |

## Вопросы

| ID | Кому | Вопрос | Где | Тип | Ответ |
| --- | --- | --- | --- | --- | --- |
| В25 | Bartello | Трёхсторонний контракт не согласован | BP-16 | блокер | — |
```

- **Команды** — ID латиницей-слагом; он же исполнитель задачи `@gds`.
- **Вопросы** — каждый `[УТОЧНИТЬ у {кого}]` по задаче или карточке. «Кому» — роль или команда, «Где» — ID задачи или карточки, тип — `вопрос` или `блокер`. Одинаковый блокер у двух задач пишется одним текстом.

«История» — согласованная история через экраны (`resources/story_line.md`). Её frontmatter переезжает в комментарий `<!-- bft-story … -->`, тело — как в `<epic>-story.md`. Этапы и экраны истории на карте не меняются.

## Задача «Что делаем»

Одна задача — один результат одной команды на этапе пути. Это бэклог: без этих задач требования БФТ не реализовать. Задача — постановка для техлида: что есть, чего не хватает, что должно стать и как это проверить. Как делать, она не расписывает.

```bash
backlog task create "Проверка билета: одна покупка — одна скидка" \
  -a @gds -l "stage:F,создать" --no-dod-defaults \
  -d $'Одна покупка — одна скидка. Без проверки скидку не выдать ни разу\n\nТребования БФТ: ПТ-1, ФТ-1, ФТ-15\n\n### ASIS\nМеханика скидки привязана к брони, проверки билета нет.\n\n### GAP\nБез проверки одна покупка может дать несколько скидок или ни одной.\n\n### TOBE\nПроверка по штрихкоду: билет активен, не использован, мероприятие было не больше 7 дней назад.\n\n### HowToDemo\n1. Сканирую действующий билет — проверка пройдена\n2. Сканирую тот же билет снова — отказ «использован»' \
  --ac "Проверка: активен, не использован, не больше 7 дней" \
  --ac "Отказ — с понятной причиной" \
  --doc doc-12
```

| Поле | Что писать |
|---|---|
| название | результат до 80 знаков: «Проверка билета: одна покупка — одна скидка», а не «GDS валидирует». Без API, протоколов, таблиц (`BL018`) |
| исполнитель | команда `@gds`. Неизвестна — без исполнителя (`-a ""`) и метки `кандидат:vit`, `кандидат:gds` из «Зависимостей»: выбор за PO |
| метки | этап `stage:F` (подготовка — первый этап истории, видно только по итогам — `stage:стало`) и вид: `создать`, `доработать` (опора — ASIS), `используем`, `уточнить` |
| описание | первая строка — зачем: вклад в цель, что сломается без задачи. Затем строка `Требования БФТ: …` и разделы `### ASIS`, `### GAP`, `### TOBE`, `### HowToDemo`, по желанию `### Дополнительно` |
| критерии приемки | чеклист приемки: короткие проверяемые пункты `--ac`, из критериев процессов и НФТ |
| documentation | документы требований к экранам задачи (`doc-12`) |
| references, notes | исполнение: ссылки на JIRA и Confluence (`--ref`), заметка исполнителя (`--notes`) |

- **ASIS** — как устроено сейчас, одна-две фразы из «Изменения в UJM» и ASIS БФТ.
- **GAP** — чем текущее не соответствует требованиям: что ломается для человека или бизнеса.
- **TOBE** — какой станет система после доработки, из ФТ, ИТ, НФТ задачи.
- **HowToDemo** — E2E-сценарий проверки от лица пользователя, нумерованный, хотя бы два шага.

Каждое ФТ, ИТ и НФТ БФТ должно оказаться в задаче или карточке (`BL017`). Неизвестное — `[УТОЧНИТЬ у {кого}]` и строка в «Вопросах».

## Карточка «Как это работает»

Карточка — техническая задача со слоем системной аналитики: подзадача той задачи «Что делаем», без которой её результат не получить. Это то, что происходит, а не работа команды: «Официант сканирует билет — приложение сразу отвечает». У каждой задачи — хотя бы одна карточка (`BL021`).

| Слой `layer:` | Что сюда | Пример |
|---|---|---|
| `employee` — Employee Actions | сотрудник на виду у гостя: официант, оператор, курьер. Нет такого сотрудника — ряд пустой, это тоже ответ | «Официант даёт скидку и фотографирует чек» |
| `technology` — Technology | интерфейсы, которые видит гость: страница, письмо, уведомление | «Письмо с билетом приходит с одним офером» |
| `backstage` — Backstage | за линией видимости, в нашей зоне: каталог, проверка, триггер, компенсация | «Проверка билета: активен, не использован, ≤7 дней» |
| `support` — Support | общие ресурсы и внешние каналы, без которых процессы не работают | «Email и SMS; push — если канал есть» |

Ряд — слой Service Blueprint, не система и не команда. Команда видна по цвету и фильтру.

```bash
backlog task create "Проверка билета: активен, не использован, ≤7 дней" \
  -p BP-16 -a "" -l "stage:F,layer:backstage" --no-dod-defaults \
  -d $'GDS проверяет штрихкод: билет активен, не использован, мероприятие было не больше 7 дней назад.\n\n### Параметры\n- **Вход:** Штрихкод на проверку (BP-15.1); Статус билета и дата мероприятия\n- **Управление:** Активен, не использован, не больше 7 дней (ФТ-1); Возврат, отмена, перенос (ФТ-15)\n- **Выход:** Валиден или отказ (BP-15.1); Билет «использован» (BP-18.1)\n- **Механизм:** GDS; Сервис проверки билетов\n\n### HowToDemo\n1. Сканирую действующий билет — «валиден», билет помечен «использован»\n2. Сканирую тот же билет снова — отказ «использован»'
```

Описание карточки — короткая заметка по разделам:

- **суть** — первая строка: что происходит, одной-двумя фразами;
- **`### Параметры`** — функция IDEF0, по строке на сторону, значения через `;`:
  - вход — что функция получает;
  - управление — правила и ограничения с ID требований;
  - выход — что отдаёт, хотя бы одно значение (`BL009`);
  - механизм — кто и чем исполняет;
- **`### IDEF0`** — схема mermaid. Её не пишешь: сборка собирает блок из «Параметров» и переписывает, если параметры поменялись (`BL022`). Тот же блок Backlog.md рисует в `backlog browser`;
- **`### HowToDemo`** — как показать работу карточки, нумерованно, хотя бы два шага;
- **ссылки** — `--doc` на документы экранов, `--ref` на страницы и другие карточки. На странице это раздел «Ссылки» вместе с задачей-родителем.

Ссылка `(BP-15.1)` во входе или управлении говорит, откуда пришло; в выходе — куда уходит. Из этих ссылок страница рисует стрелки между карточками. Карточка без единой связи — `BL028`.

Исполнитель карточки по умолчанию — команда задачи-родителя (`-a ""`). Другая команда — `-a @mrs`.

## Требования к экранам

Документ на экран истории в `backlog/docs/screens/`, заголовок «F3 · Название экрана»:

```bash
backlog doc create "F3 · Сканер — результат проверки" -t specification -p screens
backlog doc update doc-12 --content "$(cat F3.md)"
```

Тело — вкладки Product, Design, Functions и стек заметок, формат и проверки — `resources/screen_notes.md`.

## На странице

Три слоя — по экрану на всю высоту, переключатель рядом с меню открывает тот же этап. Строка этапов закреплена сверху.

- **Что видят** — раскадровка истории; клик по кадру — требования к экрану.
- **Что делаем** — задачи по этапам с цветом команды; клик открывает постановку. Вкладка «Требования» — зачем, ASIS, GAP, TOBE, HowToDemo, чеклист приемки, дополнительно. Вкладка «Исполнение» — JIRA, Confluence и заметка. Правки хранятся в браузере. «Скопировать команду для бэклога» отдаёт `backlog task edit BP-16 --ref … --notes …`.
- **Как это работает** — четыре ряда: Employee Actions, Technology, Backstage, Support; стрелки — из ссылок в «Параметрах». Клик открывает карточку: суть, параметры, IDEF0, HowToDemo, вопросы, ссылки.

Правой кнопкой мыши по любой секции — замечание. Выделенный текст попадает цитатой. Меню «Замечания» собирает промпт для ИИ-агента: что править, в каком файле проекта, какие команды прогнать после. Пересобранная карта закрывает учтённые замечания.

## Проверка

`bft-backlog-lint.py <проект> [--source БФТ.md]` — коды выхода 0, 1, 2. Сборка с ошибками ничего не пишет.

| Код | Уровень | Что не так |
|---|---|---|
| BL001 | ошибка | не проект Backlog.md |
| BL002 | ошибка | «Карта»: нет паспорта `<!-- bft-map -->`, ключа или заголовка |
| BL003 | ошибка | «История»: нет или с ошибками (коды `ST`) |
| BL004 | ошибка | «Команды», «Вопросы»: таблица, ID |
| BL005 | ошибка | файл не читается как задача или документ Backlog.md, повтор ID |
| BL006 | ошибка | задача: этап, вид, команда, лишний родитель |
| BL007 | ошибка | постановка: зачем, разделы, HowToDemo, критерии приемки |
| BL008 | ошибка | карточка: родитель, слой, этап, команда |
| BL009 | ошибка | карточка: разделы, строки «Параметров», выход, ссылки на карточки |
| BL010 | ошибка | вопрос: ID, «Где», тип |
| BL011 | ошибка | `documentation` ссылается на несуществующий документ |
| BL014 | ошибка | задача длиннее 80 знаков, карточка длиннее 90 |
| BL015 | ошибка / предупреждение | БФТ не найден: из `--source` — ошибка, без него — сверка пропущена |
| BL016 | ошибка | требования нет в БФТ |
| BL017 | ошибка | ФТ, ИТ, НФТ не попало на карту |
| BL018 | ошибка | технический язык в названии или сути |
| BL020 | предупреждение | этап истории без задач |
| BL021 | предупреждение | задача без карточки |
| BL022 | предупреждение | IDEF0 не совпадает с «Параметрами» — пересоберёт сборка |
| BL023 | предупреждение | у карточки нет управления или механизма |
| BL026 | предупреждение | БФТ изменился после сборки |
| BL027 | предупреждение | число без источника |
| BL028 | предупреждение | карточка без связей |

Требования к экранам — коды `SN` (`resources/screen_notes.md`).

## Перед показом PO

1. Колонки и «Что видят» совпадают с согласованной историей.
2. Каждая задача — один результат одной команды, без технических слов, с постановкой и критериями приемки.
3. У каждой задачи есть карточка «Как это работает», у каждой карточки — параметры, HowToDemo и хотя бы одна связь.
4. Каждое ФТ, ИТ, НФТ есть в задаче или карточке.
5. Ни одной команды, канала или числа без источника: неизвестное — в «Вопросах».
6. Открой страницу: карта читается за минуту, фильтр по команде подсвечивает её работу, карточка отвечает на «что входит, что выходит, как показать».
