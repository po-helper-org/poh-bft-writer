# environment_setup — сетап окружения перед deep (стадия 0а)

## Зачем

`/bft-fast` наружу не ходит по построению: он фиксирует сказанное PO и работает без
единого внешнего вызова. `/bft-deep` — **первая стадия всего пайплайна, которая
поднимает внешние источники**: трекер, вики, git, индекс воркспейса. Без них аудит
сверять не с чем, и прогон вырождается в пересказ seed с чужой уверенностью.

До этого этапа настройка подключений оставалась на PO и нигде не была описана: агент
молча обнаруживал, что `jira_get_issue` недоступен, и шёл дальше. Сетап делает этот
момент явным шагом — с проверкой, помощью в подключении и честной пометкой того, что
подключить не удалось.

## Что проверяется

| Источник | Зачем deep | Обязателен |
|---|---|---|
| Трекер (JIRA MCP) | эпик и связанные задачи, статусы, решения и отказы — якоря R2 | нет, но без него срез «противоречие» слепой |
| Вики (Confluence MCP) | существующие ТЗ и БФТ, страница эпика для публикации | нет, но без него `/bft-deliver` публиковать некуда |
| Индекс воркспейса `.bft/index/` | статичный фон: архитектура, домен-правила, глоссарий, стейкхолдеры | нет, строится `/bft-index` |
| git-история | когда и чем менялась затронутая область | нет |

Обязательных источников нет ни одного: прогон обязан пережить отсутствие каждого. Но
отсутствие обязано быть **зафиксировано**, а не пропущено молча.

## Порядок

### 1. Проверка живым вызовом, а не наличием инструмента

Инструмент может быть в списке, а VPN — нет; сервер может подняться, а прав на
пространство не быть. Поэтому проверка — дешёвый **read-only вызов на реальном
объекте** из конфига:

- трекер — `jira_get_issue` по ключу эпика из документа; ключа ещё нет → `jira_search`
  по первому проекту из `tracker_projects`;
- вики — `confluence_get_page` по `pageId` из frontmatter; `pageId: pending` →
  `confluence_search` по `wiki_space`;
- индекс — прочитать `<index_path>/MANIFEST.md`;
- git — `git log -1` в рабочем каталоге.

Три исхода на источник, четвёртого нет:

| Исход | Что значит | Что делаем |
|---|---|---|
| **доступен** | вызов вернул объект | источник в фактбазе, claims якорятся по `anchor_rules.md` |
| **не настроен** | инструмента нет в наборе агента | шаг 2 — помощь в подключении |
| **не отвечает** | инструмент есть, вызов упал (VPN, права, 401/403) | шаг 2, отдельной строкой: чинится не конфигом, а доступом |

### 2. Помощь в подключении

Агент показывает, **что** добавить и **куда**, и не делает этого за PO втихую:
конфиг MCP — файл пользователя, а не артефакт прогона.

- Claude Code — `.mcp.json` в корне воркспейса; Codex/Cline/DevX — свой файл того же
  назначения. Точное имя сервера и параметры берутся из документации того MCP, который
  выбрал PO: у корпоративных JIRA/Confluence обычно свой внутренний сервер, а не
  публичный.
- После правки конфига MCP-серверы поднимаются на **старте сессии агента** — новый
  сервер в текущей сессии не появится. Честная формулировка: «добавь и перезапусти
  сессию», а не «сейчас подхватится».
- Форма конфига проверяется машинно, до перезапуска:
  `python3 <skills_path>/bft-writer/scripts/bft-env-lint.py <путь к конфигу MCP>`.
  Он ловит то, что видно из файла: нет сервера трекера или вики, токен записан
  значением вместо ссылки на переменную окружения, файл с секретами не закрыт от git.

**Секреты.** Токен не спрашивается в чат, не печатается в отчёт и не коммитится.
В конфиге — ссылка на переменную окружения (`${JIRA_TOKEN}`), сама переменная живёт в
окружении PO. Файл конфига с секретами закрывается `.gitignore`. Нарушение любого из
трёх — находка `EN004`/`EN005` линтера, не замечание на словах.

### 3. STOP или пометка — по ветке прогона

**Интерактивный прогон.** Есть источник в состоянии «не настроен» или «не отвечает» →
вывести отчёт и **остановиться**. PO выбирает:

- настроить и перезапустить прогон — нормальный ход;
- продолжить без источника — тогда источник получает статус `UNAVAILABLE` в
  `MANIFEST.md`, и это решение записано, а не подразумевается.

**Фоновый прогон** (авто-форк из `/bft-fast`) не останавливается: помечает
недоступное `UNAVAILABLE`, идёт дальше, выносит список в нотификацию.

### 4. Что значит UNAVAILABLE дальше по прогону

Ровно то же, что и раньше (стадия 2, per-source fallback): claim, который мог бы
прийти из недоступного источника, идёт как `[УТОЧНИТЬ]`. **Пусто ≠ нет данных.**
Отсутствие ответа от трекера не превращается в «связанных задач нет» — это
непроверенное утверждение, и в документе ему место только под `[УТОЧНИТЬ]`.

Гейт грундинга (19) при этом не пропускается: `--source` просто не получает
недоступный файл, а находки по нему разбираются как обычные.

## Отчёт этапа

```
── СЕТАП ОКРУЖЕНИЯ <epic_slug> ──
трекер (JIRA)        <доступен: PROJ-101 прочитан | не настроен | не отвечает: 403>
вики (Confluence)    <доступен: pageId 12345 прочитан | не настроен | не отвечает>
индекс .bft/index/   <есть, MANIFEST от 2026-09-01 | нет → /bft-index>
git                  <доступен | нет репозитория>
конфиг MCP           <bft-env-lint: OK | EN002 нет сервера трекера, EN004 токен значением>

UNAVAILABLE: <перечень; claims оттуда пойдут как [УТОЧНИТЬ]>
```

Дальше — STOP (интерактивный прогон) либо строка в нотификацию (фоновый).

## Чего этап не делает

- Не правит конфиг MCP сам и не перезапускает сессию за PO.
- Не спрашивает и не хранит токены.
- Не блокирует прогон: недоступный источник — это `UNAVAILABLE`, а не остановка. Единственная
  остановка — STOP интерактивной ветки, и её снимает решение PO.
