# orchestration — Deep+Sync (seed → обогащение → синк)

## ruflo-контракт (координация, опционально)

> Внешняя координация, которой в репозитории нет и которая нигде здесь не настраивается. Контракт оставлен точкой расширения: если ruflo доступен в окружении — используется, иначе прогон идёт native-исполнением с файловым хендоффом через `artefacts/`. Деградация — норма, не сбой.
- `swarm_init(topology=hierarchical)` — один swarm на прогон; swarmId в память.
- `agent_spawn(agentType per роль, model — модель текущей сессии (точка расширения); дефолт-ориентир: opus для lead/verify, sonnet для worker; фактический per-step выбор — вне итерации)` — cost-tracking + memory на стадию.
- `memory_store/retrieve(namespace="bft-deep/<epic_slug>")` — shared fact-base + хендофф артефактов (актуально только если ruflo доступен).
- `coordination_consensus` — вердикт дебатов + грудинг-споры.
- **Degradation:** ошибка любого ruflo-tool → native-Task исполнение + файловый хендофф `artefacts/` + лог в error-callback. ruflo down ≠ прогон прерван.

## Стадии
0. init: `pin_commit` для этого прогона — документ уже несёт `pin_commit` во frontmatter (читает стадия 1) → использовать его; не задан → pin хэш текущего прогона репозитория `poh-bft-writer`. epic_slug — из frontmatter/пути читаемого документа; деградация без документа → date-slug из темы Summary (независим от JIRA key). Запуск `/bft-deep` — вручную либо фоновым авто-форком `bft-fast` (`../../bft-fast/resources/deep_fork.md`, форк по умолчанию включён, отключается `--no-deep`). Владелец обогащения по умолчанию — форк; правило приоритета путей и запрет на параллельный прогон — `../../bft-fast/resources/open_field.md` §«Приоритет путей».
0а. setup: **сетап окружения** — `environment_setup.md`. Deep первым в пайплайне ходит наружу, поэтому подключения проверяются до того, как на них опёрся аудит: живой read-only вызов по каждому источнику (трекер, вики, индекс, git), три исхода на источник — доступен / не настроен / не отвечает. Форму конфига MCP проверяет `python3 <skills_path>/bft-writer/scripts/bft-env-lint.py <конфиг>` (объявлены ли трекер и вики, не записан ли секрет значением). Интерактивный прогон при недоступном источнике выводит отчёт и **останавливается**: PO либо настраивает и перезапускает, либо отвечает «продолжай без него» — и тогда источник получает `UNAVAILABLE` в `MANIFEST.md` как записанное решение, а не умолчание. Фоновый прогон не останавливается: помечает `UNAVAILABLE` и выносит список в нотификацию. Обязательных источников нет ни одного — недоступность не блокирует прогон, но обязана быть зафиксирована.
1. seed: прочитать **документ БФТ стадии fast** — файл `<docs_path>/<epic_slug>/<epic_slug>-fast.md`, **только на чтение** (`../../bft-fast/resources/document_assembly.md` §«Путь файла»: deep в него не пишет ни при каких условиях, чтобы неудачный прогон не уничтожал выверенную шапку). Приоритет источника: локальный `<epic_slug>-fast.md`; его нет, но есть уже собранный `<epic_slug>.md` (доработка своего же прошлого прогона) → он; ни того, ни другого локально, есть страница → `confluence_get_page` по `pageId`; нет ни того, ни другого → деградация: собрать шапку по `../../bft-fast/resources/document_assembly.md` из Summary/письма, затем продолжить. Найти границу шапки по порядку якорей (`document_assembly.md` §Порядок якорей). Зафиксировать замороженную область (от `## Шапка (сутевое описание запроса)` до границы включительно) — она не меняется до конца прогона. Vague вход → шире `[УТОЧНИТЬ]`.
   **Проверка режима прогона — отдельным шагом, независимо от порядка якорей** (список якорей останавливается на первом совпадении, поэтому в корректном документе якорь 3 «Проблема которую решаем» не срабатывает и режим по нему не определяется): `stage: deep` во frontmatter **или** раздел «Проблема которую решаем» ниже строки-границы (искать обе формы разметки — ATX и Setext) → канон уже собран, прогон — **доработка**: закрыть `[УТОЧНИТЬ]` и уточнить отдельные разделы, канон не пересобирать. Ни того, ни другого нет → **первичная сборка**. Режим фиксируется здесь и задаёт ветку стадии 11.

### DEEP (обогащение seed)
2. context: `/bft-index` (само-генерируемый индекс воркспейса `.bft/index/`; если устарел или неполон по теме — перезапустить `/bft-index` перед этой стадией) + JIRA/Confluence + git-история и прошлые артефакты эпика в `<docs_path>/` (опц., если доступны). **Карта контекста `<docs_path>/<epic_slug>/context_map.md`** (её мог оставить фоновый `/bft-recon`, `../../bft-fast/resources/recon_fork.md`) читается первой — как **указатель, куда смотреть**, не как фактбаза: каждый её пункт открывается по ссылке и якорится самостоятельно по `../../bft-writer/resources/anchor_rules.md`. Факт, попавший в канон со ссылкой на карту и без собственного якоря, — дефект: карта гейтами документа не проверялась. Карты нет — стадия идёт как раньше. **Это первая стадия всего пайплайна, где вообще поднимаются внешние источники:** `/bft-fast` их не читает по построению, поэтому seed несёт только слова PO, и сверять его есть с чем именно здесь. Per-source fallback: источник со статусом `UNAVAILABLE` в `MANIFEST.md` → claim оттуда → `[УТОЧНИТЬ]`, никогда «пусто=нет данных». Memory-audit гейтит фактбазу.
2а. audit: сверить seed с поднятым контекстом по шести срезам (пробел / противоречие / edge-кейс / граница / термин / риск) и собрать список уточняющих вопросов к PO — `audit.md`. **Вопросы уходят в диалог, не в документ** (ЗМ-020, гейт 7): записать вопрос строкой в документ — 🔴, разделов-накопителей нет. **Интерактивный прогон:** вывести вопросы и остановиться (STOP-пауза аудита; вторая пауза прогона — сухой прогон публикации на стадии 11), полученные ответы внести в блокируемые ячейки канона с якорем R3, продолжить. **Фоновый прогон:** блокируемые ячейки помечаются `[УТОЧНИТЬ]`, прогон идёт дальше, список вопросов уходит в нотификацию — PO отвечает и перезапускает прогон в режиме доработки. Вопрос, ответ на который нашёлся в поднятом контексте, вопросом не выносится: он закрывается фактом с якорем по `anchor_rules.md` (трекер/wiki/ADR — R2, сказанное PO на встрече — R3).
3. value: ось 1 (enrichment.md §Ценность) — inline, без внешней команды.
4. what-if: ось 2 (enrichment.md §What-if).
5. bounds: ось 3 (enrichment.md §Границы).

### SYNC (укладка в канон)
6. draft: `/bft-draft` — **только генератор канона**, не автор документа. Вход: обогащённый seed. Выход: текст канон-области MTS (от «Проблема которую решаем» до «Якоря истины», 11 разделов) — **без frontmatter и без H1**, возвращается в прогон как текст.
   **Запрет (буквально):** на этой стадии `/bft-draft` ничего не сохраняет в `<docs_path>/<epic_slug>/<epic_slug>.md`, тем более в `<epic_slug>-fast.md`, и вообще не пишет в файл документа. Своим сохранением он положит собственный документ поверх единого и уничтожит шапку. Инструкция `/bft-draft` §«Этап 8: Сборка + STOP» о сохранении в корень папки эпика здесь не выполняется. Сборка документа и единственная запись файла — стадия 11.
7. verify: grounding_verifier.md §типизация.
8. validate: `/bft-validate` — hard-gates + Светофор **по канону ниже строки-границы**; проверяемая область этим и ограничена. Шапка и блок открытого поля передаются валидатору как read-only контекст (нужны для сверки ID, scope и якорей) и из жёстких гейтов исключены: `### Ограничения и договоренности` в шапке, `✅`/`⚡` в строке-статусе под H1 и `▶`/`⏳` в открытом поле — санкционированные элементы единого документа, а не нарушения. 🔴, поднятый на шапку или строку-статус, — ложное срабатывание: правку туда не вносить, в отчёте пометить как исключение. Карв-аут в гейтах — `../../bft-writer/resources/hard_gates.md` и `../../bft-writer/resources/writing_style.md`. Правки по 🔴 вносятся в текст канона внутри прогона; файл документа на этой стадии не переписывается (единственная запись — стадия 11). Convergence-stop (grounding_verifier.md §convergence).
9. citation: grounding_verifier.md §forced-citation.
10. review: свежий агент, **канон ниже строки-границы** против канон-ориентира. Шапка, строка-статус и блок открытого поля идут read-only контекстом и под правку ревью не попадают; замечание на них — ложное срабатывание (тот же карв-аут, что на стадии 8).
11. emit: собрать документ = шапка (формулировки байт-в-байт) + канон MTS, **со снятой строкой-границей** `BFT-HEAD-END`: она служебный якорь стадии fast и в финальный документ не уходит (ЗМ-022; `bft-lint.py` даёт `BD003`, если осталась). Вместе с ней снимается блок шапки `### Критичные требования (скелет на цитатах)`: скелет развёрнут в типизированные разделы канона, ID сохранены (ЗМ-027; `bft-lint.py` даёт `HD003`, если блок остался на `stage: deep`). Эти два снятия — единственные изменения внутри замороженной области, всё остальное в шапке переносится дословно. Ветка по режиму, зафиксированному на стадии 1:
    - **первичная сборка** — канон встаёт вместо плейсхолдера `## ⏳ Полный БФТ — в проработке` (плейсхолдер снимается);
    - **доработка** — существующий канон ниже границы сохраняется как есть; правятся только ячейки с `[УТОЧНИТЬ]` и строки, где появился ответ. Новые ID дописываются **в конец** соответствующей типизированной таблицы; существующие ID не перенумеровываются, разделы не пересобираются, ответы PO и ручные правки ниже границы не затираются.

    **Блок продолжения обязателен в обеих ветках:** в конце документа — компактный «Продолжить / уточнить БФТ» со слим-промтом (контракт `../../bft-fast/resources/open_field.md` §«Судьба после deep»: `⏳`-плейсхолдер снят, поле остаётся точкой входа для следующего прогона). Форма блока — `../examples/golden_deep_document.md`. Без него документ выходит без пути восстановления.

    **Гейт грундинга перед записью (обязателен, ЗМ-024, гейт 19).** `python3 <skills_path>/bft-writer/scripts/bft-ground-lint.py <файл> --source <seed> --source <каждый файл поднятого контекста> --strict`. В `--source` идут все входы прогона: fast-документ, `personas.csv`/`requirements.csv`, названный в документе Summary и файлы индекса, попавшие в фактбазу. Источник со статусом `UNAVAILABLE` в `--source` не подставляется, и это не повод пропустить гейт: находка по недоступному источнику разбирается как обычная — либо факт заякорен и остаётся, либо это утечка. Находка **в шапке** (зона fast) шапку не правит: строка уходит в нотификацию и отчёт, чинит её повторный `/bft-fast`.

**Гейт шаблона перед записью (обязателен, ЗМ-017).** Собранный текст сохранить во временный файл и прогнать `python3 <skills_path>/bft-writer/scripts/bft-lint.py <файл>`. Ненулевой код выхода = документ не по шаблону: исправить и прогнать снова, в `<docs_path>` и в Confluence не писать. Проверяется весь документ, включая шапку: read-only-карваут стадий 8 и 10 касается формулировок, а не структуры — именно так теряются строка-границы и разделы канона. Линтер сообщил `ERROR` в шапке, относящийся к зоне fast (например `HD007` — нет SMART-таблицы под «Цель»; `HD008` — под ней осталось прозаическое пояснение) → шапку не переписывать, вынести строкой в нотификацию и отчёт: чинить её должен повторный `/bft-fast`, не deep.

    Обновить frontmatter (`stage: deep`, `version`+1, `synced`, `status`) и строку-статус под H1. Сохранить `<docs_path>/<epic_slug>/<epic_slug>.md` + `artefacts/` — это единственная запись документа за прогон. Файл `<epic_slug>-fast.md` при этом не трогается: он остаётся исходником стадии fast, с которого прогон можно повторить. Публикация: `pageId` из frontmatter реальный → сухой прогон превью → STOP → «ок» PO → `confluence_update_page` по этому `pageId`. Новую страницу deep не создаёт ни при каких условиях. `pageId: pending` → в Confluence не писать вовсе: сохранить локально и вывести подсказку `/bft-deliver <epic_slug>` — создание страницы и запись `pageId`/`source` обратно во frontmatter принадлежат ему (`/bft-deliver` Шаг 2, режим CREATE). MCP недоступен → `[УТОЧНИТЬ: MCP недоступен]`, локальный файл сохранён. Нотификация — успех/провал, никогда молча.
