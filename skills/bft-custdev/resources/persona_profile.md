# Результат интервью и возврат в БФТ (persona_profile.md)

Формализация результата — Шаг 4 методички «Awesome Problem Interview Script», но по своим
блокам: методичка описывает персону, а БФТ пишут под приёмку (`interview_outcomes.md`).

## Результат — те же шесть блоков

После встречи раздел «Что должны унести» заполняется ответами. Профиль персоны канона
(общая характеристика, контекстное поведение, ценности, боли) не используется: он описывает
человека, а БФТ пишут под приёмку. Шесть блоков `interview_outcomes.md` отвечают ровно на
то, чего документу не хватает.

| Блок | Куда идёт в БФТ |
|---|---|
| Для кого | `personas.csv`; `[роль не подтверждена]` снимается |
| Какую проблему решаем | блок `### Цель` шапки, строка R SMART-таблицы |
| Как принимается работа | `### How to demo` — это и есть приёмка |
| Как поймём, что решает | строка M SMART-таблицы; метрика получает значение |
| Кто вовлечён | `personas.csv`, владельцы открытых вопросов |
| Какое решение видит запрашивающий | не требование: гипотеза решения с критерием успеха, проверяется отдельно |

Блок остался `[пробел]` после встречи — так и записывается. Пустая приёмка честнее
выдуманной: по ней сразу видно, что БФТ писать рано.

## Гипотеза решения

Решение, названное запрашивающим, записывается его формулой и проверяется, а не
принимается:

```
Если <роль> дать <решение>, закроется <проблема>, проверим по <критерий>.
```

Критерия нет — это не гипотеза, а требование в маскировке. Такая строка уходит в открытые
вопросы ответа в чат, а не в документ.

## Чего результат не делает

Не заменяет разведку: то, что записано в Confluence, проверяется по ссылке, а не
пересказом респондента. Не становится требованием сам по себе — требование пишет
`/bft-fast` или `/bft-deep` из ответа, проходя свои гейты. Не публикуется: профиль живёт
рядом с документом эпика, наружу его выносит только `/bft-deliver` в составе БФТ.
