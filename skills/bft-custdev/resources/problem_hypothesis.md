# Шаг 1 — гипотеза проблемы (problem_hypothesis.md)

Источник: «How to create Awesome Problem Interview Script», Сергей Тихомиров, Product
Architecture Framework Library (productframework.ru). Методика опирается на Стива Бланка,
Синди Альварес, Роба Фицпатрика, Эрика Риса.

## Формула

```
Person + Problem + Cause + Motivation = Problem Hypothesis
```

| Блок | Что это | Как звучит |
|---|---|---|
| **Person** | профиль персоны или сегмента, у которого возникает проблема | «Бухгалтер на удалённой работе», «UX-специалист» |
| **Problem** | действие или поведение персоны, которое мешает ей достигать результата | «Концентрируется на фичах, которые дают меньше профита» |
| **Cause** | возможные причины проблемы; их может быть несколько | «Потому что не понимает, на чём сфокусироваться в первую очередь» |
| **Motivation** | цель персоны, желаемый результат, путь к которому затрудняет проблема | «…тем самым профит от UX размывается» |

Две производные формулы методички:

```
Описание проблемы  = Поведение + Метрика блокера
Описание мотивации = Желаемый результат + Метрика цели
```

## Метрика — опора качелей

**Метрика блокера и метрика цели — одна и та же метрика.** Это опора «качелей»: на одной
стороне текущее поведение персоны, которое метрику понижает, на другой цель, то есть
значение метрики, которого персона хочет достичь.

```
UX-специалист стремится приносить больше импакта, но получается меньше,
ведь концентрируется не на том.        Метрика: импакт / количество принесённого профита
```

Формулировка без измеримой метрики гипотезой не является: подтвердить или опровергнуть
её нечем. Метрика не названа в источнике — она **не выдумывается**, а становится первой
целью интервью (`[УТОЧНИТЬ — метрика не названа]`). Дописать метрику за PO значит нарушить
гейт 5 ровно так же, как дописать за него SLA.

## Контекст цели

Поведение становится проблемой только в контексте цели. Отсутствие руки само по себе не
проблема, это обстоятельство; проблемой оно становится, когда у человека есть задача
быстро печатать. Отсюда правило: **блок Problem без блока Motivation бессмыслен** — без
цели описанное поведение остаётся нейтральным фактом.

## Как гипотеза собирается из артефактов `/bft-fast`

Гипотеза не сочиняется, она **выводится** из того, что уже записано:

| Блок | Откуда берётся |
|---|---|
| Person | `personas.csv` — персона с наибольшим влиянием по теме эпика; роль не подтверждена → `[роль не подтверждена]` переносится как есть |
| Problem | колонка ASIS в `requirements.csv` и блок `### Цель` шапки `<epic_slug>-fast.md` (часть «почему») |
| Cause | «Ограничения и договорённости», операционные заметки блока «Границы», строки открытых вопросов про причины |
| Motivation | часть блока `### Цель` про желаемый результат, SMART-таблица цели |

## Гипотеза — предположение, но не выдумка

Гипотеза по определению не факт: её и зовут проверять на интервью. Поэтому правило
источника здесь мягче, чем в документе БФТ, но не отменяется. Колонка «Источник» у каждого
блока принимает одно из трёх:

| Форма источника | Когда | Пример |
|---|---|---|
| Цитата | блок прямо назван в тексте PO | `Summary: «вопросы должны попадать в поиск»` |
| `гипотеза ← <маркер> · <место>` | блок выведен из пробела, а не назван | `гипотеза ← [ASIS не озвучен] · requirements.csv` |
| `[УТОЧНИТЬ]` | блок не выводится даже из пробела | `[УТОЧНИТЬ]` |

Разница принципиальная. Цитата говорит «это сказали», вторая форма — «это моё
предположение, вот из какой дырки оно выросло», и на встрече его подтверждают или
опровергают. Формулировка без обеих отметок выдаёт догадку за сказанное: это дефект
(`CD002`), и он же ломает возврат ответов, потому что непонятно, что именно проверяли.

Пустая гипотеза — нормальный результат для сырого эпика: интервью тогда и нужно, чтобы её
собрать. Блок с `[УТОЧНИТЬ]` автоматически становится целью № 1 интервью.

## Одна гипотеза на скрипт

Скрипт проверяет **одну** ключевую гипотезу проблемы. Остальные предположения выносятся
в перечень дополнительных гипотез (`extra_hypotheses.md`, Шаг 3) и проверяются короткими
блоками вопросов, а не вторым полным скриптом.

## Границы жанра

Методичка прямо ограничивает область: скрипт предназначен **только для проблемного
интервью** и не решает задачи:

- общего изучения среды клиента, когда проблема ещё не известна (поиск проблемных точек рынка);
- изучения проблемных точек в существующем продукте или процессе, когда проблема ещё не известна;
- подтверждения того, насколько ваше решение закрывает проблему (валидация решения).

Для БФТ это означает вот что. Эпик часто приходит уже с решением: `/bft-fast` записал
«что делаем». Скрипт проверяет **проблему под этим решением**, а не само решение. Вопрос
«удобно ли будет пользоваться тем, что мы собираемся сделать» в скрипт не попадает — он
из жанра валидации решения. Такие вопросы уходят в раздел «Чего не спрашиваем» с
указанием причины.
