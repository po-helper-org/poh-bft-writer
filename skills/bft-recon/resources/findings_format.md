# Формат карты находок (findings_format.md)

## Файл

`<docs_path>/<epic_slug>/context_map.md` — единственный файл, который пишет навык. Существующая карта перезаписывается целиком: карта отражает один обход, а не копится.

## Скелет

````
---
epic_slug: <слаг>
scanned: <YYYY-MM-DD>
sources: <JIRA: PROJ1, PROJ2 | Confluence: SPACE | пропущено: …>
findings: <N>
---

# Карта контекста: <тема встречи>

Обход JIRA и Confluence по теме встречи. Ссылки — точки входа для проверки, не факты:
что в найденном документе написано, читает человек по ссылке.

## Находки

| Тип | Заголовок | Ссылка | Почему релевантно | Статус/дата |
|---|---|---|---|---|
| УЖЕ ОПИСАНО | … | [PROJ-123](URL) | … | В работе · 2026-07 |

## Что не найдено

* <термин/срез> — ничего по <источник>
* <срез> — пропущен: <причина>

## Связи с открытыми вопросами

* <вопрос из письма> → похоже, отвечает [PROJ-123](URL) — проверить
````

## Типы находок

| Тип | Когда ставится |
|---|---|
| `УЖЕ ОПИСАНО` | по теме есть готовый документ или требования |
| `ПЕРЕСЕЧЕНИЕ` | другой эпик трогает те же сущности |
| `ЗАВИСИМОСТЬ` | задача другой команды влияет на сроки или объём |
| `ПРОТИВОРЕЧИЕ` | прошлое решение расходится со сказанным на встрече |
| `ВЛАДЕЛЕЦ` | человек вёл эту тему раньше |
| `ТЕРМИН` | в компании то же самое называется иначе |

Другой тип не изобретается: находка, которая никуда не попала, — сигнал, что связь с темой неочевидна, и её надо отбросить.

## Дисциплина формулировок

Колонка «Почему релевантно» — одна строка **про документ**, не про предметную область:

| Так | Не так |
|---|---|
| эпик про тот же виджет, статус «в работе» | виджет отключается по фича-флагу |
| страница с решением по этой интеграции | интеграция работает через Kafka |
| задача закрыта с резолюцией «Won't do» | эту фичу делать не будут |

Правая колонка — пересказ чужого документа как факта: он выглядит как знание, но проверить его по одной строке нельзя, а в БФТ он уедет уже без ссылки. Модальность обязательна: «похоже», «относится к», «проверить».

## Гейт находки

Строка выводится, только если у неё есть **ключ задачи или URL**, полученный из ответа MCP. Нет якоря → строки нет. «Где-то это точно обсуждали» — не находка.

Проверяется машинно: `bft-recon-lint.py`, код `RC003` (гейт 20).

## Пустой результат

Раздел «Что не найдено» обязателен всегда, даже когда находок много: он отделяет «искал и не нашёл» от «не искал». Пропущенный срез идёт туда же с причиной (`../../bft-recon/resources/search_plan.md` §Деградация).

Карта без этого раздела не сохраняется — `RC005`.

## Нотификация

По завершении — одно сообщение в чат, три части:

1. **Топ-5 находок** — тип, заголовок, ссылка, одна строка «почему». Больше пяти в чат не выводится: остальное в карте.
2. **Вопросы с возможным ответом** — «на этот вопрос письма, похоже, уже есть ответ: <ссылка>, проверь». Только для вопросов, реально прозвучавших в письме.
3. **Предлагаемый блок «Документация»** — готовая копипаста markdown-ссылками.

Третья часть — **предложение, а не правка**. Письмо уже отдано PO и разведчиком не переписывается: в блоке «Документация» письма живут только источники, названные самим PO (`../../bft-fast/resources/letter_format.md`). Вставляет PO, если сочтёт нужным.

Провал — тоже нотификация, никогда молча: `разведка не выполнена: <причина>; письмо и документ не затронуты`.
