# Сводный отчёт за 3 спринта — что считаем и как

Шапка отчёта показывает `{среднее} / {медиана} / {кол-во}` по **Lead Time за последние 3 спринта** — это единственное, для чего нужен объект `METRICS`. Клик по числам открывает панель с тремя графиками; их данные лежат отдельно в `BURNDOWN`, `VELOCITY` и `CONTROL`.

## Определения (согласованы с PO, не менять молча)
| Метрика | Считается как |
|---|---|
| **Lead Time** | от `fields.created` задачи до перехода в статус категории «Выполнено» |
| **Cycle Time** | от первого перехода в статус категории «В работе» до перехода в «Выполнено» |
| **Запрос** | любая закрытая задача спринта — истории, задачи, баги И подзадачи |

Разница медиан Lead и Cycle — время ожидания в очереди до взятия в работу. Выводится отдельной строкой в «Метриках управления».

## Как собирать
1. Найди последние 3 спринта доски: `GET /rest/agile/1.0/board/{boardId}/sprint?state=closed,active&maxResults=50`. Фильтруй по `originBoardId == boardId` (в ответ попадают спринты чужих досок), сортируй по `startDate`, бери три последних.
2. По каждому спринту: `GET /rest/agile/1.0/sprint/{id}/issue?fields=key,summary,status,issuetype,created,assignee&expand=changelog&maxResults=200`.
3. Построй карту «id статуса → категория» из `GET /rest/api/2/status` — **по `id`, а не по имени**. В changelog имена статусов приходят на языке workflow (`Closed`, `In progress`, `Review`), а `/status` отдаёт русские названия; сопоставление по строкам даёт ноль совпадений. Поля `item.from` / `item.to` содержат числовые id — по ним и матчить.
4. Для каждой задачи пройди `changelog.histories[]` по возрастанию `created`:
   - первый переход в категорию «В работе» → начало Cycle Time;
   - переход в «Выполнено» → дата закрытия; если после него был переход в НЕ-«Выполнено» (задачу переоткрыли), дату сбросить и ждать следующего закрытия;
   - «закрыта» определяется по текущей категории статуса, а не по наличию перехода в истории.
5. Cycle Time не определён для задач, закрытых без перехода в работу (сразу из бэклога в закрыто) — такие просто не попадают в выборку Cycle, счётчик `count` у Lead и Cycle поэтому различается. Это нормально, не «терять» их и не подставлять нули.

## Структура METRICS
```js
{
  sprints: [{
    name: "2026Q3-S4",
    total: 104, closed: 75, open: 29, throughputPct: 72,
    lead:  { mean: 22.3, median: 14.0, count: 75 },
    cycle: { mean: 8.1,  median: 3.9,  count: 66 },
    leadStory: { ... },   // только issuetype История / История Enabler
    leadTask:  { ... },   // верхний уровень кроме историй (задачи, баги)
    points: [0.2, 1.4, …] // Lead Time каждой закрытой задачи, для диаграммы
  }],
  overall: { lead, cycle, leadStory, leadTask, total, closed }
}
```
Пустая выборка → `null` вместо объекта статистики, шаблон рисует «—». Нули не подставлять: «0 дней» и «нет данных» — разные утверждения.

## Секции панели
Только графики, без таблиц: сводные числа уже живут в шапке отчёта (Lead Time) и в подписях под графиками. Таблицы «Производительность команды», «Метрики управления» и разрезы Lead Time по историям и задачам были удалены как дублирующие — velocity-график показывает то же наглядно.

1. **Burndown текущего спринта** — остаток незакрытых задач по дням. Серая прямая — идеальный темп от объёма на старте до нуля, красная ломаная — фактический остаток, обрывается на сегодняшнем дне (будущие дни не рисуем — это не прогноз). Выходные затенены.
2. **Производительность: запланировано / сделано** — пара столбцов на спринт. Левый (плановый) разложен стопкой по текущим статусам `TODO → Заблокировано → В работе → Тестирование → Ревью → Готово`: видно, где именно осело незакрытое. Правый — сделано. Пунктир — среднее выполнение за показанные спринты.
3–4. **Диаграммы управления — истории и подзадачи** (две отдельные: у подзадач свой масштаб Cycle Time, в общей куче он теряется). X: дата закрытия, Y: Cycle Time задачи. Зелёные точки — задачи, красные — выбросы, синяя линия — скользящее среднее по окну из 5 задач, светлая полоса — коридор ±σ этого окна, красная горизонталь — порог выброса (`среднее + σ` за период). **Зона риска** — жёлтые точки у правого края: задачи, которые ещё НЕ закрыты, но уже в работе дольше медианы своей группы. По вертикали — сколько длятся на сегодня. Это единственные точки на графике, которые говорят о будущем, а не о прошлом: выбросы уже случились, а эти ещё можно спасти. Считается от первого перехода в категорию «В работе»; задачи, не начатые вовсе, в риск не попадают. Точки выше шкалы не рисуем, но их число пишем в легенде.

Под графиком — кликабельный список выбросов с текущим статусом каждой задачи, отсортированный по убыванию Cycle Time: ради него диаграмма и нужна. Статус в списке не всегда «Закрыт» — финальные статусы бывают разные (Отменён, Отклонён), и отменённая задача с огромным циклом читается иначе, чем доведённая до конца.

Отдельного внешнего графического движка нет и не нужно: SVG строится строкой, отчёт остаётся одним самодостаточным файлом.

## Burndown: честный объём
Объём спринта берётся не как «сколько задач в спринте сейчас», а пересчитывается по дням из changelog поля `Sprint` (`fromString`/`toString` содержат имена спринтов). Внесённые и вынесенные посреди спринта задачи видны ступеньками — иначе burndown врёт, показывая сегодняшний объём как стартовый.

## Velocity: почему задачи, а не story points
Эталонный график JIRA считает в story points, но на живых данных поле заполнено у 67–88% задач в зависимости от спринта. Столбец в SP молча потерял бы от 12 до 33 процентов работы. Весь остальной отчёт — счётчики, burndown, диаграмма управления — считает задачи, поэтому и velocity в задачах: одна единица измерения на весь отчёт. Если у команды дисциплина оценки близка к 100%, переключение на `customfield_10106` — замена одной строки в сборе данных, но проверь покрытие перед этим.

## Выбросы
Порог — `среднее + одна σ` по всем закрытым за период. На данных GDS это 25 дней при медиане 4,2: распределение с тяжёлым хвостом, поэтому среднее сильно выше медианы, и σ большая. Порог намеренно считается от среднего, а не от медианы — иначе в «выбросы» попадала бы треть потока и список перестал бы быть сигналом.

## Лента изменений (кнопка «Logs»)

Отдельная панель, не часть сводного отчёта: кто какую задачу куда перевёл за последнюю неделю. Открывается кнопкой в правом верхнем углу страницы.

**Три типа событий** (`kind`), все за последние 7 дней:

| kind | Что это | Источник |
|---|---|---|
| `status` | смена статуса | `changelog.histories[].items[]` с `field == "status"`, автор `history.author.displayName` |
| `comment` | оставлен комментарий | `fields.comment.comments[]` — автор, `created`, тело (обрезаем до 160 символов) |
| `created` | задача создана | `fields.created` + `fields.creator`, отдельной записи в changelog у создания нет |

Комментарии НЕ приходят вместе с `expand=changelog` — нужен отдельный проход с `fields=...,comment,creator` по тем же спринтам. Это второй пакетный запрос на спринт, не запрос на задачу.

Дедупликация — по типу события: `st:{history.id}:{key}`, `cm:{comment.id}`, `cr:{key}`. Одна задача может числиться в нескольких спринтах и попасть в выгрузку дважды. Автор отсутствует (правка сделана интеграцией) → «Система».

**Панель.** Два ряда чипов: сверху фильтр по типу события со счётчиками, ниже — по автору. Фильтры комбинируются. Дальше лента, сгруппированная по дням: «Сегодня», «Вчера», затем дата. В строке — инициалы автора, полное имя, относительное время, ссылка на задачу и тело события: для смены статуса `старый → новый` бейджами, для комментария — цитата в рамке, для создания — тип задачи.

Показываем и «пустые» переходы вида `Backlog → Backlog`: в JIRA это реальное событие workflow (смена статуса внутри той же колонки доски), и молча прятать его — врать о том, что человек ничего не делал.


## Несколько команд на одной странице
`TEAMS` — массив объектов, по одному на команду, каждый со своим набором `epics/metrics/burndown/control/velocity/logs`. Переключатель в шапке меняет активную команду и перерисовывает таблицу; панели закрываются, чтобы не показывать данные предыдущей команды.

`REPORT_ID` равен slug команды — это разводит localStorage-заметки: заметка по эпику GDS не всплывёт у LIVE, даже если rowId совпал.
