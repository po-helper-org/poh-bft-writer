# Сбор данных из JIRA — алгоритм запросов

## Инструменты
Предпочтительно — Atlassian MCP-сервер сессии (например `mcp__MCP_DOCKER__jira_*` в Docker MCP Toolkit, или любой другой подключённый Atlassian MCP). Если MCP недоступен/не авторизован, а у пользователя есть личный токен и рабочий VPN — fallback на прямой REST через `curl` с `Authorization: Bearer $JIRA_PERSONAL_TOKEN` (спроси токен/переменную у пользователя, не жёстко зашивай значение).

Не блокируй весь навык на одном недоступном инструменте: если MCP только что переподключался — подожди/повтори поиск инструмента один раз, а не спамь ошибками.

## 1. Доска и спринт
- Поиск доски по проекту/имени команды: `jira_get_agile_boards` (`project_key` или `board_name` fuzzy). Если несколько досок — покажи список пользователю, пусть выберет.
- Активный спринт доски: GET `/rest/agile/1.0/board/{boardId}/sprint?state=active` (через MCP-обёртку или REST). Если активных спринтов на разных досках одной команды несколько — уточни, какой смотреть.
- Держи `sprintId`, `boardId`, `boardName`, `sprintName` — они уходят в поля объекта команды и рисуют шапку.

## 2. Issues спринта
- GET `/rest/agile/1.0/sprint/{sprintId}/issue?fields=key,summary,status,issuetype&maxResults=100` (пагинируй, если `total` > `maxResults`).
- Фильтруй по issuetype, согласованному на стадии 0 (дефолт — только «История»/Story; не тяни подзадачи, баги, эпики, задачи в основной список, если явно не попросили).

## 3. Эпик каждой Истории → группировка
Единица отчёта — эпик (PO трекает прогресс на уровне эпика, не истории), поэтому финальная структура данных — не плоский список историй, а список эпиков с вложенными историями (см. `resources/data_shape.md`). Собери сырые данные по историям, потом сгруппируй.

- Узнай точный customfield эпик-линка один раз за диалог: `GET /rest/api/2/field`, найди поле с именем вида «Ссылка на эпик» / «Epic Link» (НЕ «Эпики ЦК/ЦП» и не «Цвет эпика» — это другие поля). ID различается между инстансами JIRA, не угадывай/не переиспользуй ID из прошлых запусков без проверки.
- Для каждой Истории: `GET /rest/api/2/issue/{key}?fields={epicLinkFieldId}` → это ключ эпика (или пусто).
- Для полученных ключей эпиков — по одному `GET /rest/api/2/issue/{epicKey}?fields=summary` (кэшируй, чтобы не дублировать запрос, если несколько Историй ссылаются на один эпик).
- Сгруппируй истории по `epicKey` в объекты `EPICS[i].stories[]`. Истории без эпика (`epicKey` пусто) собери в один псевдо-эпик `rowId: "no-epic"`, `epicKey: null`, `epicTitle: "Без эпика"` — не выбрасывай их из отчёта.
- Группировка строго визуальная: не считай агрегированный статус/процент выполнения эпика, только собери истории под одним заголовком.

## 3b. Дата последней смены статуса (для «возраста» статуса)
Нужна каждой Истории и каждой Подзадаче — по ней страница показывает «1д / 22д» и красит красным всё, что стоит дольше 3 дней.

- Отдельного поля с датой смены статуса на инстансе нет (`statusCategoryChangedDate` отсутствует). Источник — changelog.
- Тянуть пакетно, одним запросом на весь спринт: `GET /rest/agile/1.0/sprint/{sprintId}/issue?fields=key,status,updated,created&expand=changelog&maxResults=100`. Список спринта включает и подзадачи, так что 47 задач закрываются одним вызовом, а не 47 отдельными.
- Для каждой задачи: пройти `changelog.histories[].items[]`, взять максимальный `histories[].created` среди записей с `field == "status"`.
- Никогда не менявшийся статус (в changelog нет записей `status`) → взять `fields.created` задачи. `fields.updated` НЕ подходит: он двигается от любой правки — комментария, вложения, смены исполнителя — и завысит свежесть.
- Класть в данные ISO-строку как есть (`statusChanged`), не считать дни заранее: число дней вычисляет браузер при рендере, иначе отчёт «протухает» уже на следующий день после генерации.

## 3c. Исполнитель
Берётся из того же пакетного ответа (`fields.assignee.displayName`) — отдельные запросы не нужны. В данные кладётся полное ФИО; инициалы для показа считает шаблон. Не назначен → `null`.

## 3d. Данные для графиков сводного отчёта
Всё это `scripts/collect.py` делает сам — раздел нужен, если собираешь руками или чинишь сборщик.

Три набора собираются отдельно от основной таблицы (`resources/metrics.md` — что означает каждое число):

- **Burndown** (поле `burndown`) — по дням текущего спринта. Объём на каждый день пересчитывается из changelog поля `Sprint`: `fromString`/`toString` содержат имена спринтов, по ним видно, когда задача вошла в спринт и когда её вынесли. Дни позже сегодняшнего помечаются `future: true` — фактическую линию по ним не рисуем.
- **Control** (поле `control`) — две независимые выборки, `control.stories` и `control.subtasks`: закрытые за 30 дней с Cycle Time, датой закрытия и флагом выброса (`cycle > среднее + σ`), плюс `risks[]` — незакрытые задачи, идущие дольше медианы своей группы. Задачи дедуплицируются по ключу: одна и та же может числиться в нескольких спринтах.
- **Velocity** (поле `velocity`) — по каждому спринту: сколько запланировано, сколько сделано и разбивка планового объёма по текущим статусным бакетам.
- **Logs** (поле `logs`) — активность за последние 7 дней трёх видов: смены статусов (changelog), комментарии и создание задач. Комментарии и создатель требуют второго пакетного прохода по спринтам с `fields=key,summary,issuetype,created,creator,comment` — в ответе с `expand=changelog` их нет. Дедуп по типу: `st:{history.id}:{key}`, `cm:{comment.id}`, `cr:{key}`.

## 4. Подзадачи
- Через MCP `jira_get_issue(issue_key, fields="subtasks,summary,status")` — поле `subtasks` уже приходит вложенным списком (`key`, `fields.summary`, `fields.status.name`, `fields.status.statusCategory.name`), отдельного запроса на каждую подзадачу не нужно.
- Если MCP недоступен и идёшь через REST — `GET /rest/api/2/issue/{key}?fields=subtasks` даёт тот же вложенный список.
- Пустой список подзадач — нормальный случай, не ошибка.

## Ловушки
- `jira_get_all_projects`/`jira_search` иногда возвращают пусто или «anonymous»-ошибку, даже если токен рабочий — проверь напрямую `GET /rest/api/2/myself` тем же токеном; если он валиден, но MCP-обёртка не видит проект — используй agile-board-эндпоинты (`board/{id}/sprint/{id}/issue`) напрямую, они реже ломаются на фильтрах по проекту.
- Без VPN/при разрыве MCP-сервера — `jira.mts.ru`(или другой корпоративный хост) резолвится в публичный адрес, все запросы висят/таймаутят. Проверь `curl -sk -m 10 .../rest/api/2/myself` перед тем, как тратить время на цикл запросов по issues.
- Статус-категория (`statusCategory.name`) — основа для цвета бейджа в HTML (`Выполнено`→done, `В работе`→progress, остальное→backlog), а не сам `status.name` (тех же категорий много разных статусов с разными названиями по проектам).
