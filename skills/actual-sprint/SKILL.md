# Навык: Actual Sprint — HTML-отчёт по факту спринта

## Роль
Ты — репортёр по факту спринта. Не выдумываешь статусы и не берёшь данные "из головы" — только то, что реально вернул JIRA. PO трекает прогресс на уровне **эпика**, не истории — поэтому единица отчёта = эпик; история — деталь внутри эпика, подзадача — деталь внутри истории.

## Принцип нулевого допуска к галлюцинациям
Название эпика, история, подзадача, их статусы — каждое поле имеет источник: конкретный JIRA issue, полученный инструментом в этом диалоге. Нет данных → не выдумывай. История без эпика — не выбрасывай, собери в псевдо-эпик «Без эпика», а не в «—» без объяснения.

## Стадии

### 0. Уточнить команды (STOP, диалог)
Спроси одним вопросом: какая команда (или несколько) интересует, и если известно — какой спринт (по умолчанию активный). Не угадывай доску/проект в JIRA — если у пользователя несколько досок с похожим названием, покажи список и дай выбрать (`AskUserQuestion`/список вариантов).
Заодно уточни (если не очевидно из истории диалога):
- какие типы issue считать «Историями» внутри эпика (по умолчанию — только issuetype = Story/История, см. `resources/data_collection.md`);
- дефолт по формату отчёта (закреплён по итогам предыдущих запусков навыка, не переспрашивай, если не просят иначе): строка = эпик, одна кнопка «Статус» на строку — открывает ДВА раздельных сайдбара одновременно (заметка о прогрессе + список историй эпика), без агрегированного % по эпику (см. дизайн-контракт ниже).

### 1. Зайти в JIRA
Используй доступный Atlassian MCP (или прямой REST, если MCP недоступен/не авторизован — см. `resources/data_collection.md` про fallback через `curl` при рабочем VPN/токене). Порядок:
1. Найди agile-доску(и) команды: поиск по имени команды/проекту.
2. Определи активный спринт этой доски (`state=active`); если активных несколько на разных досках одной команды — уточни у пользователя, какой имел в виду.
3. Держи цепочку источников: доска → спринт → issues спринта. Не подставляй ID руками, только то, что вернул JIRA.

### 2. Собрать данные по спринту и сгруппировать по эпику
Для выбранного спринта:
1. Вытяни список issues спринта, отфильтруй по нужному issuetype (шаг 0) — это Истории.
2. Для каждой Истории получи: `key`, `summary`, `status` (name + statusCategory), эпик (`Ссылка на эпик` / epic link поле — прочитай точный customfield ID через поиск полей, не угадывай номер) и его `summary`.
3. Если у Истории есть подзадачи — вытяни их `key`, `summary`, `status` (name + statusCategory).
3b. Для каждой Истории и Подзадачи возьми дату последней смены статуса из changelog — одним пакетным запросом на весь спринт (`data_collection.md`, шаг 3b). Кладётся в поле `statusChanged` как ISO-строка.
3c. Там же возьми исполнителя (`fields.assignee.displayName`) — поле `assignee`, полное ФИО как вернул JIRA; инициалы шаблон считает сам. Не назначен → `null`.
3d. Собери данные для трёх графиков сводного отчёта и ленты изменений — burndown, control, velocity, logs (`data_collection.md`, шаг 3d).
3e. Посчитай сводные метрики за последние 3 спринта команды — Lead Time, Cycle Time, производительность, разрезы по историям и задачам (`resources/metrics.md`). Результат кладётся в `{{METRICS_JSON}}`.
4. Сгруппируй Истории по эпику: один элемент данных на эпик, с вложенным списком его Историй. Истории без эпика — в один псевдо-эпик «Без эпика». Данные по эпикам (summary) кэшируй в рамках диалога — не дёргай JIRA повторно за тем же эпиком.
5. Полный алгоритм запросов, правила группировки и обработка «без эпика» — `resources/data_collection.md`. Форма итоговых данных — `resources/data_shape.md`. Бакеты статусов НЕ считай сам и не клади в данные — шаблон считает их в браузере по `status` + `category` (`resources/status_mapping.md`).

### 3. Сформировать HTML-страницу
Возьми шаблон `resources/report_template.html` (самодостаточный, фиксированный ч/б дизайн со цветовой кодировкой статусов). Заполни:
- `{{TEAM_NAME}}`, `{{SPRINT_NAME}}`, `{{BOARD_NAME}}`, `{{BOARD_URL}}` в hero-блоке. `{{BOARD_URL}}` — прямая ссылка на agile-доску вида `{JIRA_BASE}/secure/RapidBoard.jspa?rapidView={boardId}&projectKey={KEY}`, `boardId` берётся из ответа поиска доски на стадии 1, не выдумывается;
- `{{METRICS_JSON}}`, `{{BURNDOWN_JSON}}`, `{{CONTROL_JSON}}`, `{{VELOCITY_JSON}}`, `{{LOGS_JSON}}` — данные сводного отчёта, трёх графиков и ленты изменений (`resources/metrics.md`);
- JS-массив `EPICS` — по одному объекту на эпик (см. структуру в шаблоне и `resources/data_shape.md`): `epicKey`/`epicTitle` (`epicKey: null` → псевдо-эпик «Без эпика»), `rowId`, `stories[]` (`key`, `title`, `status`, `category`, `subtasks[]` с той же формой).

Сохрани готовый файл как `{team-slug}-sprint-report.html` рядом с рабочей директорией пользователя (не внутри этого репозитория навыка). Не публикуй как Artifact, если пользователь явно не попросил — это локальный рабочий файл, как в `bft-html`.

STOP: покажи путь к файлу и краткую сводку (сколько эпиков, сколько историй в «Без эпика», спринт/доска).

## Дизайн-контракт HTML (не менять произвольно)
- Ч/б интерфейс, цвет несёт смысл только в статусах. Hero сверху с полосой-разделителем; название доски в hero — ссылка на саму доску в JIRA.
- В hero вместо счётчика эпиков — **Lead Time за 3 спринта в формате `среднее / медиана / кол-во`**. Это кликабельный элемент: открывает панель со сводным отчётом команды за 3 спринта — три графика без таблиц: burndown текущего спринта, производительность «запланировано / сделано» с разбивкой планового столбца по статусам, диаграмма управления со списком задач-выбросов (см. `resources/metrics.md`). Сводные числа не дублировать таблицами: Lead Time уже в шапке, остальное читается из подписей под графиками. Подписи колонок панели переключаются на «Заметка» / «Метрики», заметка сводного отчёта хранится под отдельным ключом `__metrics__`.
- Таблица: одна строка = один эпик, **без шапки-заголовка** (названия колонок не несут информации — эпик и так виден, счётчики расшифровываются подсказкой). Колонки: «Эпик» (простой текст, БЕЗ ссылки — иначе клик по строке конфликтует с переходом; ссылка на JIRA живёт в шапке панели) | счётчики статусов | кнопка действия.
- **Кликабельна вся строка**, не только кнопка «Статус»: обработчик вешается на `<tr>`, курсор `pointer`, подсветка строки по hover. Кнопка остаётся как явная точка входа и как носитель маркера заметки.
- **Счётчики статусов** — миниатюрный цветной текст `2/2/3/0/5/1` в порядке `Открыто / Заблокировано / В работе / Тестирование / Ревью / Готово`. Агрегируется ВСЯ иерархия эпика: каждая История + каждая её Подзадача = единица подсчёта. Ни легенды, ни подписей колонок — расшифровка во всплывающей подсказке при наведении, только ненулевые бакеты словами. Цвета бакетов и маппинг статусов — `resources/status_mapping.md`; реализация — `classifyBucket` в шаблоне (считается в браузере при рендере, в данных бакеты не хранятся).
- Проценты/сводный статус эпика не выводить — только счётчики и группировка.
- Кнопка **«Статус»** (одна на эпик) → выезжает ОДНА неделимая панель справа: общая рамка, общая тень, **одна** кнопка закрытия. Общая шапка (ключ эпика, название, ссылка «Открыть в JIRA →») — не дублировать её по колонкам. Внутри шапки — две колонки, разделённые тонкой линией **без тени между ними**:
  1. **Колонка «Прогресс»** (слева, фиксированная ширина) — обычный `<textarea>`, plain-текст, автосохранение в `localStorage` по ключу `actual-sprint:{REPORT_ID}:note:{rowId}` эпика (`REPORT_ID` — уникальный на файл отчёта, чтобы несколько открытых отчётов не путали заметки в одном браузере). Кнопка «Статус» получает класс `has-note` (визуальная точка-маркер), если заметка не пуста.
  2. **Колонка «Истории»** (справа, тянется) — сразу список историй эпика (`key — title` + цветной статус-бейдж + возраст статуса), без сводных чипов сверху: счётчики уже есть в таблице, дублировать их в панели не нужно. У истории с подзадачами — стрелка-тоггл разворачивает их список под ней (тот же набор: бейдж + возраст, вложенно). Нет историй в эпике → «Историй нет.». Панель широкая (~1040px), чтобы длинные названия историй не рвались на четыре строки.
- **Возраст статуса** — короткая метка справа от бейджа: «1д», «22д». Дольше `STALE_DAYS` (3 дня) без смены статуса — красным. Считается в браузере от `statusChanged`, не зашивается числом при генерации.
- **Готовые задачи никогда не красные**: у бакета `done` возраст всегда зелёный, сколько бы дней ни прошло — закрытая задача стоит без движения по определению, «просрочка» там ложный сигнал. Подсказка меняется на «Закрыто N дн. назад».
- **Исполнитель** — двухбуквенные инициалы слева от ключа задачи (фамилия + имя из `displayName`: «Ишманов Алексей Юрьевич» → «ИА»), полное ФИО во всплывающей подсказке. Не назначен → «—» приглушённым. Колонка фиксированной ширины, чтобы названия задач выстраивались в ровную колонку.
  Закрытие — крестик, клик по оверлею, Esc.
- Кнопка **«Logs»** в правом верхнем углу страницы → та же панель в режиме ленты: что команда делала за последнюю неделю — смены статусов, комментарии и создание задач. Фильтры по типу события и по автору комбинируются, группировка по дням. Заметка этой панели хранится под отдельным ключом `__logs__`.
- Все внешние ссылки — `target="_blank" rel="noopener"`.

## Границы
Только чтение JIRA + генерация локального HTML-файла. Никаких записей в JIRA/Confluence, никакого автопубликования как Artifact без явной просьбы, никакого cron/автозапуска.
