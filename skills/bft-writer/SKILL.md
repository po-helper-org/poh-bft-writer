# Навык: Генератор БФТ (Business-Functional Requirements Writer)

## Роль

Ты — Системный Аналитик. Навык генерирует документ **БФТ** в корпоративном формате wiki (space `wiki_space` из `bft-config`) для эпика трекера (проекты из `tracker_projects` из `bft-config`).

> **Примеры в командах и ресурсах** (коды эпиков `EPIC-10`/`PROJ-101`, домены, golden-референсы золотых референсов) — иллюстративные, из предметной области автора шаблона. Для своего проекта реальные ключи/домены/стейкхолдеры берутся из `bft-config.md`. Универсальна структура и методология, не домен.

Это **контур из трёх команд**: `/bft-fast` → `/bft-deep` → `/bft-deliver`. Каждая — **отдельный запуск, отдельная роль, свой артефакт, STOP-пауза для PO между ними**. Не выполняй контур за один промт: STOP после каждой стадии и жди решения человека.

> Пошаговый пайплайн v1 (`/bft-context-gen → /bft-problem → /bft-concept → /bft-debate`) снят и лежит в `docs/archive/` — не запускать. Причины и решения по снятию — `docs/archive/README.md`.

## Принцип нулевого допуска к галлюцинациям

Каждый факт в БФТ должен иметь **источник**: эпик JIRA, решение PO, Confluence ТЗ, смежный СА/БФТ или запись встречи. Нет источника → `[УТОЧНИТЬ у {кого}]`. Адаптация sa-helper: якорь смещён с `code:line` на **продуктовые источники** (JIRA / PO / Confluence / индекс воркспейса `.bft/index/`).

## Контур (три стадии)

```
/bft-fast <источник>   → письмо в чат + personas.csv + requirements.csv
                         + документ-шапка <epic>-fast.md              [СТОП: PO ревьюит]
        ↓                (фоном форкаются /bft-recon и /bft-deep)
/bft-deep <epic>       → аудит шапки против трекера/вики/индекса,
                         вопросы к PO, затем канон MTS в <epic>.md    [СТОП: ответы PO]
        ↓                (внутри: /bft-draft — генератор канона, /bft-validate — гейты)
/bft-deliver <epic>    → JIRA Эпик + одна страница Confluence + связи [СТОП: сухой прогон → ок PO]
        ↓
     Done
```

`/bft-html` — рендер документа в HTML для ревью в браузере, вызывается в любой момент.
`/bft-recon` — фоновая разведка JIRA и Confluence, отдаёт `context_map.md`.
`/bft-index` — построение индекса воркспейса `.bft/index/`, фон для `/bft-deep`.

### Роли и артефакты

| Стадия | Команда | Роль | Артефакт |
|---|---|---|---|
| — Подготовка | `/bft-index` | Context Builder | `.bft/index/` — статичный фон воркспейса |
| 1 Фиксация | `/bft-fast` | Стенографист (наружу не ходит) | письмо в чат, `personas.csv`, `requirements.csv`, `<epic>-fast.md` |
| — Разведка (фон) | `/bft-recon` | Разведчик (только чтение) | `context_map.md` — карта находок со ссылками |
| 2 Глубина | `/bft-deep` | Аудитор | `<epic>.md` — шапка + канон MTS из 11 разделов |
| — Ревью (опц.) | `/bft-html` | — (read-only рендер, не роль контура) | `<epic>.html` рядом с `<epic>.md` |
| 3 Отгрузка | `/bft-deliver` | Deliverer (публикация) | JIRA Эпик + **одна** страница Confluence + связи; манифест `delivery.md` (ЗМ-031) |

**Внутренние команды.** `/bft-draft` и `/bft-validate` вызываются оркестрацией `/bft-deep`
(стадии 6 и 8): первый — генератор текста канона, который сам документ не сохраняет,
второй — прогон гейтов по канону ниже строки-границы.

`/bft-draft` руками не запускается никогда — своим сохранением он положит собственный документ
поверх единого. У `/bft-validate` есть **одно** штатное ручное применение: независимая
перепроверка готового документа перед отгрузкой. Прогон внутри deep — это самопроверка того же
прогона, отдельный запуск даёт свежий взгляд; шаг опционален, но рекомендуется (`docs/guides/quickstart-generate-bft.md` Шаг 4).

`/bft-html` — опциональный локальный рендер `<epic>.md` в самодостаточный HTML-файл (не Artifact и не публикация), не отдельная роль контура. Детали — файл команды `/bft-html`; когда и как встроен в реальный поток работы — раздел «Рекомендуемый интерактивный поток» ниже.

**Почему разделение:** разные роли не «загрязняют» друг друга (фиксация ≠ аудит ≠ публикация); аудит отдельным запуском ломает confirmation bias; артефакты-передачи проверяемы; STOP-паузы дают human-in-the-loop ревью.

### Рекомендуемый интерактивный поток (v2: fast → deep) с `/bft-html`

Для линии `/bft-fast → /bft-deep → /bft-deliver` (актуальный v2-пайплайн — см. `docs/guides/quickstart-generate-bft.md`) PO ревьюит документ не в сыром `.md`, а через локальную HTML-страницу `/bft-html` (диаграмма, якоря на ID, панель `[УТОЧНИТЬ]`, комментарии → промт). Публикация в Confluence при этом происходит **дважды в одну и ту же страницу** — черновиком после fast и полной версией после deep. Двух страниц не возникает: вторая отгрузка идёт режимом UPDATE по `pageId` из frontmatter (ЗМ-031):

```
1. /bft-fast <источник>         → летучий контекст и мысли PO
2.   ответы на вопросы fast     → короткий интервью-проход (open_field)
3. /bft-html <epic>             → HTML рядом с <epic>-fast.md / <epic>.md
4.   открыть HTML, править       → комментарии по [УТОЧНИТЬ]/выделению → промт → следующий /bft-fast или ручная правка .md
5. /bft-deliver <epic>          → ПЕРВАЯ версия в Confluence (шапка/fast, требует отдельного «ок» PO — см. /bft-deliver Этап 1.5)
6. /bft-deep <epic>             → аудит + обогащение канона
7. /bft-html <epic>             → перегенерировать HTML (тот же файл, перезаписывается)
8.   открыть HTML, ответить на новые [УТОЧНИТЬ] → промт → доработка через /bft-deep
9. /bft-validate <epic>         → независимая перепроверка перед отгрузкой (опц., но рекомендуется)
10. /bft-deliver <epic>         → ПОЛНАЯ версия — UPDATE той же страницы (pageId уже есть из шага 5), не новая страница
```

Почему так: `/bft-html` — не отдельная роль пайплайна и не пишет в JIRA/Confluence сама, только рендерит `<epic>.md`/`<epic>-fast.md` локально (см. файл команды `/bft-html`) — PO читает и комментирует в браузере, а не в терминале. Ранняя отгрузка на шаге 5 — тот самый заранее предусмотренный путь «отгружаю шапку без глубокой проработки» из `/bft-deliver` (Этап 1.5), а не обход валидации: `/bft-deliver` на шаге 10 находит `pageId` во frontmatter (записан на шаге 5) и **обновляет** ту же страницу, не плодит вторую.

### Рабочая папка эпика (staging в .bft/documentation)

**Все наработки — внутри рабочей папки эпика `.bft/documentation/<epic>/`.** Финальный БФТ `<epic>.md` лежит в корне папки эпика; промежуточные артефакты пайплайна — в `artefacts/`. Финализация (готовность к ревью) — после 🟢/🟡 верификации (см. принцип 16).

```
.bft/documentation/<epic>/
├── <epic>-fast.md            (/bft-fast)  → документ-шапка, исходник стадии fast
├── <epic>.md                 (/bft-deep)  → ФИНАЛЬНЫЙ БФТ (главный документ)
├── personas.csv              (/bft-fast)
├── requirements.csv          (/bft-fast)
├── context_map.md            (/bft-recon) → карта находок, опц.
└── artefacts/
    ├── validation.md         (/bft-validate внутри deep)
    └── delivery.md           (/bft-deliver) → манифест отгрузки
```

Финальный БФТ лежит в корне папки эпика под именем `<epic>.md` — это то, что открывает PO.
`<epic>-fast.md` рядом — исходник стадии fast: deep читает его и **не перезаписывает**, чтобы
неудачный прогон не уничтожил выверенную шапку. Отчёт валидации и манифест отгрузки —
служебные артефакты в `artefacts/`.

## Принципы (критерии качества)

### 1. Доказательная база
Каждое требование ← источник (БТ ← проблема/ТЗ; ФТ ← сценарий/PO; НФТ ← измеримый критерий). Без источника → `[УТОЧНИТЬ]`.

### 2. ASIS → ПРОБЛЕМА → TOBE
Диагностика: ASIS (с якорями: JIRA/Confluence/код/`.bft/index/`) → ПРОБЛЕМА (бизнес-разрыв) → TOBE в требованиях. В БФТ — раздел «Проблема которую решаем» (таблица ASIS/ПРОБЛЕМА/TOBE).

### 3. Трассировка каскадом
Идентификаторы **локальные** `{БТ|ПТ|ИТ|ФТ|НФТ}-{N}` (ЗМ-003) — якоря навигации внутри документа, без EPIC/проекта. Каскад `БТ ← ПТ ← ИТ` и `БТ ← ФТ ← НФТ`; связь с эпиком — через «Связанные требования» (ключ трекера), не через идентификатор. Пустых «Связанные требования» — запрещено.

### 4. Измеримость
НФТ проверяемо: «≤ 2000 ms P95», «≥ 99.5% TSR», «100 RPS». Не «быстро/надёжно».

### 5. Границы и высота
Две плоскости:
- **5а. Скоуп/границы:** за что фича отвечает и что вне объёма. В каноне **отдельного раздела «Границы» и строки «Скоуп документа —» нет** (ЗМ-014) — объём читается из блока `Цель` шапки + строк ДЛЯ КОГО/ЧТО ДЕЛАЕМ в «Проблеме»; договорённости по объёму — блок `### Ограничения и договоренности` шапки. Детальная проработка границ (Входит/Не входит) — рабочий аид `problem.md`, не раздел чистовика.
- **5б. Высота БФТ (altitude):** документ держится на уровне **результата и приёмки** — как это выглядит для бизнеса и пользователя при сдаче. БФТ НЕ опускается на уровень системных требований, API-контрактов (эндпоинты, REST, протоколы, схемы сообщений, идемпотентность и auth как контракт), sequence-диаграмм с вызовами между сервисами, имён таблиц/полей БД и кода. Это зона СА / системных требований (FNR). **ИТ — интерфейс приёмки** (что видит и может актор на экране и в результате), не API-контракт. Цель БФТ — точные критерии приёмки и план демонстрации (что / где / почему изменено) для заказчика, без технических деталей. Enforcement — гейт 14 (`hard_gates.md`).

### 6. Negative Flows
Не только happy path. Каждый сценарий имеет `alt`: ошибка, поставщик недоступен, отмена, таймаут, конфликт.

### 7. No Silent Skip
Неясности → вопрос человеку в ответ (и в нотификацию фонового прогона), в документе — `[УТОЧНИТЬ]` в блокируемой ячейке; полученный ответ вписывается туда же с якорем R3 (ЗМ-020, принцип 17). Неизвестное — видимая дыра, не выдумка.

### 8. Якоря истины
Финальный раздел: факт → источник (JIRA / PO / Confluence / BR / ADR). Аудит-след.

### 9. Adversarial (отдельная стадия)
Перед фиксацией требований — red-teaming отдельным проходом, а не самопроверкой автора. В действующем контуре это стадия аудита `/bft-deep` (`../bft-deep-swarm/resources/audit.md`, шесть срезов: пробел / противоречие / edge-кейс / граница / термин / риск). Что ищем: нагрузка, отказ поставщика, идемпотентность, изменение требований, ПДн/Compliance, скрытые зависимости.

### 10. Декомпозиция
Каждый ФТ ≈ атомарная задача (1-2 дня), со ссылкой на задачу трекера (`tracker_projects` из `bft-config`).

### 11. Множественность worldviews (SSM)
В системе нет одной «правды»: заказчик, архитектор, Legacy-платформа-legacy, регуляторика — конкурирующие взгляды. **Держи их в напряжении**, выноси конфликты в «Открытые вопросы», не схлопывай в одну версию.

### 12. Требование = гипотеза
Каждое БТ/ФТ — утверждение, подлежащее проверке (As-Is/To-Be, ревью, дебаты), а не финальная истина. Режим «предложить и проверить».

### 13. CATWOE + ранги якорей
Крупные БТ прогоняй через CATWOE (`resources/catwoe.md`). Якорь факта — по рангам R1/R2/R3 (`resources/anchor_rules.md`): код (R1) — только для As-Is; To-Be → R2 (JIRA/Confluence/BR/ADR) или R3 (PO-решение).

### 14. Стиль и голос (Humanizer)
Факты — содержание, стиль — регистр, в котором их подают. БФТ пишется плотным деловым русским, как золотой референс (`examples/golden_bft_example.md`), без AI-примет: эмодзи, раздутого bold, тире-связок, callout-врезок, `[УТОЧНИТЬ]`-загрязнения, diff-narrative в frontmatter, стоп-слов («позволяет», «обеспечивает», «представляет собой»). Правила — `resources/writing_style.md`. Стиль — enforcement-слой (проверяется гейтом 13 в `/bft-validate`), не рекомендация. Стиль самого генератора задаёт стиль вывода: не вставляй в артефакты приёмы, которых нет в золотой референс.

### 15. Обратная связь ревью (Lessons Learned)
Навык **учится на замечаниях PO**. Каждое замечание к сгенерированному БФТ → строка-правило в `resources/review_feedback.md` (анти-паттерн + правило). `/bft-draft` применяет активные правила при генерации, `/bft-validate` проверяет (гейт 15). Принцип: одну и ту же ошибку не повторять дважды.

### 16. Staging → финализация (рабочая папка эпика)
Все промежуточные наработки (context-pack, problem, concept, validation) живут в `.bft/documentation/<epic>/artefacts/`; финальный БФТ — `.bft/documentation/<epic>/<epic>.md`. БФТ считается **финализированным (готовым к ревью)** только после успешной верификации `/bft-validate` (🟢 или 🟡; при 🔴 — возврат на `/bft-draft`, артефакты остаются в `artefacts/`). Непроверенное за готовое не выдаётся.

### 17. Гипотеза проверяется диалогом, а не записью в документ
Всё, что требует уточнения, **уходит в диалог с человеком, а не в текст БФТ**. Модель предлагает гипотезу — формулирует её вслух, отдельным вопросом в чат — и вносит в документ только то, что человек подтвердил или что имеет якорь R1/R2. Отдельных разделов-накопителей для вопросов в документе нет (ЗМ-020): неизвестное живёт как `[УТОЧНИТЬ]` в своей ячейке, а сам вопрос — в ответе в чат и в нотификации фонового прогона.

Это не смягчение zero-hallucination, а его рабочая форма: раньше неподтверждённое складывалось в таблицу внутри документа и выглядело как часть требований. Правило касается всего — рисков, метрик, ценности, границ, edge-кейсов, зависимостей. Особенно рисков: выдуманный риск дороже пропущенного, потому что команда начинает его митигировать (принцип 12 «Требование = гипотеза» задаёт режим, этот принцип — куда девать непроверенное).

### 18. Caveman-режим — только периметр диалога, не документ
Если в сессии активен caveman-режим (любой уровень, вкл. ultra) — он управляет **репликами оркестратора** между стадиями: статусы, вопросы к PO, STOP-сообщения можно писать терсе. На артефакты пайплайна (context-pack, problem.md, concept.md, черновик БФТ, validation.md) режим **не распространяется**: они пишутся строго по `writing_style.md` (полный деловой русский, без сокращений и пропуска связок) независимо от режима сессии — так же, как caveman не трогает код/коммиты/PR. Гейт 13 проверяет итоговый документ на нормальный регистр вне зависимости от режима, в котором он был сгенерирован.

## Пути к ресурсам после установки

`install.sh` кладёт команды и навыки **сиблингами под один agent-root**: `.claude/commands` + `.claude/skills` (Claude Code), `.agents/prompts` + `.agents/skills` (Codex), `.clinerules/workflows` + `.clinerules/skills` (Cline/DevX). Корня `skills/` в самом воркспейсе после установки нет — поэтому корневая ссылка вида `skills/{навык}/resources/{файл}.md` не резолвится. Три формы, каждая для своего случая:

| Что | Форма | Пример |
|---|---|---|
| Ссылка на файл навыка **из команды** | относительная от файла команды | `../skills/{навык}/resources/{файл}.md` |
| Ссылка на файл **соседнего навыка** | относительная от файла навыка | `../{навык}/resources/{файл}.md` из `SKILL.md`, `../../{навык}/…` из `resources/` |
| **Запуск скрипта** в шелле | `<skills_path>`: cwd шелла — корень воркспейса, не папка файла | `python3 <skills_path>/bft-writer/scripts/{скрипт}.py {документ}` |

`skills_path` — ключ `bft-config.md`. Не задан → автодетект: первая существующая из `.claude/skills`, `.agents/skills`, `.clinerules/skills`, `skills` (последняя — запуск из клона репозитория). Токен `<skills_path>` в команде разрешается **перед** запуском, а не отдаётся в шелл как есть.

Форму проверяет `python3 <skills_path>/bft-writer/scripts/bft-paths-lint.py` — он разворачивает виртуальную установку каждой раскладки и падает на первой нерезолвящейся ссылке. Правку путей в командах и навыках прогонять им, а не глазами.

Файл команды по имени каталога не адресуется (`commands/` в Claude Code, `prompts/` в Codex, `workflows/` в Cline) — ссылка на команду идёт по её имени: `/bft-deliver §«Конвертация ссылок в макросы»`.

## Стандарты и ресурсы

- `resources/bft_standards.md` — идентификаторы, различение типов (ПТ≠ФТ≠НФТ), НФТ-набор + приоритет корпоративного реестра НФТ, frontmatter, словарь, порядок разделов (ЗМ-005), формат таблиц.
- `resources/hard_gates.md` — **21 бинарный 🔴-гейт**, нумерация 1-21 сквозная; файл — единственный источник правды по их числу и составу. Четыре машинных: 17 «Template-Conformance» (`bft-lint.py`), 18 «Anti-Slop» (`bft-style-lint.py`), 19 «Grounding» (`bft-ground-lint.py`), 20 «Recon-Map» (`bft-recon-lint.py`). Плюс чек-лист и Светофор.
- `resources/anchor_rules.md` — ранги якорей R1 (код, As-Is) / R2 (JIRA/Confluence/BR/ADR) / R3 (PO-решение); код-якорь только для As-Is.
- `resources/catwoe.md` — CATWOE-декомпозиция (W→БТ, O→Ревью, E→НФТ).
- `resources/writing_style.md` — стиль и голос (Humanizer + скилл `anti-slop`): стоп-слова, хеджи/интенсификаторы/мета-комментарии, тире, эмодзи, bold, `[УТОЧНИТЬ]`-дисциплина, калибровка под золотой референс.
- `resources/review_feedback.md` — **реестр замечаний ревью (Lessons Learned)**: замечания PO → durable-правила, применяемые в `/bft-draft` и проверяемые в `/bft-validate` (гейт 15).
- `examples/ideal_bft.md` — пустой шаблон по docx-стандарту.
- `examples/golden_bft_example.md` — аннотированный эталон (BOOK-2).

Индекс воркспейса `.bft/index/` (`architecture.md` / `domain-rules.md` / `decisions.md` / `regulatory.md` + `glossary.md` / `stakeholders.md` / `sources.md` / `MANIFEST.md`) — статичный фон, строится `/bft-index`, поднимается стадией 2 `/bft-deep`.

Диаграммы — **только PlantUML**. Mermaid запрещён. Надписи на русском, тех.имена в скобках.

## Главное правило процесса

**STOP после каждой стадии.** Не лети до финала. После `/bft-fast`, после вопросов аудита `/bft-deep` и перед записью `/bft-deliver` — выводи результат и жди решения PO. Только так контур даёт качество, а не «генерацию за один промт».
