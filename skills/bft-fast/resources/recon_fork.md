# recon_fork — фоновая разведка контекста + нотификации

## Флаг
`--no-recon` → пропустить разведку целиком (письмо, csv и документ отдаются как обычно; ручной путь `/bft-recon <epic_slug>` остаётся).

## Зачем отдельный контур

`/bft-fast` наружу не ходит и ходить не должен: на этом держатся ноль галлюцинаций и работа на Haiku. Но PO нужны **связи с уже накопленным знанием** — по теме встречи в JIRA может быть открытый эпик, в Confluence страница с решением, а в закрытых задачах отказ делать ровно это (ЗМ-028).

Разведка закрывает разрыв, не трогая периметр: она идёт **отдельным фоновым субагентом**, пишет **свой файл** и не открывает на запись ни письмо, ни csv, ни документы БФТ. Поэтому гейт грундинга (ЗМ-024, гейт 19) продолжает работать как работал: факту из JIRA физически некуда просочиться в fast-документ.

## Запуск (Этап 8 — вместе с deep-форком)

Разведка и deep форкаются на одном этапе, после того как Этап 7 дописал frontmatter. Порядок внутри этапа:

1. **Нотификация старта — обязательна.** PO должен видеть, что сбор данных идёт, а не гадать, откуда возьмутся находки:

   ```
   🔍 Разведка контекста запущена в фоне: JIRA (<проекты>) + Confluence (<space>).
      Ищу: <3-5 ключевых терминов>.
      Письмо и документ собраны, они от разведки не зависят — находки придут отдельным сообщением.
   ```

2. **Форк `bft-recon`** — Agent tool, `run_in_background`: субагент выполняет `/bft-recon <epic_slug> <fast-документ>`.

3. **Форк `bft-deep`** — по `deep_fork.md`, как раньше. В промт добавляется путь `context_map.md` с оговоркой: файл появится позже или не появится вовсе, работать в любом случае. Жёсткой зависимости между форками нет — они не синхронизируются.

Конфликта записи между тремя прогонами нет, файлы разные:

```
<docs_path>/<epic_slug>/<epic_slug>-fast.md   ← /bft-fast
<docs_path>/<epic_slug>/context_map.md        ← /bft-recon
<docs_path>/<epic_slug>/<epic_slug>.md        ← /bft-deep
```

## Что разведка не делает

- Не дописывает блок «Документация» письма: там живут только источники, названные самим PO (`letter_format.md`). Нотификация даёт готовый блок копипастой — вставляет PO.
- Не правит `personas.csv` и `requirements.csv`: найденный человек — строка `ВЛАДЕЛЕЦ` в карте, а не новая персона.
- Не трогает `<epic_slug>-fast.md`: находка, меняющая суть запроса, — повод для разговора с PO, а не для тихой правки документа.
- Не пишет в JIRA и Confluence вообще ничего.

## Деградация

| Ситуация | Поведение |
|---|---|
| Atlassian MCP недоступен | нотификация «разведка не выполнена: MCP недоступен (VPN?)», файл не создаётся, прогон `/bft-fast` считается успешным |
| `tracker_projects` и `wiki_space` не заданы | нотификация «разведка пропущена: в bft-config.md не заданы tracker_projects/wiki_space» |
| Задан только один из двух | разведка идёт по доступному источнику, пропуск виден в карте (§«Что не найдено») |
| Разведка упала | нотификация с причиной; письмо, csv и документ не затронуты |

Молча разведка не пропускается ни в одном из случаев: PO должен знать, была она или нет, иначе пустой чат читается как «ничего не нашлось».

## Нотификация (по завершении фона)

- Успех: `🗺 Карта контекста готова: <path> · N находок · топ-5 ниже` + три части по `../../bft-recon/resources/findings_format.md` §Нотификация (топ-5, вопросы с возможным ответом, предлагаемый блок «Документация»).
- Пусто: `🗺 Разведка завершена: по теме ничего не нашлось в <источники>. Карта: <path>` — пустой результат тоже результат, он снимает вопрос «а смотрели ли».
- Провал: `🗺 Разведка УПАЛА: <причина>; письмо, csv и документ не затронуты`.

## Отношение к `/bft-deep`

Карта — **указатель источников**, не фактбаза. `/bft-deep` на стадии 2 читает её, чтобы знать, куда смотреть, но поднимает источники сам и якорит факты по `../../bft-writer/resources/anchor_rules.md`. Факт, попавший в канон только со ссылкой на карту и без собственного якоря, — дефект: карта не проверялась гейтами документа.
