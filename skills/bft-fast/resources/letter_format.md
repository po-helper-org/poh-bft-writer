# Формат письма (letter_format.md)

Результат `/bft-fast` — одно письмо в чат, копируемое в мессенджер как есть. Пять блоков строго в порядке ниже. Вложение — два csv-файла (`personas.csv` + `requirements.csv`), пишется всегда на диск, не в теле письма.

## Шаблон

```
Цель: <драйвер/контекст: для эпика X, почему — закон/бизнес/требование>. <что делаем, одно предложение>.

How to demo:
1. … (нумерованный E2E — см. demo_synthesis.md; дизамбигуации «X, не Y» в скобках у шага; без внутренних US#N/story-ид)
2. …

Открытые вопросы:
* <вопрос / блокер / решение — одна развилка на строку> (<владелец или «кто уточнит, срок» — если есть>)
* …

Границы:
* <in-scope сущности> (<out-of-scope> — не входят в зону БФТ)
* Дополнительно, если возможно: <optional-scope пункты>
* <операционная заметка: сроки/эффекты>

Документация:
* <указатель одной строкой, или [подпись](URL) где URL известен>
* …
```

## Правила сборки

- **Порядок блоков фиксирован:** `Цель` → `How to demo` → `Открытые вопросы` → `Границы` → `Документация`.
- **Вложение — два csv-файла, всегда.** `/bft-fast` пишет `personas.csv` (стейкхолдеры) + `requirements.csv` (их требования) на диск (см. `requirements_table.md`), независимо от тела письма. Письмо остаётся чистым для пересылки; csv открываются в Excel/Sheets.
- **«Цель»** — 1-2 строки, WHY вперёд: вести с драйвером/контекстом (если фича — под-требование эпика, якорить на эпик: «для эпика GDSLV-1374 появилось требование от юристов — …, чтобы не нарушать закон»), затем «что делаем» одним предложением. Даёт мгновенный intent до демо. Всё из Summary; нет данных о драйвере/«зачем» — не выдумывать, оставить короче.
- **В теле письма нет frontmatter, меток пайплайна, идентификаторов `СТ-*`/`ФТ-*`/`US#N`/story-номеров.** Ссылка на родительский эпик (`GDSLV-1374`) допустима как якорь; внутренние user-story/US-номера — нет. Только человекочитаемый текст, копируемый в мессенджер как есть.
- **Точность.** Дизамбигуации из Summary (`дизамбигуации[]`) встраиваются в скобках прямо в свой демо-шаг или строку границ: «(оплачен, не создан)», «(как передают распы по АИС)». Не выносить отдельным пунктом, не выдумывать при отсутствии.
- **Вопросы — плоский сжатый список**, по строке на развилку. Строка = сам вопрос / блокер / решение / зависимость, кратко. Владелец — НЕ обязательный префикс: указывается в скобках в конце строки, только если известен (ответственный/исполнитель или «кто уточнит + срок»). Без группировки по ФИО, без чекбоксов. Допустимы блокеры и зависимости как строки (не только «вопросы»). Неатрибутированная строка — просто без скобок.
  - **Не делать:** обязательный префикс `ФИО —`; заголовки-группы `ФИО:` со списком под ними; чекбоксы `- [ ]`.
  - **Вопрос — только о том, что реально всплыло на встрече.** Не изобретать технические развилки (алгоритмы ранжирования BM25/TF-IDF, фильтры по типу кухни и т.п.), если участник их не поднимал. Выдуманный вопрос — та же галлюцинация, что и выдуманный факт.
  - **Пример-эталон (реальный кейс GDSLV-1569):**
    ```
    * Релиз не выкатываем, пока не стабилизирован переход с PayBox на Live.Процессинг (блокер)
    * Блокирует ли ограничение выпуск GDSLV-1374 (Даня + Катя уточнят у юристов к 29.07)
    * Что делаем в смешанных заказах — один билет по пушке, один обычный
    * Если заказ по Пушкинской карте — каталог ресторанов всё равно отправляем?
    * Откуда и как подтягивать признак оплаты Пушкинской картой (тех. реализация)
    ```
- **«Границы»:** список `*`, как «Открытые вопросы» и «Документация» — не сплошной абзац. Один пункт — одна мысль: in-scope сущности + явное «не входят в зону БФТ» для out-of-scope — одним пунктом; «Дополнительно, если возможно: …» — из `optional_scope_hints` (nice-to-have, отделён от must-have) — отдельным пунктом; операционные заметки (сроки, эффекты, интеграции) — отдельными пунктами, по одной на строку. Пусто по out-of-scope / optional / заметкам — соответствующий пункт не выдумывать и не оставлять пустым, просто не выводить.
- **«Документация»:** блок после «Границ» — пункты-указатели на источники, **названные самим PO** (Confluence основной истории, JIRA-эпик, смежные истории). Продиктован URL — кликабельная markdown-ссылка `[подпись](URL)`; назван источник без URL — человекочитаемая подпись, НЕ выдумывать URL. Ничего не искать, не резолвить и не проверять на существование: fast наружу не ходит. Источников не названо — блок не выводить (без пустого блока).
- **Голос** — по `../../bft-writer/resources/writing_style.md`: деловой русский, без эмодзи, без раздутого bold, без тире-связок, без стоп-слов, без AI-примет. Регистр — деловой, короче, WHY вперёд; сленг PO (рестики, пушка и т.п.) в письмо не тащить — оно уходит смежным командам/юристам.

## Гейт перед выводом (hallucination gate — СТ-23)

Пройти по каждому утверждению письма:
- Есть источник в Summary (факт, договорённость, затронутая сущность) → оставить.
- Нет источника → переоформить в строку блока «Открытые вопросы» (как вопрос/развилку).

**Правило:** ни одного факта-выдумки. Если что-то уверенно звучит, но нет цитаты в Summary — это не опускается молча, а становится вопросом. URL/ссылки в «Документации» — только реальные; нет URL → подпись без ссылки.

## Канал вывода

- **Основной канал:** текст письма в чат PO (копируется как есть, без служебных маркеров).
- **Вложение (всегда):** `personas.csv` + `requirements.csv` в `.bft/documentation/{epic_slug}/` (`docs_path` из `bft-config.md`, дефолт `.bft/documentation`; создать папку при отсутствии). Нет доступа к папке → рядом с источником, пометка `[УТОЧНИТЬ путь копии]`. В чат после письма — одна строка-ссылка: «Вложение: …/requirements.csv (N требований), …/personas.csv (M персон)».
- **Опциональная копия письма:** файл `.bft/documentation/{epic_slug}/letter.md` там же.
- **Документ БФТ:** блоки письма переносятся в шапку документа (`document_assembly.md` §Шапка) без изменения формулировок, с двумя отличиями переноса (ЗМ-016):
  - блок «Границы» в документе называется **«Ограничения и договоренности»** — имя другое, содержимое то же;
  - блок «Открытые вопросы» в документ **не переносится вовсе** (ЗМ-020): вопросы живут в письме и в ответе в чат, а в документе неизвестное остаётся как `[УТОЧНИТЬ]` в своей ячейке. Разделов-накопителей для вопросов в документе нет.

  Письмо остаётся самодостаточным для пересылки; документ — растущий артефакт, который дальше обогащает `/bft-deep`.
- **После письма (вне пересылаемого тела):** одна простая строка о развилке. Две формулировки, дословно (этот файл — их единственный источник, команда берёт отсюда):
  - штатно: «Глубокая проработка запущена в фоне, уведомление придёт по завершении».
  - при `--no-deep`: «Глубокая проработка не запускалась (`--no-deep`) — запусти `/bft-deep <epic_slug>` или скопируй промт из открытого поля документа».

  Без внутренностей пайплайна (swarm-субагенты, «3 оси», «тяжелее»).

## Формат ответа в чат

Ответ команды — не пересказ проделанного, а короткая сводка с адресами. Порядок фиксирован, лишних строк нет:

```
Документ: <путь к файлу>
Вложение: <путь>/requirements.csv (N требований), <путь>/personas.csv (M персон)

Открытые вопросы:
* <вопрос> (<владелец, если известен>)
* <вопрос>

<строка о развилке — дословно из «Канала вывода» выше>
```

Правила: список вопросов — тот же, что в письме, без пересказа и перегруппировки; вопросов нет — блок не выводится (пустого заголовка не ставить). Ни описания этапов, ни отчёта о том, что было прочитано, ни похвалы результату. Тело письма выводится отдельно и выше — оно копируется как есть.

Тот же формат держит `/bft-deep` в своём ответе и в нотификации фонового прогона: путь к документу, список вопросов аудита, следующий шаг. Вопросы попадают в этот блок — не в документ (ЗМ-020).

## Уроки правок PO (durable — не повторять)

Реальные правки PO к письму `/bft-fast` (кейс GDSLV-1569, пушкинская карта). Применять на всех письмах:

- **Цель — WHY вперёд**, якорь на родительский эпик; вести с драйвером (юр./бизнес), не с механизма.
- **Открытые вопросы — гибрид:** строка = вопрос/блокер/решение/зависимость; владелец опционален, в скобках как исполнитель или «кто уточнит + срок». Не обязательный префикс `ФИО —`.
- **Блок «Документация»** — указатели на источники (Confluence/JIRA/смежные истории), живые ссылки где есть URL.
- **Таблица-вложение = два csv-файла** (`personas.csv` + `requirements.csv`), пишется всегда, не в теле письма.
- **US#N/story-иды — вне тела письма** (эпик-якорь можно).
- **Без мета-хвоста пайплайна** в пересылаемом теле (никаких «Контекст RICH», «/bft-deep», «swarm-субагенты», «3 оси»).
