# Скелет документа БФТ (document_assembly.md)

## Назначение

Единственный источник правды о скелете единого документа БФТ: frontmatter-ключи, порядок блоков шапки, строка-граница, замороженная область, путь файла. Документ растёт в два такта — `bft-fast` собирает шапку и сохраняет файл, `bft-deep-swarm` дописывает канон MTS ниже границы, не трогая шапку. Оба навыка читают этот файл как контракт; эталон шапки — `../examples/golden_document.md`. Правила содержимого блоков этот файл не задаёт — только форму и порядок.

## Frontmatter

Десять ключей, в этом порядке:

| Ключ | Правило |
|---|---|
| `source` | URL опубликованной страницы Confluence; не опубликовано → `[УТОЧНИТЬ — не опубликовано]` |
| `space` | ключ пространства из `wiki_space` (`bft-config.md`); не задан → `[wiki_space не задан]` |
| `pageId` | id страницы Confluence после публикации; страницы ещё нет → `pending` |
| `version` | `0.1` на fast; на deep — инкремент (`0.2`, …) |
| `synced` | дата последней синхронизации, `YYYY-MM-DD` |
| `jira` | ключ эпика в трекере; эпика нет → `[СОЗДАТЬ эпик]` |
| `status` | короткий текстовый статус стадии |
| `epic_slug` | слаг эпика; неизменен на весь путь fast → deep |
| `stage` | `fast` \| `deep` |
| `pin_commit` | hash репозитория `poh-bft-writer` на прогоне; недоступен → `[УТОЧНИТЬ]`. В golden-фикстуре показан стенд-ин `[hash прогона]` — реальный hash в фикстуру не вписывается |

## H1

```
# [БФТ] <epic_slug>: <Название>
```

## Строка-статус

Блок-цитата сразу под H1, обновляемая на каждой стадии:

- **fast:** `> Статус проработки: ⚡ Шапка (bft-fast). Полный БФТ по шаблону MTS ещё не собран — см. блок «Полный БФТ — в проработке» внизу.`
- **deep:** заменяется на статус полного БФТ; конкретный текст задаёт `bft-deep-swarm`.

## Шапка

Заголовок и порядок подблоков фиксированы:

```
## Шапка (сутевое описание запроса)

Цель: <1-2 строки>.

| SMART | Значение |
|---|---|
| S (Specific) | <что именно делаем, конкретно> |
| M (Measurable) | <по чему проверяем, что цель достигнута> |
| A (Achievable) | <чем/кем достижимо> |
| R (Relevant) | <почему это важно сейчас, для кого> |
| T (Time-bound) | <срок/веха> |

### How to demo
### Ограничения и договоренности
### Документация          ← только если у письма есть этот блок
### Критичные требования (скелет на цитатах)
### Общая информация
```

`Цель` — бесзаголовочный абзац сразу под «## Шапка», не отдельный `###`-блок. Сразу под ним — SMART-таблица (см. ниже, документ-специфика). `Документация` — условный блок: письмо его опускает, когда источников нет (`letter_format.md`); тогда его нет и в шапке, пустой заголовок не ставится. Содержимое и правила сборки каждого блока этот файл не задаёт:

- `Цель`, `How to demo`, `Ограничения и договоренности`, `Документация` — по `letter_format.md`. В письме соответствующий блок называется «Границы»; в документе он идёт под именем «Ограничения и договоренности» (ЗМ-016) — переименование при переносе, содержимое то же.
- Персоны и таблица требований в «Критичные требования» — по `requirements_table.md`. В шапке они markdown-таблицами; те же строки уходят в машиночитаемое вложение `personas.csv` / `requirements.csv`.
- `Общая информация` — карточка проекта таблицей `Поле | Значение`: Название проекта, Ответственный за продукт, Ответственный за документ, Задача/Epic Jira, Статус, Системные требования. Неизвестное → `[УТОЧНИТЬ]`, не догадка.

**Блока `### Открытые вопросы` в шапке нет** (ЗМ-016). В письме он остаётся — письмо пересылают коллегам, вопросы там и работают. В документе открытые вопросы живут единственный раз, в таблице «Вводные для разрабатываемого функционала\*» ниже границы: `bft-fast` заводит её сразу, `bft-deep` дописывает ответы. Дубль «вопросы в шапке + вопросы во Вводных» запрещён.

**Раздела «Бизнес описание» в каноне тоже нет** (ЗМ-016): образ результата несёт блок `Цель` шапки. Отдельного «Общая информация» ниже границы нет — она в шапке.

## SMART-таблица цели (только документ)

**Исключение из переноса «письмо → документ» без изменений (см. выше):** `Цель` — единственный блок, где документ добавляет то, чего нет в письме. В письме `Цель` остаётся 1-2 строкой WHY-вперёд (`letter_format.md`) — коротко, чтобы копироваться в чат как есть. В документе сразу под этой строкой встаёт таблица `SMART | Значение`, пять строк, порядок фиксирован S → M → A → R → T.

Источник каждой строки — Summary/транскрипт этой же встречи, не домысел:

| SMART | Откуда брать |
|---|---|
| S (Specific) | конкретика «что делаем» из `Цель`/«Что делаем» Summary — без обобщений |
| M (Measurable) | измеримый критерий из Summary (срок/% /наличие эффекта), если прозвучал |
| A (Achievable) | способ/ресурс достижения, если на встрече обсуждали, кем и как |
| R (Relevant) | связь с бизнес-драйвером/проблемой, которая уже названа в `Цель` |
| T (Time-bound) | срок/веха, если названа (иначе — не путать со сроком публикации правок, это другое) |

**Zero-hallucination.** Для встречи уровня discovery (что и есть typичный вход `bft-fast`) не каждая буква обязательно имеет основание в Summary — особенно A и T реже звучат явно, чем S/M/R. Нет основания → `[УТОЧНИТЬ]` в ячейке, не общая формулировка-заглушка («достижимо силами команды», «важно для бизнеса»). Общая заглушка без конкретики — то же самое, что придуманный департамент из `requirements_table.md`: гейт 18 (`bft-writer/resources/hard_gates.md`) такие формулировки ловит как хедж/интенсификатор.

Гейт: `bft-lint.py` проверяет, что таблица `SMART | Значение` с пятью строками S/M/A/R/T присутствует сразу после `Цель:` (код `HD007`, гейт 17).

## Строка-граница

Байт-точная константа, ровно одна на документ, сразу после раздела «Критичные требования»:

```
<!-- BFT-HEAD-END · ГРАНИЦА ШАПКИ · выше bft-fast, ниже bft-deep · шапку не затирать -->
```

Не переформулировать и не переносить в другое место. Одинакова в `bft-fast` (пишет) и `bft-deep-swarm` (ищет).

## Замороженная область

От строки `## Шапка (сутевое описание запроса)` до строки-границы включительно. `bft-deep-swarm` не меняет здесь ни байта — ни формулировки, ни порядок ID, ни таблицы. Frontmatter и строка-статус — обновляемые, в заморозку не входят: они лежат выше замороженной области.

## Область канона

Всё ниже строки-границы:

- **До deep (`stage: fast`):** раздел `Бизнес-Требования` с единственным подразделом `## Вводные для разрабатываемого функционала*` (таблица открытых вопросов из письма, колонка «Ответ» пуста) → затем плейсхолдер-заголовок `## ⏳ Полный БФТ — в проработке` + открытое поле по `open_field.md`.
- **После deep (`stage: deep`):** полный канон MTS в порядке `../../bft-writer/resources/bft_standards.md` §«Порядок разделов», вместо плейсхолдера. Таблица «Вводные» не пересоздаётся — в неё дописываются ответы.

## Порядок якорей поиска границы

`bft-deep-swarm` ищет точку вставки канона в этом порядке:

1. HTML-комментарий `BFT-HEAD-END`.
2. Заголовок `## ⏳ Полный БФТ — в проработке`.
3. Заголовок «Проблема которую решаем» — первый раздел канона, его наличие означает, что документ уже обогащён. Искать в обеих формах разметки: ATX (`## Проблема которую решаем`) и Setext (строка `Проблема которую решаем`, под ней линия `===`). Эталоны канона MTS используют Setext (`../../bft-writer/examples/ideal_bft.md`), поэтому проверка только по `#`-заголовкам даёт ложный «не обогащён».
4. Ничего не найдено → канон дописать в конец файла, ничего не удалять, вывести предупреждение.

## Проверка перед записью (обязательна)

Скелет из этого файла проверяется машинно, а не «на глаз». Перед сохранением документа прогнать:

```bash
python3 skills/bft-writer/scripts/bft-lint.py <docs_path>/<epic_slug>/<epic_slug>.md
```

Ненулевой код выхода = документ не соответствует шаблону: исправить и прогнать снова. Записывать и публиковать документ с ошибками линтера нельзя — именно так теряются граница шапки, разделы канона и цитаты в критичной таблице. Полный список кодов — `../../bft-writer/scripts/bft-lint.py` (заголовок файла) и `../../bft-writer/resources/hard_gates.md` §«Гейт 17».

## Путь файла

```
<docs_path>/<epic_slug>/<epic_slug>.md
```

`docs_path` из `bft-config.md`, дефолт `.bft/documentation`.
