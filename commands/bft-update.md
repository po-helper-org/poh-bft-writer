## Использование

```
/bft-update [--check] [--workspace <корень>] [--no-restart]
```

**Параметры:**
- `--check` — только отчёт: версия чекаута против `origin/main`, из какого чекаута харнесс грузит плагин, синхронны ли навыки воркспейса с чекаутом, отвечает ли харнесс. Ничего не меняет.
- `--workspace <корень>` — воркспейс, чьи `.claude/skills` и `.claude/commands` обновить. Не задан → берётся `workspaceRoot` из строки `bft-requirements` в `cordis.patch.yml` профиля харнесса.
- `--no-restart` — обновить чекаут, собрать плагин и навыки, но харнесс не перезапускать (плагин подхватится после ручного перезапуска).

Остальные ключи — `bash update.sh --help`.

## Важно

**Две половины устаревают по отдельности.** Плагин раздела «Управление требованиями» харнесс грузит по `link:` из `plugin/` чекаута `poh-bft-writer` — новый код появляется после `git pull`, `pnpm build` и перезапуска. Навыки `/bft-*` — копия `skills/` и `commands/` в `.claude/` воркспейса, подключённого к харнессу как skill-root, — их кладёт `install.sh`. Обновить одно и забыть другое — обычный способ получить «навык пишет `-fast.html`, а раздел его не видит» или наоборот.

**Запускать из терминала или Claude Code, не из чата харнесса.** Перезапуск убивает процесс харнесса вместе с сессией, из которой его позвали; launchd поднимет харнесс заново, но ответа в тот чат уже не будет.

**Гейт — HTTP 200.** Несобранный или сломанный плагин роняет весь харнесс, а launchd перезапускает его в цикле: агент в `launchctl list` живой, порт мёртвый. Поэтому перед перезапуском гоняется `plugin/test-contract.sh`, а после — опрос адреса до `200` и лог на `invalid plugin`. Не 200 — обновление не считается выполненным.

## Инструкция для LLM

1. Найти чекаут `poh-bft-writer`, из которого харнесс грузит плагин: `DSH_HOME` живого процесса `dsh web` → `profiles/web/node_modules/<пакет плагина>` → `pwd -P` → это `<чекаут>/plugin`. Скрипт делает это сам; если профиль ссылается на другой чекаут, он откажется и назовёт путь — обновлять надо тот.
2. Выполнить из корня чекаута:

```bash
bash update.sh --check
```

   Прочитать отчёт: что отстаёт (чекаут, `plugin/lib`, навыки), на какой ветке чекаут, есть ли незакоммиченные изменения. Ветка не `main` или грязное дерево — обновление скрипт не начнёт: это чекаут разработчика, решает человек (`git stash` / `git checkout main`), спросить.
3. Обновить:

```bash
bash update.sh --workspace <корень воркспейса>
```

   Скрипт: `git pull --ff-only origin main` → `pnpm install --frozen-lockfile` и `pnpm build` в `plugin/` → `plugin/test-contract.sh` → `install.sh` в воркспейс (та же версия, что у плагина: `BFT_WRITER_SRC`) → перезапуск (`launchctl kickstart -k` агента с `dsh-harness` в имени или `--restart-cmd`) → опрос адреса до `200` → лог харнесса на ошибки плагина.
4. Отчитаться строкой «Готово: bft-writer <коммит> в харнессе» из вывода скрипта и напомнить, что открытая вкладка харнесса получила новый токен — ссылка в последней строке `/tmp/dsh-harness-ui.log`.
5. Не 200 или `FAIL` в выводе — процитировать причину, не отчитываться о готовности. Разбор типовых поломок — `docs/guides/dsh-plugin-setup.md` §«Если не поднялось».

Полная инструкция с разбором каждой половины — `docs/guides/dsh-plugin-update.md`.
