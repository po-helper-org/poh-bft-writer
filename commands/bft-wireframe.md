## Использование

```
/bft-wireframe <epic_slug|путь> [сценарий] [--device browser|mobile]
```

**Параметры:**
- `<epic_slug|путь>` — слаг эпика (документ ищется по стандартному пути `<docs_path>/<epic_slug>/<epic_slug>.md`, если есть, иначе `<epic_slug>-fast.md`) либо прямой путь к документу.
- `[сценарий]` — опц., номер или заголовок конкретного сценария («Сценарий 2», «расчёт без реальных сделок»). Не задан → все сценарии `How to demo`, у которых ещё нет блока раскадровки.
- `--device browser|mobile` — опц., принудительно задать рамку вместо эвристики (`../skills/bft-wireframing/resources/device_heuristic.md`).

## Примеры

```
/bft-wireframe 2026-09-07-ton-mev-sandwich
/bft-wireframe 2026-09-07-ton-mev-sandwich "Сценарий 3"
/bft-wireframe .bft/documentation/direct-faq/direct-faq.md --device mobile
```

## Важно

**Роль: раскадровщик.** Не источник требований — рисует то, что уже написано в `HowToDemo`, ничего не придумывает и не меняет ни слова сценария.

**Не входит в контур по умолчанию.** `/bft-fast` и `/bft-deep` эту команду не вызывают ни в фоне, ни автоматически — только явный запуск.

**Не занимает высоту БФТ.** Живёт в шапке рядом с `How to demo`, не в каноне. Раздел «Требования к интерфейсам\*»/«Макеты интерфейса\*» и «План демонстрации» (canon) не трогает и не подменяет.

**Один shell на документ.** Все кадры одного БФТ используют одну и ту же навигацию — различается только подсвеченный активный пункт.

**Не перерисовывает готовое.** Сценарий, под которым уже стоит блок раскадровки, пропускается по умолчанию; перерисовать — явная просьба.

**Рендер — на странице ревью.** В `.md` остаётся компактный DSL-текст; сам SVG собирает `/bft-html` при сборке страницы. Требует установленного рантайма (`npm install` в `../skills/bft-wireframing/scripts/wireloom-runtime/`) — без него блок остаётся, но на странице вместо картинки честный `[УТОЧНИТЬ: навык bft-wireframing не установлен]`.

## Инструкция для LLM

Навык — `../skills/bft-wireframing/SKILL.md`. Порядок работы — этапы 1-9 оттуда (read → parse → skip existing → device → shell → frame → insert → verify → notify).

### Гейт перед записью (обязателен)

Каждый новый блок — до того, как он останется в документе:

```bash
python3 <skills_path>/bft-wireframing/scripts/wireloom-render.py --device browser < блок.txt > /dev/null
```

(`--device mobile` — если рамка мобильная). Ненулевой код — причина в stderr, переписать кадр и прогнать снова; в документ не сохранять заведомо битый DSL.

### САМОПРОВЕРКА ПЕРЕД ВЫВОДОМ

1. Текст `HowToDemo`/«Образ результата»/SMART-таблица и весь канон ниже границы — не тронуты?
2. Каждый блок стоит сразу после `HowToDemo:` своего сценария, до заголовка следующего?
3. Навигация (список разделов слева / `tabbar`) одна и та же во всех кадрах документа, отличается только `active`/`selected`?
4. Каждое число или статус на кадре — цитата уже одобренного текста документа, а не новое значение?
5. Каждый новый блок прогнан через `wireloom-render.py` с кодом 0 (или причина отказа явно вынесена в нотификацию)?
6. Сценарии, у которых раскадровка уже была, не перегенерированы без явной просьбы?
