## Использование

```
/bft-validate <epic_code>
```

Вход: финальный БФТ `.bft/documentation/<epic>/<epic>.md` (из `/bft-draft`). Выход: отчёт `artefacts/validation.md` + правки БФТ.

## Важно

**Роль: Validator (свежий взгляд).** Это **отдельный запуск** — критический проход по чужому черновику, не «самопроверка» автора. Прогон 16 бинарных 🔴-гейтов + чек-лист + отчёт «Светофор».

> Аналог sa-helper: `/validate-doc`. При 🔴 — вернуть на `/bft-draft`.

**Область валидации.** Сначала найди в файле строку с токеном `BFT-HEAD-END` — это HTML-комментарий-граница шапки (искать по токену, не по полному тексту комментария). Она есть → это единый растущий документ, и гейты прогоняются **только по канону ниже границы**. Шапка (от `## Шапка (сутевое описание запроса)` до границы включительно), строка-статус под H1 и открытое поле / блок «Продолжить / уточнить БФТ» — read-only контекст: их читают для сверки канона, не правят и в нарушения гейтов не записывают. Строки-границы нет → поведение прежнее, гейты по всему документу.

**Принцип:** проверяй против источников (якорей), не «верь на слово» черновику.

## Инструкция для LLM

### Этап 1: Загрузка ролей и чек-листов
1. Прочитай `skills/bft-writer/SKILL.md` (принципы — это критерии).
2. Гейты: `resources/hard_gates.md`. Стандарты: `resources/bft_standards.md`. Стиль: `resources/writing_style.md`. Шаблон: `examples/ideal_bft.md`.
3. **`resources/review_feedback.md` — реестр замечаний ревью.** Все строки `активно` = проверяемые правила (уроки прошлых БФТ).

### Этап 2: 4 итерации рефлексии (разные линзы)

**Итерация 1 — Структура и трассировка (Gateway):**
- Все разделы канона **в фиксированном порядке** (ЗМ-005/ЗМ-016: Проблема которую решаем → Изменение в UJM → План демонстрации → Бизнес-Требования (Ценность\*) → Пользовательские\* → Интерфейсы\* → Функциональные\* → Нефункциональные\* → Зависимости → Риски → Якоря); имена разделов/колонок дословно (ЗМ-006); в каноне нет «Бизнес описание», «Общая информация», «Заинтересованные стороны», «История изменений», «Доп. материалов», «Ревью требований», «Границы», «Критерии успеха», «Ключевые решения» — блок `### Ограничения и договоренности` в шапке это не нарушает: обязательный блок шапки, другой уровень (гейт 4); идентификаторы локальные `{TYPE}-{N}` (без EPIC, ЗМ-003); frontmatter без служебных лесов (ЗМ-007); объём задан блоком `Цель` шапки + ДЛЯ КОГО/ЧТО ДЕЛАЕМ в «Проблеме», без строки «Скоуп документа —» (ЗМ-014).
- Нет пустых «Связанные требования»; каскад БТ←ПТ←ИТ и БТ←ФТ←НФТ; эпик-якорь.

**Итерация 2 — Качество требований (Storage):**
- БТ и каждый ФТ имеют приоритет. НФТ только измеримые (число/%/RPS/срок) — оценочные = 🔴.
- ПТ в формате Когда/Я хочу/Чтобы. ФТ ≈ атомарные.
- Есть раздел «Изменение в UJM» (Было/Стало). Числовых «Критериев успеха» отдельным разделом в чистовике не требуется (v10).
- Блок `Цель` шапки даёт образ результата конкретно и операционно (ЗМ-013). Абстрактное «документ описывает требования к…» = 🟡, но правится повторным `/bft-fast`: шапку валидатор не редактирует.
- **Самопроверка на противоречия (ЗМ-014):** блок `Цель`, «Проблема» (ДЛЯ КОГО/ЧТО ДЕЛАЕМ/TOBE), БТ, ФТ, «Изменение в UJM» и перечень сущностей не должны противоречить друг другу (напр. «пилот на одном типе» в одном месте и «все типы» в другом). Противоречие = 🔴, указать оба места. Нет строки «Скоуп документа —».

**Итерация 3 — План демонстрации и высота БФТ (Human-Readable + Altitude):**
- Раздел «План демонстрации»: PlantUML — actor-level / black-box, с ≥1 веткой `alt` (negative flow). Вызовы между сервисами, имена сообщений/API = 🔴 (гейт 14). Mermaid = 🔴.
- Таблица акторов. Надписи на языке документа, тех.имена в скобках.
- Атрибутивный состав сообщений отсутствует (он — зона СА). Эндпоинты/REST/схемы/БД-поля/код в теле = 🔴 (гейт 14).

**Итерация 4 — Источники и неизвестное (Hallucination):**
- Открытые вопросы в документ не записаны: нет раздела «Вводные для разрабатываемого функционала\*» и других накопителей, неизвестное — `[УТОЧНИТЬ]` в ячейке (ЗМ-020, гейт 7).
- Якоря истины заполнены (факт → источник). Неподтверждённое → `[УТОЧНИТЬ]`.
- Ни одного факта без якоря и без `[УТОЧНИТЬ]`; ни одного выдуманного стейкхолдера/метрики/срока (ЗМ-008); нет утечки служебных лесов (ЗМ-007) — Hallucination Gate.
- Все ссылки Jira/Confluence ведут на существующую страницу (ЗМ-009): markdown-ссылка, не голый текст, не битый/выдуманный URL; где MCP доступен — сверить существование (`jira_get_issue`/`confluence_get_page`). Несуществующее ссылкой = 🔴.
- Каждое вхождение JIRA/Confluence линковано, а не только первое; линкованы и **JIRA-проекты**, и **Confluence-пространства** (ЗМ-012). Голый ключ/pageId/имя проекта в любой колонке = 🔴 (гейт 10). `BR-*`/`US#N` не линкуются.

**Итерация 5 — Стиль и голос (`writing_style.md`):**
- В каноне нет эмодзи (`⚠️ ✅ ❌ ⚡ …`). Статусные значки только в самом `validation.md`. Маркеры прогресса `⚡ ⏳ ▶ ✅` в строке-статусе под H1, в заголовке `## ⏳ Полный БФТ — в проработке` и в `<summary>` открытого поля / блока «Продолжить / уточнить БФТ» — санкционированная семантика стадии, не 🔴 (гейт 13).
- Нет callout-врезок `> **⚠️ …`. Скоуп-предположения живут в прозе или «Открытых вопросах».
- В ячейках таблиц БТ/ИТ/ФТ/НФТ нет `**bold**` (кроме story-ключей ПТ).
- Em-dash — для определений и перечислений, не как связка; не больше одного на предложение.
- Нет стоп-слов («позволяет», «обеспечивает», «осуществляет», «представляет собой», «важно отметить»).
- `[УТОЧНИТЬ]` без кросс-рефов `[УТОЧНИТЬ Ox]`; нет дубля «верхняя + нижняя» таблицы вопросов.
- Frontmatter без diff-narrative (`supersedes …исправлено`, многословный `status`).

**Итерация 6 — Замечания ревью (Known-Mistake):**
- Прогон по всем `активно`-строкам `resources/review_feedback.md`.
- Любое нарушенное правило реестра = 🔴 (гейт 15). В отчёте укажи ID замечания (`ЗМ-NNN`).

### Этап 3: Hard Gates (17 бинарных 🔴)
Прогон по таблице из `resources/hard_gates.md` (гейты 1–16, включая гейт 13 «Стиль/Голос», гейт 14 «Высота БФТ», гейт 15 «Known-Mistake» и гейт 16 «Self-Consistency») — в едином документе по канону ниже `BFT-HEAD-END` (§«Область валидации», `hard_gates.md` §«Область применения»).

**Гейт 17 «Template-Conformance» прогоняется первым и по всему файлу:** `python3 skills/bft-writer/scripts/bft-lint.py <документ>`. Ненулевой код = 🔴; коды и зоны — `hard_gates.md` §«Гейт 17». Находки линтера в шапке (`HD*`, `CT*`) в отчёт попадают, но правит их повторный `/bft-fast` — валидатор шапку не редактирует. Любой 🔴 = документ не готов.

### Этап 4: Отчёт «Светофор»
Таблица по слоям (Структура / Скоуп+высота БФТ / Трассировка / НФТ / Negative flows / Изменение в UJM / Якоря / Риски-зависимости / Стиль и голос / Замечания ревью / Шаблон) → 🟢/🟡/🔴 с доказательством и «что исправить».

### Этап 5: Маршрут
- Сохрани `.bft/documentation/<epic>/artefacts/validation.md`.
- **Если есть 🔴:** внеси правки в БФТ — в едином документе **только ниже строки-границы `BFT-HEAD-END`**; шапка, строка-статус и открытое поле не редактируются ни при каком 🔴 — ИЛИ выведи:
  ```
  🔴 Найдены нарушения Hard Gates: <список>.
  → /bft-draft <epic> (исправить и пересдать). БФТ не финализирован.
  ```
- **Если 🟢/🟡 только — выведи РОВНО это (финал пайплайна), ничего сверх:**
  ```
  Файл БФТ: .bft/documentation/<epic>/<epic>.md

  Артефакты — .bft/documentation/<epic>/artefacts/:
  | Файл | Стадия |
  |---|---|
  | bft-context-pack.md | контекст |
  | problem.md | диагноз As-Is/Gap |
  | concept.md | концепты + дебаты + вердикт |
  | validation.md | hard gates + Светофор |

  Валидация: <светофор> (<N> блокирующих 🔴, <гейты>/17; bft-lint: <код выхода>).
  Перед разработкой закрыть (если есть 🟡): <одной строкой>.
  ```
- **Только эти блоки.** НЕ добавляй: пересказ покрытия end-to-end, список вшитых решений (PD-*), «следующий логичный шаг» с предложением другого скила, похвалу. Главное — путь к файлу БФТ и таблица артефактов. Если папка эпика содержит файлы сверх перечисленных, добавь их строками в таблицу; выдуманные строки не добавляй.

## Запреты
1. Не «сглаживай» 🔴 — если гейт нарушен, фиксируй честно.
2. Не переписывай черновик целиком — точечные правки или возврат на /bft-draft.
3. Не трогай шапку единого документа: ни байта выше строки-границы `BFT-HEAD-END` (плюс строка-статус и открытое поле). Нужна правка там — вынеси её строкой в отчёт, правь ниже границы.
4. Проверяй против якорей, не против самого черновика.
5. Не финализируй БФТ при 🔴 — готовым к ревью считается только верифицированное (🟢/🟡). Непроверенное за готовое не выдаётся (принцип 15).
