---

## Использование

```
/bft-context-gen <epic_code> <jira_key>
```

**Параметры:**
- `<epic_code>` — короткий код БФТ (напр. `EPIC-10`).
- `<jira_key>` — эпик JIRA (напр. `PROJ-101`).

## Примеры

```
/bft-context-gen EPIC-10 PROJ-101
/bft-context-gen EPIC-PROC PROJ-103
```

## Важно

**Режим:** контекст-пак из `.bft/index/` (см. `/bft-index`) + один запрос к JIRA, далее LLM синтезирует вероятную картину домена. Неизвестное — честно помечает `[УТОЧНИТЬ]`. Индекс неполон (см. `MANIFEST.md` — источники со статусом `UNAVAILABLE`) — перезапусти `/bft-index` для полного покрытия перед `/bft-problem`.

**Когда достаточно текущего индекса:**
- `MANIFEST.md` показывает `INDEXED` по релевантным источникам
- Нужно быстро войти в контекст перед встречей с PO
- Первый черновик для ориентира перед перестройкой индекса
- JIRA/Confluence временно недоступны (VPN)

**Когда сначала перезапустить `/bft-index`:**
- Новый/незнакомый эпик, индекс собирался давно или не собирался
- В `MANIFEST.md` много `UNAVAILABLE` по релевантным источникам
- Требуется полная доказательная база для БФТ без дыр

## На выходе

```
.bft/documentation/<epic>/artefacts/
└── bft-context-pack.md   ← pack: .bft/index/ + базовый JIRA + LLM-синтез + матрица покрытия
```

**Иные файлы не создавать.** Pack — единственный артефакт, который читает `/bft-problem`. Кладётся в `artefacts/` (служебная папка пайплайна); финальный БФТ `<epic>.md` появится в корне папки эпика на стадии `/bft-draft`.

## Инструкция для LLM

### Этап 0: Подготовка

1. Создай папку `.bft/documentation/<epic>/artefacts/`.
2. Зафиксируй `epic_code` и `jira_key`.
3. Прочитай `.bft/index/MANIFEST.md` — зафиксируй покрытие (INDEXED/UNAVAILABLE по источникам).
4. В шапке pack сразу пометь: `Режим: контекст-пак из .bft/index/. Индекс неполон — /bft-index.`

### Этап 1: `.bft/index/` — читаем локальный фон (без сетевых запросов)

Прочитай из индекса только релевантное по теме эпика:

- **Архитектура** (`.bft/index/architecture.md`) — границы, потоки, сервисы.
- **Регуляторика** (`.bft/index/regulatory.md`) — применимые законы.
- **Бизнес-правила** (`.bft/index/domain-rules.md`) — релевантные правила домена.
- **Решения** (`.bft/index/decisions.md`) — известные ADR и PO-решения.
- **Глоссарий** (`.bft/index/glossary.md`) — термины домена.
- **Стейкхолдеры** (`.bft/index/stakeholders.md`) — владельцы/роли по зонам ответственности.
- **Смежные БФТ** (`.bft/documentation/*/`) — есть ли уже готовый документ по этому домену?

Фиксируй: что нашёл / чего нет (→ `[УТОЧНИТЬ: нет в индексе]`). Источник со статусом `UNAVAILABLE` в `MANIFEST.md` — не «пусто», а прямой сигнал перезапустить `/bft-index`.

### Этап 2: JIRA базовый (один запрос на эпик)

1. `mcp__atlassian__jira_get_issue(<jira_key>)` — описание, статус, приоритет, labels, assignee, components.
2. Из описания эпика выдели: цель, scope, связанные компоненты, упомянутые зависимости.
3. **Дочерние задачи не запрашиваем** — только эпик.
4. Если JIRA недоступен → `[УТОЧНИТЬ: JIRA недоступна (VPN?)]`, продолжай по индексу.

### Этап 3: LLM-синтез на основе индекса + JIRA

На основе прочитанного — рассуждай как опытный аналитик домена. **Явно разделяй факт и вывод:**

- **Факт** (из индекса / трекера) — помечай источником: `(architecture.md)`, `(JIRA)`, `(domain-rules.md)`, `(decisions.md)`
- **Вывод LLM** — помечай: `[вывод LLM, требует проверки]`
- **Неизвестное** — помечай: `[УТОЧНИТЬ у {кого}]`

Синтезируй по блокам:

**A. Домен и контекст**
- Что делает эпик (своими словами, 2-3 предложения)
- К какому домену относится (термины и команды из `.bft/index/glossary.md`)
- Какие сервисы и БД затрагивает (из `architecture.md` + JIRA)

**B. As-Is (вероятная текущая ситуация)**
- Как эта область работает сейчас (из `architecture.md`, смежных БФТ в `.bft/documentation/`)
- Где источник истины (системы из `architecture.md` / `.bft/index/sources.md`)
- Что считается болью/проблемой (из JIRA description + индекса)

**C. Стейкхолдеры (вывод LLM)**
- Кто владелец домена (из `stakeholders.md`)
- Кого затрагивают изменения (смежные команды/системы из `architecture.md`)
- Кто согласует (PO / архитектор / юристы по `regulatory.md`)
- Пометь весь блок: `[вывод LLM — проверить с PO]`

**D. Зависимости (вывод LLM)**
- Какие смежные системы/команды вовлечены (из `architecture.md`)
- Какие интеграции затрагивает
- Известные блокеры или зависимые эпики (из JIRA description)
- Пометь: `[вывод LLM — статус согласования неизвестен, уточнить]`

**E. Регуляторика и риски (из `regulatory.md`)**
- Применимые законы/требования из `.bft/index/regulatory.md`
- Если `regulatory.md` не покрывает тему → `[УТОЧНИТЬ: регуляторика для данного домена]`

**F. Открытые вопросы**
- Всё неизвестное из блоков выше — сводный список `[УТОЧНИТЬ у {кого}]`

### Этап 4: Матрица покрытия

| Раздел БФТ | Источник | Режим | Статус |
|---|---|---|---|
| Домен и контекст | JIRA + architecture.md | факт | ✅/[УТОЧНИТЬ] |
| As-Is | architecture.md + смежные БФТ | факт | ✅/[УТОЧНИТЬ] |
| Стейкхолдеры | stakeholders.md + LLM-вывод | вывод | ⚠️ проверить |
| БТ (ценность) | JIRA description | факт+вывод | ✅/[УТОЧНИТЬ] |
| ПТ/ФТ | LLM-вывод | вывод | ⚠️ проверить |
| НФТ (нагрузка/SLA) | architecture.md + LLM | вывод | ⚠️ /bft-index (перестроить индекс) |
| Negative flows | LLM-вывод | вывод | ⚠️ /bft-index (перестроить индекс) |
| Риски/Compliance | regulatory.md + LLM | факт+вывод | ✅/[УТОЧНИТЬ] |
| Зависимости | architecture.md + LLM | вывод | ⚠️ проверить |
| Дочерние задачи | — | не собрано | ➡️ /bft-index (расширить охват трекера) |

### Этап 5: Сборка pack

Собери `.bft/documentation/<epic>/artefacts/bft-context-pack.md`:

1. **Шапка:** epic, jira_key, дата, покрытие индекса (из `MANIFEST.md`).
2. **Выдержки из индекса** (architecture/domain-rules/decisions/regulatory/glossary/stakeholders) — только релевантное.
3. **JIRA-факты** — что взято из эпика.
4. **LLM-синтез** (блоки A–F) с явными пометками факт / вывод LLM.
5. **Матрица покрытия**.
6. **Требует уточнения** — сводный список всех `[УТОЧНИТЬ]`.
7. **Рекомендация:** если >3 блоков помечены `⚠️ вывод LLM` в критичных разделах (НФТ, Negative flows, Зависимости) или в `MANIFEST.md` много `UNAVAILABLE` по релевантным источникам → предложи перезапустить `/bft-index` перед `/bft-problem`.

### Этап 6: Отчёт

```
Контекст-пак собран: .bft/documentation/<epic>/artefacts/bft-context-pack.md

Источники: .bft/index/ (architecture/domain-rules/decisions/regulatory/glossary/stakeholders) + JIRA basic.
Факты: <X> из JIRA/индекса.
Выводы LLM (требуют проверки): <Y> блоков.
Открытые вопросы: <Z> [УТОЧНИТЬ].

<если индекс неполон или много выводов LLM>
⚠️ Рекомендую: перезапусти /bft-index для полного покрытия перед /bft-problem.
</если>

── СТОП ── PO/СА: проверьте pack, особенно блоки ⚠️ (вывод LLM).
Дальше:
• /bft-index                          ← перестроить/дополнить индекс (если неполон)
• /bft-problem <epic_code>            ← диагноз As-Is/Gap (если контекста достаточно)
```

## Жёсткие правила

1. **Явная метка покрытия.** Pack ссылается на `MANIFEST.md` — читатель видит, где вывод LLM, а где индекс неполон.
2. **Факт vs вывод** — всегда разделять. Не смешивать.
3. **Нет выдумок.** Вывод LLM ≠ факт. Вывод помечается явно.
4. **JIRA — только эпик.** Без дочерних задач и поиска по Confluence.
5. **Честно про недоступность** — VPN/MCP проблемы и `UNAVAILABLE` в `MANIFEST.md` помечать явно.
6. **Стиль pack** — по `skills/bft-writer/resources/writing_style.md`. Pack — это отчёт пайплайна (не БФТ): деловая проза без AI-стоп-слов («позволяет», «обеспечивает», «представляет собой»); эмодзи только семантические (статус источника в матрице покрытия: `✅`/`⚠️`/`➡️`); декоративных эмодзи в шапке режима не ставить — режим текстом.
