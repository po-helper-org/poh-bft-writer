## Использование

```
/bft-deliver <epic_code> [bft_space] [bft_parent_id] [project]
```

**Параметры:**
- `<epic_code>` — короткий код БФТ (напр. `EPIC-10`, `EPIC-FAQ`). По нему находится документ БФТ в папке эпика: `<docs_path>/<epic_code>/<epic_code>.md`, где `docs_path` — ключ из `bft-config.md` (дефолт `.bft/documentation`). Для документа v2 `epic_code` — **то же значение, что `epic_slug`** во frontmatter. Доставляется **один** документ, и он же определяет публикуемый вариант: сначала ищется финальный `<docs_path>/<epic_slug>/<epic_slug>.md` (владелец `/bft-deep`, `stage: deep`); его нет — берётся `<epic_slug>-fast.md` (владелец `/bft-fast`, `stage: fast`, шапка как краткое описание запроса) и требуется отдельное подтверждение PO (Этап 1 п.5). Deep читает fast-файл как seed и не перезаписывает его (`../skills/bft-fast/resources/document_assembly.md` §«Путь файла»). Нет ни одного из двух → доставлять нечего.
- `[bft_space]` — Confluence space для публикации БФТ команды API-слой. **Дефолт — `wiki_space` из `bft-config.md`.**
- `[bft_parent_id]` — parent page для БФТ-страницы (опц.). Если не задан → `[УТОЧНИТЬ у PO]`.
- `[project]` — JIRA-проект для создания Эпика. **Дефолт — первый проект из `tracker_projects` (`bft-config.md`).**

## Примеры

```
/bft-deliver EPIC-10
/bft-deliver EPIC-10 {wiki_space} {bft_parent_page_id}
/bft-deliver EPIC-FAQ {wiki_space} {bft_parent_page_id} PROJ2
```

## Важно

**Роль: Deliverer.** Финальная стадия pipeline: v2 — после `/bft-deep`; v1 — после `/bft-validate` (итог 🟢/🟡). Берёт **валидный** документ БФТ и публикует 3 артефакта: JIRA Эпик + **одну** страницу Confluence + связи между ними.

**Одна страница на эпик (ЗМ-031).** Краткое описание и полный БФТ — две стадии одного документа, а не два документа. Публикуется ровно одна страница, выбор по `stage` во frontmatter:

| Что готово | Что публикуется |
|---|---|
| только шапка (`stage: fast`) | шапка — она и есть краткое описание запроса |
| полный БФТ (`stage: deep`) | полный документ; отдельная краткая страница не создаётся |
| краткая опубликована раньше, теперь готов полный | полный документ; старая краткая страница **перенаправляется** на него (Шаг 3), а не остаётся с устаревшим содержимым |

Две страницы на один эпик — дубль контента: читатель видит две пересекающиеся версии и не знает, какая актуальна.

> Аналог sa-helper: нет прямого; это финал публикации после `/validate-doc`.

**Анти-правило (приоритет):** JIRA и Confluence — **только чтение до явного «ок» PO**. Поэтому команда работает в 2 такта:
1. **Сухой прогон** — собирает preview всех артефактов БЕЗ записи, выводит STOP.
2. После «ок» PO — **выполняет шаги подряд**, захватывая ID каждого артефакта для связывания.

**Принципы:**
- Источник содержимого — **только валидный документ БФТ** из папки эпика. Не выдумывай факты заново.
- **Повторный прогон безопасен (идемпотентность).** Повтор `/bft-deliver` — штатная ситуация (упал шаг 4, поправили ссылку, отгружаем заново). Перед записью каждый артефакт резолвит режим по сохранённым id: Эпик — `jira` во frontmatter документа; страница БФТ — `pageId` во frontmatter; ранее опубликованная краткая страница — `summary_pageId` + `summary_state` в манифесте `<docs_path>/<epic_code>/artefacts/delivery.md`; связи — по уже существующим remote links Эпика. Найден id → переиспользовать/обновить, не создавать. `summary_state: superseded` означает, что краткая страница уже перенаправлена — второй раз её не трогать.
- **Родитель единственной страницы:** `bft_parent_id` из аргумента; не задан → `{bft_parent_page_id}` из `bft-config.md`; нет ни того ни другого → `[УТОЧНИТЬ у PO]`, СТОП. Отдельного родителя под краткую страницу больше нет — публикуется одна страница.
- Каждый шаг захватывает ID (epicKey, pageId) → передаёт на шаг связывания. **Последовательно, не параллельно.**
- VPN/Confluence/JIRA недоступны → честно `[УТОЧНИТЬ: MCP недоступен]`, не эмулировать успех.
- **Ссылки Jira/Confluence → макросы Confluence (ЗМ-009).** На публикуемых страницах каждое упоминание Jira/Confluence отдаётся макросом для быстрого доступа и превью, а не голой markdown-ссылкой (см. «Конвертация ссылок в макросы» ниже). Ссылка ведёт только на **существующую** страницу; несуществующее (эпик ещё не создан) не превращать в битую ссылку.

## Инструкция для ЛLM

### ТАКТ 1. СУХОЙ ПРОГОН (без записи)

#### Этап 1: Загрузка входов
1. **Резолв конфига.** Из `bft-config.md`: `docs_path` (дефолт `.bft/documentation`), `wiki_space`, `bft_parent_page_id`, `tracker_projects`, `plantuml_render`. Папка эпика — `<docs_path>/<epic_code>/`, артефакты — `<docs_path>/<epic_code>/artefacts/`. Путь нигде не хардкодить: `docs_path` резолвится один раз здесь и подставляется во все дальнейшие пути.
2. **Найди публикуемый документ — ровно один, по приоритету.** `<docs_path>/<epic_code>/<epic_code>.md` (полный БФТ, `stage: deep`); его нет → `<docs_path>/<epic_code>/<epic_code>-fast.md` (шапка, `stage: fast`). Найденный файл и есть публикуемый вариант; второй в публикацию не идёт даже когда лежит рядом — полный документ покрывает содержание шапки (ЗМ-031). Нет ни одного → СТОП:
   ```
   🔴 Документ БФТ <epic_code> не найден: ни <epic_code>.md, ни <epic_code>-fast.md в <docs_path>/<epic_code>/.
   → /bft-fast <источник> <epic_code>, затем /bft-deep <epic_code>.
   ```
3. **Прочитай frontmatter документа:** `source`, `space`, `pageId`, `version`, `synced`, `jira`, `status`, `epic_slug`, `stage`, `pin_commit`. Значения `jira`, `pageId`, `stage` задают режимы артефактов (Этап 2). `epic_slug` должен совпадать с `<epic_code>`; расходится → отгружай по `epic_slug` из документа и скажи об этом в STOP-отчёте.
4. **Прочитай манифест прошлой отгрузки** `<docs_path>/<epic_code>/artefacts/delivery.md`, если он есть. Он — durable-хранилище того, что уже опубликовано: ключи `jira`, `bft_pageId`, `published_variant`, `summary_pageId`, `summary_state` в его frontmatter (формат — Этап 5). `summary_pageId` — краткая страница **прошлых версий команды**, когда их публиковалось две; новые прогоны её не создают. Отдельный frontmatter-ключ в документе БФТ под неё не вводится: контракт документа — ровно 10 ключей (`../skills/bft-fast/resources/document_assembly.md` §Frontmatter). Манифеста нет → прошлых публикаций не было, режим CREATE.
5. **Гейт валидации.**
   - Есть `artefacts/validation.md` и в нём 🔴 в Hard Gates → СТОП, отгрузка запрещена:
     ```
     🔴 БФТ <epic_code> не прошёл валидацию (есть 🔴 в Hard Gates).
     → v2: /bft-deep <epic_code> (доработать), v1: /bft-draft <epic_code>, затем /bft-validate.
     ```
   - **Нет `artefacts/validation.md` ИЛИ `stage: fast` во frontmatter** → это документ-шапка после `/bft-fast`, а не валидированный БФТ (в v2 `validation.md` появляется только после `/bft-deep`). Не СТОП-запрет, но и не штатный ход: вынеси предупреждение в STOP-отчёт (Этап 3) и потребуй **отдельного явного подтверждения PO** — сверх общего «ок» — строкой «отгружаю шапку без глубокой проработки». Нет обоих подтверждений → не публиковать. Нормальный следующий шаг предлагай первым: `/bft-deep <epic_code>`.
6. Прочитай `context_map.md` и `artefacts/validation.md`, если они есть, — для описания эпика и STOP-отчёта.
7. Зафиксируй параметры: `epic_code`, `bft_space` (дефолт = `wiki_space` из `bft-config.md`), `bft_parent_id`, `project` (дефолт = первый проект из `tracker_projects` в `bft-config.md`).
8. **Проверка ссылок (ЗМ-009).** Собери все упоминания Jira/Confluence из документа. Где MCP доступен — подтверди существование каждой: Jira-ключ → `jira_get_issue`; Confluence pageId → `confluence_get_page`. Несуществующее/невалидное **не публиковать ссылкой** — понизь до `[УТОЧНИТЬ]` или пометки без URL и вынеси в STOP-отчёт. Ссылки только на существующие страницы.

#### Этап 2: Сборка preview артефактов

**Сначала — выбор публикуемого варианта (ЗМ-031).** По `stage` из frontmatter:
- `stage: deep` → публикуется **полный документ**, `published_variant: deep`.
- `stage: fast` → публикуется **шапка** (она и есть краткое описание запроса), `published_variant: fast`.

Вариант всегда один. Отдельная страница-выжимка не собирается ни в одном из случаев: на `fast` шапка уже является кратким описанием, на `deep` полный документ её содержание покрывает.

**Превью 1 — JIRA Эпик** (project=`<project>`):
- `summary`: название БФТ (из H1 черновика, без префикса `[БФТ]`).
- `issue_type`: `Epic`. Если тип в проекте называется иначе → пометь `[УТОЧНИТЬ: issue_type Epic в <project>]`.
- `description`: из блока `Цель` шапки + ключевые БТ + ссылка на страницу БФТ (placeholder, ссылку подставишь на шаге связывания). Markdown.
- `labels`: `bft`, `epic_code`.
- Доп. поля: priority/assignee только если явно есть в черновике, иначе не выдумывать.

**Превью 2 — Единственная страница БФТ** (space=`<bft_space>`, parent=`<bft_parent_id>`, при пустом — `{bft_parent_page_id}`):
- **Сначала прочитать `pageId`/`source` из frontmatter документа.** Есть `pageId` (не `pending`) → режим **UPDATE**: страница уже создана раньше, публикуем в неё, **новую не создаём**. Нет `pageId` или `pending` → режим **CREATE**. Режим показать в сухом прогоне явной строкой: `режим: UPDATE pageId=<id>` или `режим: CREATE (страница ещё не создана)`.
- `title`: `[БФТ] <epic_code>: <Название>` (как H1 черновика). Заголовок один и тот же на обеих стадиях: при переходе `fast → deep` страница обновляется, а не заводится заново, поэтому «— краткое описание запроса» в заголовок не выносится.
- `body`: **полное содержимое** файла публикуемого варианта (frontmatter убери, остальное 1:1 — PlantUML-блоки сохраняй как есть).
- Ни `bft_parent_id`, ни `{bft_parent_page_id}` не заданы → пометь `[УТОЧНИТЬ у PO: parent page для БФТ в space <bft_space>]`, СТОП.
- `content_format`: markdown.

**Превью 3 — Судьба ранее опубликованной краткой страницы** (только если в манифесте есть `summary_pageId` и `summary_state` ≠ `superseded`):
- Эту страницу завели прошлые версии команды, когда публиковалось две. Удалять её нельзя: на неё уже могут вести ссылки снаружи, а удаление их порвёт.
- Собери превью **замены тела** на указатель: заголовок и одна строка «Актуальная версия — полный БФТ: <ссылка на страницу из Превью 2>». Ничего больше: устаревшая выжимка снимается целиком.
- Также покажи, что remote link Эпика будет перецелен с этой страницы на страницу БФТ.
- Публикуемый вариант — `fast` → блок не собирается: краткая страница и есть актуальная, перенаправлять не на что.

**Превью 4 — План связей** (связать всё с JIRA Эпиком):
- Remote link: `epicKey` ↔ `pageId` страницы БФТ. Один линк на эпик.
- Есть перенаправляемая краткая страница → её remote link снимается (`jira_remove_remote_issue_link` либо, где метод недоступен, помечается в отчёте как требующий ручного снятия — не оставлять две ссылки молча).
- В текст страницы БФТ подставить `epicKey` (зависит от шага 1).

▸ АРТЕФАКТ 1 — JIRA Эпик (<project>)
   summary: ...

▸ АРТЕФАКТ 2 — Страница БФТ, единственная (space <bft_space>, parent <bft_parent_id|{bft_parent_page_id}>)

### Конвертация ссылок в макросы Confluence (ЗМ-009)

Публикуемые страницы (Шаги 2–3) отдают Jira/Confluence-упоминания **макросами**, чтобы PO из документа сразу видел превью и статус.

**Инструмент:** `python3 <skills_path>/bft-writer/scripts/bft-confluence-macros.py <epic>.md --confluence-map <map.json> --format storage|wiki -o <converted>.txt`. `<map.json>` — `{"<pageId>": {"title": "...", "space": "SPACE"}}`, собери сам через `confluence_get_page` для каждого pageId из Этапа 1.5 (скрипт Confluence не читает, только подставляет уже известные title/space). Jira-ссылкам map не нужен — ключ уже в URL. Прогони на всём теле документа перед публикацией — это и есть шаг «конвертируй все упоминания» ниже, а не ручная правка построчно. pageId без записи в map (или без `title` в записи) скрипт не трогает — соответствующая ссылка остаётся исходной markdown-ссылкой (в любом `--format`, storage или wiki), не превращается в битый/наполовину-макрос; предупреждение об этом идёт в stderr — не тратить время на map для ссылок, которые не обязательно превращать в макрос.

Если скрипт недоступен/нет времени на map — делай вручную по тем же правилам:
- **`storage`** — макросы как XHTML (надёжно для Jira-макроса).
  - Jira: `[JIRA GDSLV-1610](…)` → `<ac:structured-macro ac:name="jira"><ac:parameter ac:name="key">GDSLV-1610</ac:parameter></ac:structured-macro>`
  - Confluence-страница: → `<ac:link><ri:page ri:content-title="<Заголовок>"/></ac:link>` (или макрос `include`/`excerpt-include` для превью содержимого).
- **`wiki`** — легче совмещать макросы с таблицами/текстом:
  - Jira: `{jira:key=GDSLV-1610}` · Confluence: `[<Заголовок страницы>]` или `{include:<Space>:<Заголовок>}`.

HTML-разметки в ячейках таблиц нет и при публикации не появляется (ЗМ-021): ячейка — одна короткая формулировка. Списком её не верстать ни тегами `<ul><li>`, ни глифом `•` — если содержимое просится в список, формулировка слишком длинная.

Правила: конвертируй **все** упоминания (блоки шапки «Общая информация» и «Документация» / Связанные требования / Якоря истины / текст). Только существующие страницы (проверены в Этапе 1.5). Если полная конвертация тела в storage/wiki рискованна — как минимум оформи макросами ключевые ссылки: Эпик в блоке «Общая информация», «Якоря истины», блок «Документация», «Связанные требования»; остальное — валидными markdown-ссылками на существующие страницы. В сухом прогоне покажи, каким форматом и макросами публикуешь.

**Пре-флайт.** Перед публикацией (в конце Этапа 2 сухого прогона) прогони `python3 <skills_path>/bft-writer/scripts/bft-deliver-check.py <epic>.md` — он считает, сколько голых Jira/Confluence-ссылок и сырых ` ```plantuml ` блоков всё ещё не сконвертировано, и печатает список. Ненулевой результат покажи в STOP-отчёте (Этап 3, блок «ССЫЛКИ»/«ДИАГРАММЫ») — не публикуй, зная, что конвертация не выполнена, если PO явно не попросил ускоренный прогон без неё.

### ТАКТ 2. ЗАПИСЬ (только после явного «ок» PO)

Выполняй **последовательно**, захватывая ID каждого шага.

#### Шаг 1: Создать JIRA Эпик
- `jira_create_issue(project_key=<project>, summary=..., issue_type='Epic', description=..., labels=[...])`.
- Захвати `epicKey` (напр. `PROJ-102`).
- Если `issue_type='Epic'` отвергнут → СТОП, спроси PO точное имя типа.

#### Шаг 2: Единственная страница БФТ
- Публикуется **один** вариант, выбранный на Этапе 2 (`deep` — полный документ, `fast` — шапка). Второй страницы на этот эпик не создаётся ни при каком раскладе.
- Режим **UPDATE** (`pageId` во frontmatter документа есть и не `pending` — страница уже заведена прошлым прогоном): `confluence_update_page(page_id=<pageId из frontmatter>, title=..., content=<публикуемый вариант>, content_format=<storage|wiki|markdown>)`. Новую страницу не создавать. Переход `fast → deep` идёт именно сюда: та же страница, обновлённое тело.
- Режим **CREATE** (`pageId` нет или `pending`): `confluence_create_page(space_key=<bft_space>, title=..., content=<публикуемый вариант>, parent_id=<bft_parent_id, при пустом — {bft_parent_page_id}>, content_format=<storage|wiki|markdown>)`, затем записать полученный `pageId` и URL обратно во frontmatter документа (`pageId`, `source`).
- Если parent недоступен/нет прав → СТОП, доложи.
- **Если в БФТ есть блоки ` ```plantuml ` и режим `image`** — вызов (UPDATE или CREATE) выполняется по правилам ЗМ-015 п.2 ниже: `content_format=storage`, а на месте диаграмм в теле идут плейсхолдеры (картинки подставятся на п.4). Отдельного второго создания страницы нет; в режиме UPDATE вложения грузятся на ту же существующую страницу.
- Jira/Confluence-упоминания → макросами (см. «Конвертация ссылок в макросы»); `epicKey` (из шага 1) — Jira-макросом. Ссылки только на существующие страницы.
- **PlantUML → отрендеренная картинка-вложение (ЗМ-015).** Блок ` ```plantuml … ``` ` НЕ публикуется кодом и НЕ полагается на плагин. По умолчанию (`plantuml_render: image` из `bft-config.md`) диаграмма пре-рендерится в PNG и встраивается вложением — рендерится в любом Confluence/JIRA, без плагина. Порядок строгий: **вложение можно загрузить только на уже существующую страницу**, поэтому сначала создаём страницу, потом грузим PNG, потом подставляем картинку в тело.
  1. **Рендер.** `python3 <skills_path>/bft-writer/scripts/bft-render-plantuml.py <epic>.md --out-dir <tmp>/diagrams/` — находит все ` ```plantuml ` блоки, рендерит каждый в PNG (пробует `plantuml` CLI, затем `docker run plantuml/plantuml`, в этом порядке), печатает в stdout тело документа с плейсхолдерами `[[PLANTUML-<N>]]` на месте диаграмм и манифест `N → путь к PNG` в stderr; код возврата ненулевой, если хоть один блок не отрендерился.
     - Ни `plantuml`, ни `docker` не найдены (или конкретный рендер упал) → скрипт сам пишет `[УТОЧНИТЬ: нет рендерера PlantUML]` для этого блока в манифест — **не публиковать кодом молча**, вынести это в STOP-отчёт. Такой блок в stdout остаётся исходным ` ```plantuml ` (плейсхолдером заменяются только реально отрендеренные диаграммы) — исходник не теряется даже при частичном сбое рендера.
     - Ручной fallback (скрипт недоступен): вынь тело `@startuml … @enduml` в файл `diagram-<N>.puml` и `plantuml -tpng diagram-<N>.puml`, либо `docker run --rm -v "$PWD:/w" plantuml/plantuml -tpng /w/diagram-<N>.puml`, либо POST в PlantUML-server.
  2. **Создание страницы.** Тот же `confluence_create_page` из начала Шага 3, но `content_format=storage` (обязательно для `<ac:image>`) и на месте каждой диаграммы — плейсхолдер `[[PLANTUML-<N>]]`. Захвати `pageId`.
  3. **Загрузка вложений.** На полученный `pageId` загрузи каждый PNG: `confluence_upload_attachment(content_id=<pageId>, file_path="diagram-<N>.png")`. MCP-аплоад недоступен/сломан → fallback: прямой Confluence REST изнутри окружения. Токен брать из переменной окружения, наружу не выносить и в лог не печатать:

     ```
     curl -sS -X POST \
       -H "Authorization: Bearer $CONFLUENCE_TOKEN" \
       -H "X-Atlassian-Token: nocheck" \
       -F "file=@diagram-<N>.png" \
       "$CONFLUENCE_BASE/rest/api/content/<pageId>/child/attachment"
     ```

     - `X-Atlassian-Token: nocheck` **обязателен** — без него multipart-загрузка отдаётся 403.
     - `$CONFLUENCE_BASE`: Server/DC (напр. `https://confluence.mts.ru`) → путь `/rest/api/…` как выше. Confluence **Cloud** → база с суффиксом `/wiki`, т.е. `/wiki/rest/api/…`.
     - Ответ содержит `results[0].title` — это имя вложения для `ri:filename` на п.4.
  4. **Замена в теле.** `confluence_update_page`: замени каждый `[[PLANTUML-<N>]]` на `<ac:image ac:align="center"><ri:attachment ri:filename="<имя вложения из ответа п.3>"/></ac:image>`. Имя бери **из ответа загрузки** (REST — `results[0].title`; MCP — поле имени вложения), не подставляй `diagram-<N>.png` вслепую: Confluence может нормализовать имя файла, и тогда картинка не найдётся.
- **Опционально — макрос «PlantUML»** (только `plantuml_render: macro` И плагин подтверждён в целевом пространстве): storage `<ac:structured-macro ac:name="plantuml"><ac:plain-text-body><![CDATA[@startuml … @enduml]]></ac:plain-text-body></ac:structured-macro>`, wiki `{plantuml}@startuml … @enduml{plantuml}`. `plantuml_render: auto` — по умолчанию картинка (п.1–4); макрос только если плагин **подтверждён явно**: PO подтвердил в сухом прогоне (режим показан в STOP-отчёте) либо в `bft-config.md` у ключа `plantuml_render` прямо указано, что плагин установлен. Плагин не подтверждён — **не гадать и не проверять эвристикой**, публиковать картинкой. Голый блок кода как финал недопустим ни при каком режиме.
- **Спойлер «Подробный контекст»** в «Бизнес описании» → макрос Expand (storage: `<ac:structured-macro ac:name="expand">`; wiki: `{expand}`), сохраняя свёрнутость.
- Захвати `pageId_БФТ`.

#### Шаг 3: Перенаправить ранее опубликованную краткую страницу
Выполняется **только** если в манифесте есть `summary_pageId`, его `summary_state` ≠ `superseded`, и публикуемый вариант — `deep`. Иначе шаг пропускается целиком.

- `confluence_update_page(page_id=<summary_pageId>, title=<прежний заголовок>, content=<указатель>, content_format=<storage|wiki|markdown>)`. Тело — одна строка со ссылкой на страницу БФТ из Шага 2, Confluence-ссылка макросом. Устаревшая выжимка снимается целиком: две версии одного содержания и есть та проблема, ради которой вводилось правило одной страницы.
- **Страницу не удалять.** На неё могут вести ссылки снаружи (JIRA, переписка, соседние страницы); удаление их порвёт, а указатель — нет. Удаление возможно только по отдельной явной просьбе PO.
- Запиши в манифест `summary_state: superseded` — повторный прогон эту страницу больше не трогает.
- MCP недоступен или прав на страницу нет → не эмулировать успех: `[УТОЧНИТЬ: краткая страница <id> не перенаправлена]` в отчёт, `summary_state` не менять.

#### Шаг 4: Связать документы с JIRA Эпиком
- `jira_create_remote_issue_link(issue_key=<epicKey>, url=<Confluence URL страницы БФТ>, title='БФТ <epic_code>')` — **один** линк на эпик.
- Есть перенаправлённая краткая страница со своим remote link → снять его (`jira_remove_remote_issue_link` или эквивалент). Метод недоступен → вынести в отчёт строкой «снять вручную: <URL>», не оставлять две ссылки молча.
- Опционально: добавить комментарий на Эпик со ссылкой на страницу БФТ (`jira_add_comment`).

#### Этап 5: Манифест отгрузки + отчёт
- Сохрани `<docs_path>/<epic_code>/artefacts/delivery.md`. Frontmatter — машиночитаемое состояние отгрузки, тело — читаемый отчёт:
  ```
  ---
  jira: <epicKey>
  bft_pageId: <id>
  published_variant: <deep|fast>
  summary_pageId: <id ранее опубликованной краткой страницы; нет такой — не заводить ключ>
  summary_state: <superseded — тело заменено указателем | pending — перенаправить не удалось>
  ---

  # Отгрузка БФТ <epic_code>
  - Дата: ...
  - JIRA Эпик: <epicKey> — <URL>
  - Страница БФТ (Confluence): pageId <id> — <URL>  (space <bft_space>, parent <bft_parent_id|{bft_parent_page_id}>)
  - Опубликованный вариант: <полный БФТ (deep) | шапка как краткое описание (fast)>
  - Краткая страница прошлых прогонов: <pageId <id> — перенаправлена на страницу БФТ | не было>
  - Связи: epicKey ↔ страница БФТ
  ```
  `published_variant` — то поле, по которому повторный прогон понимает, что уже опубликовано, и не заводит вторую страницу при переходе `fast → deep`.
- Финальный вывод:
  ```
  ✅ БФТ <epic_code> отгружен. Опубликована одна страница (<deep|fast>).
  Эпик: <epicKey> — <URL>
  Страница БФТ: <URL>
  Краткая страница прошлых прогонов: <перенаправлена на страницу БФТ | не было>
  Связи проставлены. Манифест: <docs_path>/<epic_code>/artefacts/delivery.md
  ```

## Запреты

1. **Не публикуй без явного «ок» PO** — сухой прогон обязателен, запись только во 2-м такте.
2. **Не публикуй при 🔴 в validation.md** — сначала `/bft-draft` + `/bft-validate`.
3. **Не выдумывай факты** в описаниях — только из черновика БФТ / problem / concept. Незакрытое → `[УТОЧНИТЬ]`.
4. **Не хардкодь `epicKey` / pageId** — они неизвестны до выполнения шагов 1-3.
5. **Не выполняй шаги параллельно** — шаг 4 зависит от ID шагов 1-3.
6. **Не эмулируй успех** при недоступности MCP (VPN) — честно `[УТОЧНИТЬ]`.
7. **Не подставляй секреты/токены** в описания; `.mcp.json` вне git.
8. **Не публикуй битые/выдуманные ссылки** (ЗМ-009) — только существующие страницы, подтверждённые в Этапе 1.5; Jira/Confluence — макросами для превью, не голым текстом.
9. **Не создавай дубль страницы БФТ.** Есть `pageId` во frontmatter — обновляй её. Вторая страница того же БФТ — ошибка отгрузки.
10. **Не публикуй две страницы на один эпик (ЗМ-031).** Краткое описание и полный БФТ — стадии одного документа. Готов полный — публикуется он, отдельная страница-выжимка не создаётся; краткая страница прошлых прогонов перенаправляется на полный, а не остаётся с устаревшим содержанием.
11. **Не удаляй краткую страницу при перенаправлении.** На неё могут вести внешние ссылки. Тело заменяется указателем; удаление — только по отдельной явной просьбе PO.
