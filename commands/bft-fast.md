## Использование

```
/bft-fast <источник> [epic_slug] [--no-deep]
```

**Параметры:**
- `<источник>` — путь к `#summary`-заметке, путь к файлу транскрипта или инлайн-текст. Пусто → команда просит указать.
- `[epic_slug]` — опц., имя эпика: определяет путь документа (`<docs_path>/<epic_slug>/<epic_slug>-fast.md`) и файла-копии письма; не задан → slug из главной темы Summary (`{ГГГГ-ММ-ДД}-{slug}`).
- `--no-deep` — не форкать фоновую deep-проработку (по умолчанию форкается, этап 8). Документ и открытое поле собираются в любом случае — глубину можно догнать вручную.

Вложение — два csv-файла (`personas.csv` + `requirements.csv`) — пишется **всегда** (не флаг), см. `resources/requirements_table.md`.

## Примеры

```
/bft-fast summaries/2026-07-03-direct-faq.md
/bft-fast skills/bft-fast/examples/golden_summary.md
/bft-fast "сырой транскрипт встречи ..." direct-faq
```

## Важно

**Роль: стенографист.** Результат — **одно письмо в чат**, пересылаемое коллегам как есть, плюс два csv-вложения и локальный документ БФТ (шапка + открытое поле). Не полный БФТ канон-структуры MTS.

**Периметр: наружу не ходить.** Ни JIRA, ни Confluence, ни git, ни индекс воркспейса `.bft/index/`. Единственный источник — текст, который дал PO. Задача — не исследовать, а точно зафиксировать сказанное в правильной форме; пробел становится открытым вопросом, а не догадкой. Исследование, поиск смежных артефактов, проверка противоречий и edge-кейсы — работа `/bft-deep`, который приходит следующим и аудирует этот результат.

**Модель.** Проход рассчитан на Haiku (`model: haiku` в шапке команды): вся работа — раскладка сказанного по формам, без рассуждений и внешних запросов.

**Глубина — два комплементарных пути.** По умолчанию фоновый `/bft-deep` форкается автоматически (этап 8, `--no-deep` отключает) и обогащает документ под шапкой. Независимо от форка в документе остаётся **открытое поле** (`resources/open_field.md`) — самодостаточный промт: если форк отключён, упал или про задачу забыли, любой PO копирует его в свою сессию Claude Code и доводит БФТ до финала.

**Анти-правило:** ничего не выдумывать. Факт без источника в Summary → «Открытый вопрос», не утверждение.

## Инструкция для LLM

### ФОРМАТ ВЫВОДА — копируй структуру точно

Письмо — фиксированный порядок блоков, до пяти: `Цель` → `How to demo` → `Открытые вопросы` → `Границы` → `Документация`. Последний блок условный: нет источников — блока в письме нет, порядок остальных не меняется. Вложение — два csv-файла (`personas.csv` + `requirements.csv`), всегда, на диск (не в теле письма).

```
Цель: <драйвер/контекст: для эпика X, почему — закон/бизнес/требование>. <что делаем, одно предложение>. (WHY вперёд)

How to demo:
1. <шаг от лица роли-приёмщика; дизамбигуация «X, не Y» в скобках, если сказана; без внутренних US#N/story-ид>
2. …

Открытые вопросы:
* <вопрос / блокер / решение — одна развилка на строку> (<владелец или «кто уточнит, срок» — если есть>)
* …
(плоский список; строка = вопрос/блокер/решение/зависимость; владелец опционален, в скобках; БЕЗ обязательного префикса `ФИО —`, БЕЗ заголовков-групп `ФИО:`, БЕЗ чекбоксов `- [ ]`)

Границы:
* <in-scope> (<out-of-scope> — не входят в зону БФТ)
* Дополнительно, если возможно: <nice-to-have, если было>
* <операционные заметки: сроки/эффекты — по одной на пункт>

Документация:
* <указатель одной строкой, или [подпись](URL) где URL известен>
* …
(блок условный: источников нет — блока в письме нет)

────────────────────────────────────────
Вложение — два csv-файла (ВСЕГДА, на диск, не в тело письма). Разделитель — запятая, UTF-8 с BOM, кавычки RFC-4180 (ячейка с `,`/`"`/переносом — в кавычках, внутренние `"` удвоены).

personas.csv — контекст о стейкхолдерах:
ФИО,Роль,Влияние

requirements.csv — их требования (порядок строк БТ→ПТ→ИТ→ФТ→НФТ):
ID,ASIS (сейчас),TOBE (после),Связанные,Источник (цитата)
```

После вложения — документ БФТ: скелет (frontmatter, H1, строка-статус, шапка, строка-граница, открытое поле) собирается точно по `resources/document_assembly.md` и `resources/open_field.md`, шаблон здесь не дублируется — эталон целиком в `examples/golden_document.md`. Сохраняется в `<docs_path>/<epic_slug>/<epic_slug>-fast.md` — отдельный файл стадии fast; `/bft-deep` его не перезаписывает, а пишет свой `<epic_slug>.md` (`document_assembly.md` §«Путь файла»).

### СТОП-ГАЛЛЮЦИНАЦИИ — на брифинге критично, не додумывать

- **Влияние/роль не сказаны на встрече → `[не указано]` / `[роль не подтверждена]`.** НЕ писать общую должность («Product», «Engineering», «QA») по догадке — «Влияние» это вклад в ЭТОТ БФТ (что решает/за что отвечает), не позиция в оргструктуре.
- **Технологии/алгоритмы (BM25, TF-IDF, типы кухни, фильтры), которых НЕ было в репликах → НЕ добавлять.** Вопрос заводится, только если сам участник его поднял.
- **Примеры и golden-фикстуры — образец ФОРМЫ, не источник фактов (ЗМ-024).** В `examples/` лежат письма и документы других эпиков (Direct FAQ, MRS, площадки). Из них берётся структура блоков и регистр речи — и ни одной сущности, персоны, границы или ограничения. Факт, которого нет во входном тексте PO, но который есть в примере, — галлюцинация того же класса, что выдуманный департамент.
- **Таймстемпы НЕ цитировать.** Колонка «Источник» = текст реплики: `ФИО: «дословно»`.
- **ASIS не проговорён → `[ASIS не озвучен]`.** НЕ реконструировать «как оно наверное сейчас».
- **out-of-scope (следующий квартал / «не делаем») → только в «Границы».** НЕ в How to demo, НЕ в таблицу требований.
- **Блок «Цель» обязателен, WHY вперёд** (драйвер/эпик впереди механизма). Вопросы — строка = вопрос/блокер/решение; владелец опционален в скобках (не обязательный префикс `ФИО —`, не группировать, не чекбоксить).
- **SMART-таблица — блок «Цель» документа целиком (ЗМ-026): в документе под заголовком `### Цель` стоит только таблица, прозаического пояснения нет.** Буква без основания в Summary → `[УТОЧНИТЬ]`; НЕ заполнять A/R общей заглушкой («достижимо силами команды», «важно для бизнеса») — это то же самое, что выдуманный департамент. В письме строка `Цель: …` остаётся как есть.

### САМОПРОВЕРКА ПЕРЕД ВЫВОДОМ (пройди каждый пункт, иначе переделай)

1. Первая строка письма — `Цель: …`, WHY/драйвер вперёд? Если нет — добавь Цель, не начинай с «How to demo». В документе эта строка не повторяется: под `### Цель` стоит только SMART-таблица (ЗМ-026).
2. Блок «Открытые вопросы» — строка = вопрос/блокер/решение/зависимость, владелец опционален в скобках? Нет обязательного префикса `ФИО —`, нет заголовков-групп `ФИО:`, нет `- [ ]`? Если есть — переписать в плоский гибрид-список.
3. В теле письма нет внутренних `US#N`/story-ид? (Ссылка на родительский эпик `GDSLV-1374` как якорь — можно.)
4. Блок «Документация» — только реальные указатели/URL (нет URL → подпись без ссылки, не выдумывать)? Нет источников → блока нет.
5. Вложение — всегда два csv-файла (`personas.csv` + `requirements.csv`) на диск, инлайн-таблицы в чате нет? В чат — только строка-ссылка на файлы.
6. В `personas.csv`: влияние = `[не указано]` там, где не звучало? Влияние — про вклад в этот БФТ, а не должность? Роль не в индексе стейкхолдеров и не названа → `[роль не подтверждена]`? Нет выдуманных «Product/Engineering»?
7. В `requirements.csv`: каждая строка имеет **реальную цитату** в «Источник» (строка с пустым источником — удалить)? «Связанные» — только ID (`БТ-1`, без нулей `БТ-001`), нет связи → пустая ячейка? ASIS без реплики = `[ASIS не озвучен]`? Ячейки с `,`/`"` — в кавычках (RFC-4180)?
8. В «How to demo» нет шагов про следующий квартал/будущие итерации («в Q4 будет…») и нет out-of-scope? Всё это — только в «Границы», не в демо и не в таблице?
9. В вопросах нет выдуманных технологий (BM25, кухни, фильтры), которых не поднимали участники?
9а. Ни одна сущность из golden-примеров (MRS, FAQ для категорий, площадки, персоны Direct и т.п.) не просочилась в письмо, csv или документ, если её нет во входном Summary? Пройди по «Границам» и «How to demo» отдельно — туда чужой контекст попадает чаще всего (ЗМ-024).
10. Документ собран по `document_assembly.md`: frontmatter (10 ключей), H1, строка-статус, шапка без блока «Открытые вопросы», под `Цель:` — SMART-таблица (S/M/A/R/T; буква без основания в Summary → `[УТОЧНИТЬ]`, не заглушка), ровно одна строка-граница `BFT-HEAD-END`, ниже неё только плейсхолдер (раздела «Вводные» нет — вопросы идут в ответ в чат, ЗМ-020)? Ответ в чат — по `letter_format.md` §«Формат ответа в чат»?
11. `python3 skills/bft-writer/scripts/bft-lint.py <файл>` вернул 0? И `bft-style-lint.py <файл>`? И `bft-ground-lint.py <файл> --source <входной Summary> --strict` (гейт 19 — ловит факты из чужих примеров, которых самопроверка не видит)? Любой ненулевой код — переделать, не сохранять.
12. Открытое поле присутствует, и четыре строки блока «КОНТЕКСТ ЭТОГО БФТ» заполнены реальными значениями прогона (`epic_slug`, источник Summary, Confluence-URL или «не опубликовано», `pin_commit`)? Литерал `<путь-к-этому-документу>` в секции «КАК ЗАПУСТИТЬ» — часть промта, его не подставлять.
13. Ни одного обращения наружу за весь прогон — не читались JIRA, Confluence, git, `.bft/index/`; в Confluence ничего не публиковалось; `pageId: pending` и `source: [УТОЧНИТЬ — не опубликовано]` во frontmatter, строка `Confluence: не опубликовано` в промте на месте?
14. Этап 8 отработал по ветке: без `--no-deep` — форк запущен после сохранения файла и выведена штатная финальная строка; с `--no-deep` — форка нет, выведена строка про `--no-deep`? Обе формулировки — дословно из `letter_format.md` §«Канал вывода»?

### Этап 1: Загрузка
1. `skills/bft-fast/SKILL.md` (роль, принципы, этапы, резолв конфига).
2. `skills/bft-fast/resources/`: `extraction_schema.md`, `demo_synthesis.md`, `letter_format.md`, `requirements_table.md`, `document_assembly.md`, `open_field.md`.
3. Голос: `skills/bft-writer/resources/writing_style.md`.
4. Резолв конфига из `bft-config.md` (опц.; нет файла → дефолты ниже, без остановки).

### Этап 2: resolve-source
Определить форму `<источник>` (СТ-2). Транскрипт → внутренняя выжимка до `#summary`. Пусто → спросить путь/текст, не выдумывать. Путь указан, но файл не читается/не найден → сообщить ошибку пути и попросить корректный источник; не эмулировать содержимое.

### Этап 3: extract
Извлечь сущности по `extraction_schema.md`; каждая с source — цитатой из текста PO. Индекс стейкхолдеров и любые внешние справочники НЕ читать: роль не названа → `[роль не подтверждена]`.

### Этап 4: synth
Построить `Цель` (WHY вперёд: драйвер/эпик, затем что делаем, 1-2 строки), `How to demo` (demo_synthesis.md; дизамбигуации «X, не Y» в скобках у шагов; без US#N/story-ид), `Открытые вопросы` (гибрид: вопрос/блокер/решение/зависимость, владелец опционально в скобках; No Silent Skip), `Границы` (in/out + тир «Дополнительно, если возможно» + заметки), `Документация` (только то, что назвал сам PO: продиктован URL → ставится как есть, назван источник без URL → подпись без ссылки, не назван → блока нет; ничего не искать и не проверять на существование).

### Этап 5: assemble + gate
Собрать письмо по `letter_format.md` (порядок блоков фиксирован, `Документация` — условный блок; без обвязки). **Вложение — всегда:** сериализовать в два csv по `requirements_table.md` — `personas.csv` (ФИО/Роль/Влияние) + `requirements.csv` (ID/ASIS/TOBE/Связанные/Источник, порядок БТ→ПТ→ИТ→ФТ→НФТ, каждая строка ← цитата, без обогащения; запятая, UTF-8 BOM, кавычки RFC-4180). Гейт: утверждение письма ← цитата из текста PO или вопрос; URL «Документации» — только продиктованные; строка csv ← непустая цитата; роль/влияние ← сказанное или `[роль не подтверждена]`/`[не указано]`. Проверка периметра: в выходе нет ни одного факта, которого нет во входном тексте.

### Этап 6: emit
Вывести письмо в чат (готовое к пересылке). **Вложение — всегда: записать `personas.csv` + `requirements.csv`** в `.bft/documentation/{epic_slug}/` (`docs_path` из `bft-config.md`, дефолт `.bft/documentation`; нет доступа к папке → рядом с источником, пометка `[УТОЧНИТЬ путь копии]`); опц. копия письма — `letter.md`. В чат — одна строка: «Вложение: …/requirements.csv (N требований), …/personas.csv (M персон)» (без инлайн-таблицы).

Собрать документ БФТ по `document_assembly.md`: frontmatter (10 ключей — состав и порядок см. `document_assembly.md` §Frontmatter, на fast `stage: fast`) + H1 + строка-статус + шапка (`### Цель` — только SMART-таблица, без прозы (ЗМ-026)/`How to demo`/`### Ограничения и договоренности` — из письма, блок «Границы» переименован при переносе; `### Документация` — условный; `### Критичные требования (скелет на цитатах)` — те же строки, что в `personas.csv` + `requirements.csv`: персоны `ФИО | Роль | Влияние` + требования `ID | ASIS | TOBE | Связанные | Источник (цитата)`, на fast блок обязателен, ЗМ-027; `### Общая информация` — карточка проекта, неизвестное `[УТОЧНИТЬ]`) + строка-граница `BFT-HEAD-END` + открытое поле по `open_field.md` (плейсхолдер-заголовок, `<details>`, четыре строки блока «КОНТЕКСТ ЭТОГО БФТ» заполнены реальными значениями этого прогона; `Confluence` здесь — всегда «не опубликовано»: fast не публикует, страницу создаёт `/bft-deliver` после глубокой проработки; литерал `<путь-к-этому-документу>` в «КАК ЗАПУСТИТЬ» остаётся как есть). **Перед сохранением — гейт шаблона (ЗМ-017):** `python3 skills/bft-writer/scripts/bft-lint.py <файл>`. Ненулевой код = документ не по шаблону, исправить и прогнать снова; с ошибками линтера файл не сохраняется. Сохранить в `<docs_path>/<epic_slug>/<epic_slug>-fast.md` (файл стадии fast, `document_assembly.md` §«Путь файла»).

### Этап 7: hand-off (публикации нет)
`/bft-fast` в Confluence не пишет и страницу не создаёт — ни при каком конфиге. `wiki_space`/`bft_parent_page_id` на этой стадии не читаются, MCP-вызовов не делается вовсе. Во frontmatter остаётся `pageId: pending`, `source: [УТОЧНИТЬ — не опубликовано]`, `space: [wiki_space не задан]`; строка `- Confluence: не опубликовано` в промте открытого поля не меняется.

В вывод — путь к сохранённому файлу и следующий шаг: глубокая проработка (`/bft-deep`, форком или вручную), публикация — `/bft-deliver <epic_slug>` уже после неё. Страницу создаёт `/bft-deliver`, он же записывает `pageId`/`source` во frontmatter.

### Этап 8: deep-fork
Запускать после сохранения файла (Этап 6). Публикации, которой раньше нужно было дождаться, на стадии fast больше нет.

Если нет `--no-deep`: по `deep_fork.md` оценить richness контекста и форкнуть фоновый `/bft-deep` (seed = документ Этапа 6; RICH → дополнительно `.bft/index/`). Фон доводит документ до валидированного черновика локально и останавливается — в Confluence не пишет (гейт «сухой прогон → «ок» PO» в фоновом субагенте пройти некому); публикует PO у себя через `/bft-deliver`. Нотификация по завершении — успех или провал, со статусом публикации, никогда молча.

Финал: одна простая строка вне тела письма — обе формулировки (штатная и `--no-deep`) заданы в `letter_format.md` §«Канал вывода», брать дословно оттуда. Без внутренностей пайплайна (swarm/оси/тяжесть).
