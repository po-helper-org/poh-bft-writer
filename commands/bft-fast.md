## Использование

```
/bft-fast <источник> [epic_slug] [--no-deep]
```

**Параметры:**
- `<источник>` — путь к `#summary`-заметке, путь к файлу транскрипта или инлайн-текст. Пусто → команда просит указать.
- `[epic_slug]` — опц., имя эпика: определяет путь документа (`<docs_path>/<epic_slug>/<epic_slug>.md`) и файла-копии письма; не задан → slug из главной темы Summary (`{ГГГГ-ММ-ДД}-{slug}`).
- `--no-deep` — не форкать фоновую deep-проработку (по умолчанию форкается, этап 8). Документ и открытое поле собираются в любом случае — глубину можно догнать вручную.

Вложение — два csv-файла (`personas.csv` + `requirements.csv`) — пишется **всегда** (не флаг), см. `resources/requirements_table.md`.

## Примеры

```
/bft-fast summaries/2026-07-03-direct-faq.md
/bft-fast skills/bft-fast/examples/golden_summary.md
/bft-fast "сырой транскрипт встречи ..." direct-faq
```

## Важно

**Роль: PO-аналитик быстрого прохода.** Результат — **одно письмо в чат**, пересылаемое коллегам как есть, плюс два csv-вложения, документ БФТ (шапка + открытое поле) и Confluence-черновик после «ок» PO. Не полный БФТ канон-структуры MTS.

**Глубина — два комплементарных пути.** По умолчанию фоновый `/bft-deep` форкается автоматически (этап 8, `--no-deep` отключает) и обогащает документ под шапкой. Независимо от форка в документе остаётся **открытое поле** (`resources/open_field.md`) — самодостаточный промт: если форк отключён, упал или про задачу забыли, любой PO копирует его в свою сессию Claude Code и доводит БФТ до финала.

**Анти-правило:** ничего не выдумывать. Факт без источника в Summary → «Открытый вопрос», не утверждение.

## Инструкция для LLM

### ФОРМАТ ВЫВОДА — копируй структуру точно

Письмо — фиксированный порядок блоков, до пяти: `Цель` → `How to demo` → `Открытые вопросы` → `Границы` → `Документация`. Последний блок условный: нет источников — блока в письме нет, порядок остальных не меняется. Вложение — два csv-файла (`personas.csv` + `requirements.csv`), всегда, на диск (не в теле письма).

```
Цель: <драйвер/контекст: для эпика X, почему — закон/бизнес/требование>. <что делаем, одно предложение>. (WHY вперёд)

How to demo:
1. <шаг от лица роли-приёмщика; дизамбигуация «X, не Y» в скобках, если сказана; без внутренних US#N/story-ид>
2. …

Открытые вопросы:
* <вопрос / блокер / решение — одна развилка на строку> (<владелец или «кто уточнит, срок» — если есть>)
* …
(плоский список; строка = вопрос/блокер/решение/зависимость; владелец опционален, в скобках; БЕЗ обязательного префикса `ФИО —`, БЕЗ заголовков-групп `ФИО:`, БЕЗ чекбоксов `- [ ]`)

Границы: <in-scope> (<out-of-scope> — не входят в зону БФТ).
Дополнительно, если возможно: <nice-to-have, если было>.
<операционные заметки: сроки/эффекты>

Документация:
* <указатель одной строкой, или [подпись](URL) где URL известен>
* …
(блок условный: источников нет — блока в письме нет)

────────────────────────────────────────
Вложение — два csv-файла (ВСЕГДА, на диск, не в тело письма). Разделитель — запятая, UTF-8 с BOM, кавычки RFC-4180 (ячейка с `,`/`"`/переносом — в кавычках, внутренние `"` удвоены).

personas.csv — контекст о стейкхолдерах:
ФИО,Роль,Департамент

requirements.csv — их требования (порядок строк БТ→ПТ→ИТ→ФТ→НФТ):
ID,ASIS (сейчас),TOBE (после),Связанные,Источник (цитата)
```

После вложения — документ БФТ: скелет (frontmatter, H1, строка-статус, шапка, строка-граница, открытое поле) собирается точно по `resources/document_assembly.md` и `resources/open_field.md`, шаблон здесь не дублируется — эталон целиком в `examples/golden_document.md`. Сохраняется в `<docs_path>/<epic_slug>/<epic_slug>.md`.

### СТОП-ГАЛЛЮЦИНАЦИИ — на брифинге критично, не додумывать

- **Департамент/роль не сказаны на встрече → `[не указано]` / `[роль не подтверждена]`.** НЕ писать «Product», «Engineering», «QA» из головы.
- **Технологии/алгоритмы (BM25, TF-IDF, типы кухни, фильтры), которых НЕ было в репликах → НЕ добавлять.** Вопрос заводится, только если сам участник его поднял.
- **Таймстемпы НЕ цитировать.** Колонка «Источник» = текст реплики: `ФИО: «дословно»`.
- **ASIS не проговорён → `[ASIS не озвучен]`.** НЕ реконструировать «как оно наверное сейчас».
- **out-of-scope (следующий квартал / «не делаем») → только в «Границы».** НЕ в How to demo, НЕ в таблицу требований.
- **Блок «Цель» обязателен, WHY вперёд** (драйвер/эпик впереди механизма). Вопросы — строка = вопрос/блокер/решение; владелец опционален в скобках (не обязательный префикс `ФИО —`, не группировать, не чекбоксить).

### Этап 1: Загрузка
1. `skills/bft-fast/SKILL.md` (роль, принципы, этапы, резолв конфига).
2. `skills/bft-fast/resources/`: `extraction_schema.md`, `demo_synthesis.md`, `letter_format.md`, `requirements_table.md`, `document_assembly.md`, `open_field.md`.
3. Голос: `skills/bft-writer/resources/writing_style.md`.
4. Резолв конфига из `bft-config.md` (опц.; нет файла → дефолты ниже, без остановки).

### Этап 2: resolve-source
Определить форму `<источник>` (СТ-2). Транскрипт → внутренняя выжимка до `#summary`. Пусто → спросить путь/текст, не выдумывать. Путь указан, но файл не читается/не найден → сообщить ошибку пути и попросить корректный источник; не эмулировать содержимое.

### Этап 3: extract
Извлечь сущности по `extraction_schema.md`; каждая с source; участники сверить с индексом стейкхолдеров.

### Этап 4: synth
Построить `Цель` (WHY вперёд: драйвер/эпик, затем что делаем, 1-2 строки), `How to demo` (demo_synthesis.md; дизамбигуации «X, не Y» в скобках у шагов; без US#N/story-ид), `Открытые вопросы` (гибрид: вопрос/блокер/решение/зависимость, владелец опционально в скобках; No Silent Skip), `Границы` (in/out + тир «Дополнительно, если возможно» + заметки), `Документация` (указатели на источники — Confluence/JIRA/смежные истории; живая ссылка где есть URL, иначе подпись; нет источников → блока нет).

### Этап 5: assemble + gate
Собрать письмо по `letter_format.md` (порядок блоков фиксирован, `Документация` — условный блок; без обвязки). **Вложение — всегда:** сериализовать в два csv по `requirements_table.md` — `personas.csv` (ФИО/Роль/Департамент) + `requirements.csv` (ID/ASIS/TOBE/Связанные/Источник, порядок БТ→ПТ→ИТ→ФТ→НФТ, каждая строка ← цитата, без обогащения; запятая, UTF-8 BOM, кавычки RFC-4180). Гейт: утверждение письма ← source или вопрос; URL «Документации» — только реальные; строка csv ← непустая цитата; роль/департамент ← индекс стейкхолдеров/сказанное или `[не указано]`.

### Этап 6: emit
Вывести письмо в чат (готовое к пересылке). **Вложение — всегда: записать `personas.csv` + `requirements.csv`** в `.bft/documentation/{epic_slug}/` (`docs_path` из `bft-config.md`, дефолт `.bft/documentation`; нет доступа к папке → рядом с источником, пометка `[УТОЧНИТЬ путь копии]`); опц. копия письма — `letter.md`. В чат — одна строка: «Вложение: …/requirements.csv (N требований), …/personas.csv (M персон)» (без инлайн-таблицы).

Собрать документ БФТ по `document_assembly.md`: frontmatter (10 ключей — состав и порядок см. `document_assembly.md` §Frontmatter, на fast `stage: fast`) + H1 + строка-статус + шапка (`Цель`/`How to demo`/`Открытые вопросы`/`Границы`/`Документация` — из письма; «Критичные требования (скелет на цитатах)» — те же строки, что в `requirements.csv` + `personas.csv`) + строка-граница `BFT-HEAD-END` + открытое поле по `open_field.md` (плейсхолдер-заголовок, `<details>`, четыре строки блока «КОНТЕКСТ ЭТОГО БФТ» заполнены реальными значениями этого прогона; `Confluence` здесь — «не опубликовано», Этап 7 перепишет после успешной публикации; литерал `<путь-к-этому-документу>` в «КАК ЗАПУСТИТЬ» остаётся как есть). Сохранить в `<docs_path>/<epic_slug>/<epic_slug>.md`.

### Этап 7: publish
**Ветка конфига — сначала.** `wiki_space` не задан (`bft-config.md` отсутствует или ключ пуст) → публикация ручная: этап пропускается, страница не создаётся, документ остаётся локальным; во frontmatter `space: [wiki_space не задан]`, `pageId: pending`, `source: [УТОЧНИТЬ — не опубликовано]`; в выводе прямо сказать, что публикация не выполнялась и почему. `bft_parent_page_id` не задан → parent спросить у PO в сухом прогоне, не подставлять наугад.

`wiki_space` задан → сухой прогон: собрать превью Confluence-страницы (title = H1 документа; body = содержимое документа, frontmatter не публикуется; space = `wiki_space`, parent = `bft_parent_page_id` из `bft-config.md`; status «Черновик») → вывести превью → СТОП, дождаться явного «ок» PO. Без «ок» — не публиковать.

После «ок»: `confluence_create_page`. Успех → захватить `pageId`; записать `source` (URL страницы), `pageId`, `space` во frontmatter документа **и переписать строку `- Confluence: …` внутри промта открытого поля на реальный URL страницы**; пересохранить файл. Правка промта обязательна: frontmatter в Confluence не публикуется, поэтому без неё опубликованная страница утверждает «не опубликовано», а PO, скопировавший промт в чистую сессию, теряет `pageId`. MCP/VPN недоступен или запись не прошла → `pageId: pending`, `source: [УТОЧНИТЬ — не опубликовано]`, строка `Confluence` в промте остаётся «не опубликовано»; локальный `.md` уже сохранён на Этапе 6 независимо от исхода публикации; успех не эмулировать.

### Этап 8: deep-fork
Запускать только после того, как Этап 7 разрешился: опубликовано, пропущено (`wiki_space` не задан) или упало. Более ранний форк прочитает `pageId: pending` и уйдёт по неверной ветке, а его запись документа столкнётся с пересохранением Этапа 7 (потеря правки).

Если нет `--no-deep`: по `deep_fork.md` оценить richness контекста и форкнуть фоновый `/bft-deep` (seed = документ Этапа 6; RICH → дополнительно `.bft/index/`). Фон доводит документ до валидированного черновика локально и останавливается — в Confluence не пишет (гейт «сухой прогон → «ок» PO» в фоновом субагенте пройти некому); превью уходит в нотификацию, публикует PO у себя. Нотификация по завершении — успех или провал, со статусом публикации, никогда молча.

Финал: одна простая строка вне тела письма — обе формулировки (штатная и `--no-deep`) заданы в `letter_format.md` §«Канал вывода», брать дословно оттуда. Без внутренностей пайплайна (swarm/оси/тяжесть).
