# poh-bft-plugin

Раздел «Управление требованиями» для [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness):
очередь БФТ по стадиям, документ требования и доска — поверх артефактов, которые
пишет `poh-bft-writer`.

Плагин — **второй способ** работы с этим репозиторием, а не замена первого.
Контур `/bft-fast` → `/bft-deep` → `/bft-deliver` продолжает работать как набор
навыков IDE-агента; плагин ничего от него не требует и ничего в нём не меняет.
Проверяется это машинно — `bash plugin/test-dual-mode.sh`.

## Откуда берётся стадия

Плагин, из которого взят этот раздел, брал стадию только из доски Backlog.md и
без неё показывал пустой экран. Здесь это неверно: стадия записана в самом
документе, и по составу файлов эпика её видно.

Стадия — не «какой файл появился», а **пройденный набор требований**:

| Стадия | Что должно быть |
|---|---|
| `FAST-DONE` | документ `{slug}-fast.md` и его страница `{slug}-fast.html` |
| `DEEP-DONE` | `{slug}.md` со `stage: deep`, страница `{slug}.html`, ссылка на страницу Confluence, ссылка на эпик JIRA |

Набор неполон — задача не поднимается на стадию, а **возвращается на
предыдущую**: неполный deep уходит в `DEEP-REVIEW`, неполный fast — в `To Do`.
Вердикт при этом называет, чего именно не хватило (`missing`): «вернулось в
DEEP-REVIEW» без этого не отвечает на вопрос «что чинить», и PO идёт выяснять
руками.

Страницы ревью две, и различаются они обязательно: `{slug}-fast.html` закрывает
стадию fast, `{slug}.html` — стадию deep. Один общий флаг «html есть» засчитал
бы страницу от быстрого прохода как готовность глубокого.

`DEEP-WORK`, `REVIEW-DONE` и `Cancelled` по артефактам не отличаются от соседей —
это состояния процесса, а не документа. Гадать о них по косвенным признакам
значило бы показать PO уверенную неправду, поэтому их даёт только доска.
Поле `stageSource` говорит, откуда стадия взялась: `artifacts` или `backlog`.

Отсюда следствие: **Backlog.md необязателен**. Без него раздел работает по
одному воркспейсу.

## Каталог документов

Умолчание — `.bft/documentation`, как объявляет `bft-config.template.md` в корне
репозитория. Воркспейсы, где каталог переименовали в `bft/documentation`,
подхватываются запасным путём. Заданный явно `BFT_DOCS_PATH` запасных не имеет:
если PO назвал каталог, искать где-то ещё — значит молча показать не тот
воркспейс.

## Настройка

```sh
cd plugin
pnpm install
pnpm test       # тесты ядра
pnpm build      # сборка в lib/
```

Единственная обязательная переменная — `BFT_WORKSPACE_ROOT`; остальное имеет
умолчания, полный список — в `.env.example`.

## Проверки

```sh
pnpm test                        # ядро: конфиг, разбор, стадии, очередь, сборка
bash plugin/test-contract.sh     # контракт с экспортёром на настоящих эталонах
bash plugin/test-dual-mode.sh    # режим скиллов и режим плагина не мешают друг другу
```

`test-contract.sh` — не про логику плагина, а про стык: он строит воркспейс из
эталонов репозитория, гоняет по нему настоящий `bft-html-export.py` и убеждается,
что плагин находит те же файлы, которые тот записал. Подделки портов такой
проверки не заменяют — они проверяют код, а не договорённость между двумя
половинами.

## Что ещё не сделано

Ядро и стык готовы; клиентская часть (панель, превью, детальная страница,
доска) — следующий слой. Отдача данных в браузер и разметка интерфейса пока
не реализованы.
