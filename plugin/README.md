# poh-bft-plugin

Раздел «Управление требованиями» для [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness):
очередь БФТ по стадиям, документ требования и доска — поверх артефактов, которые
пишет `poh-bft-writer`.

Плагин — **второй способ** работы с этим репозиторием, а не замена первого.
Контур `/bft-fast` → `/bft-deep` → `/bft-deliver` продолжает работать как набор
навыков IDE-агента; плагин ничего от него не требует и ничего в нём не меняет.
Проверяется это машинно — `bash plugin/test-dual-mode.sh`.

## Откуда берётся стадия

Плагин, из которого взят этот раздел, брал стадию только из доски Backlog.md и
без неё показывал пустой экран. Здесь это неверно: стадия записана в самом
документе, и по составу файлов эпика её видно.

Стадия — не «какой файл появился», а **пройденный набор требований**:

| Стадия | Что должно быть |
|---|---|
| `FAST-DONE` | документ `{slug}-fast.md` и его страница `{slug}-fast.html` |
| `DEEP-DONE` | `{slug}.md` со `stage: deep`, страница `{slug}.html`, ссылка на страницу Confluence, ссылка на эпик JIRA |

Набор неполон — задача не поднимается на стадию, а **возвращается на
предыдущую**: неполный deep уходит в `DEEP-REVIEW`, неполный fast — в `To Do`.
Вердикт при этом называет, чего именно не хватило (`missing`): «вернулось в
DEEP-REVIEW» без этого не отвечает на вопрос «что чинить», и PO идёт выяснять
руками.

Страницы ревью две, и различаются они обязательно: `{slug}-fast.html` закрывает
стадию fast, `{slug}.html` — стадию deep. Один общий флаг «html есть» засчитал
бы страницу от быстрого прохода как готовность глубокого.

Полный набор стадий (`CANON_ORDER` в `src/model.ts`, он же `statuses` доски):

| Стадия | Тон | Откуда берётся |
|---|---|---|
| `To Do` | серый | по артефактам: документа нет или страница не собрана |
| `NEED-CUSTDEV` | красный | ставит PO: нужно интервью до быстрого прохода |
| `FAST-DONE` | синий | по артефактам |
| `DEEP-REVIEW` | жёлтый | по артефактам: deep есть, набор неполон |
| `DEEP-DONE` | зелёный | по артефактам |
| `OKR-ADDED` | брендовый | кнопка «Добавить в OKR» с доски |
| `BFT-CANCELED` | серый | ставит PO, терминальна |

`NEED-CUSTDEV`, `OKR-ADDED` и `BFT-CANCELED` по артефактам не отличаются от соседей —
это состояния процесса, а не документа. Гадать о них по косвенным признакам
значило бы показать PO уверенную неправду, поэтому их даёт только доска.
Поле `stageSource` говорит, откуда стадия взялась: `artifacts` или `backlog`.

Отсюда следствие: **Backlog.md необязателен**. Без него раздел работает по
одному воркспейсу — только стадии `NEED-CUSTDEV`, `OKR-ADDED` и `BFT-CANCELED`
показать будет нечем. С доской все семь стадий должны быть перечислены в
`backlog/config.yml → statuses` воркспейса, иначе `task edit -s` их отвергнет.

Доска при этом включена умолчанием (`backlog` из PATH): требование, заведённое
агентом через MCP, обязано появиться в разделе сразу, а не после первого
`/bft-fast`. Бинаря в PATH нет — запуск возвращает код -1, и очередь остаётся
той же, что была бы без доски. Отказ от доски пишется словом:
`BFT_BACKLOG_BIN=off`.

### Задача доски и каталог эпика — одна строка

Требование живёт в двух местах — задачей на доске (`PO-11`) и каталогом эпика
(`bft/documentation/<slug>/`), и общего ключа у них нет. Раздел связывает их сам
(`src/epic-link.ts`), по убыванию надёжности: **ссылка задачи** внутрь каталога
документов; **слаг, равный идентификатору** без учёта регистра; **H1 документа**
`# [БФТ] <slug>: <Название>` — ключ или название совпало с задачей. Эвристик по
времени файлов нет намеренно: две задачи, начатые подряд, они бы перепутали, а
перепутанная ссылка хуже отсутствующей. Не связалось — две строки, и PO добавляет
ссылку рукой (`backlog task edit PO-N --add-ref …`).

Слитая строка: `id` задачи, `slug` каталога, стадия — старшая из двух по
хронологии (`BFT-CANCELED` доски терминален и старше всего), `stageSource` говорит,
чья взяла, `missing` — всегда по артефактам: что чинить до следующей стадии
документа.

Доска читается одним вызовом `backlog task list --type bft --json` (Backlog.md
≥ 1.51): статус и ссылки задачи приходят вместе, а фильтр по типу делает сам CLI
— задачи без типа в очередь не текут. Для CLI без `--json` остаётся разбор
`--plain`, где ссылок нет и связка идёт только по слагу и H1.

### Доска пишется по факту артефактов

Навык пишет файлы, раздел их видит и приводит Backlog.md в соответствие
(`src/backlog-writer.ts`): стадия — по составу файлов эпика, ссылка — на
собранную страницу ревью. После `/bft-fast` задача сама становится `FAST-DONE`
со ссылкой на `{slug}-fast.html`; PO больше не ходит за `backlog task edit`.

Инварианты: стадия двигается **только вверх** (доска знает про процесс больше,
чем видно по файлам: `NEED-CUSTDEV` ставит PO, `OKR-ADDED` — кнопка с доски, и
стереть это решение раздел не вправе); `BFT-CANCELED` не трогается ни в какую
сторону; правка — только
при расхождении, повторная сверка по неизменному воркспейсу не зовёт CLI вовсе;
провал `task edit` — строка «доска не обновлена: …» в `missing` задачи, не падение
раздела.

После `/bft-deliver` frontmatter получает `pageId` и `jira`: стадия по файлам —
`DEEP-DONE`, и к задаче дописываются те же ссылки на страницу Confluence и эпик
JIRA, что видны в превью (`--add-ref`, уже записанные не дублируются).

Когда сверка идёт: при каждом запросе списка (подкоманда `list`), после каждого
хода агента харнесса — серверное событие `agent/status: idle` с паузой в полторы
секунды, чтобы не дёргать `backlog` на каждый инструмент, — и по завершении
каждого хода Claude Code с детальной страницы (у внешнего процесса события
харнесса нет, узел зовёт сверку сам). Открытая панель обновляется тихо раз в
полминуты — вернувшись из чата, PO видит новую стадию без клика по «Обновить».

### Стадия доски выше файлов

Доска бывает впереди артефактов и по праву (`NEED-CUSTDEV`, `OKR-ADDED` ставит
PO), и по инерции: эпик сбросили до чистого `/bft-fast`, deep-файлы удалили, а
стадия вниз не двигается. Раздел не гадает, кто прав, — показывает обе стадии
(«DEEP-REVIEW · по артефактам: FAST-DONE») и считает «Не хватает до стадии» от
той, что на доске (`gapsToward` в `src/stage.ts`): для deep-стадий первым пунктом
идёт сам единый документ `{slug}.md` со `stage: deep`. Иначе `DEEP-REVIEW` без
deep-документа читался бы как «всё на месте».

### Черновик для чата: слэш-команда первой строкой

Харнесс загружает инструкции навыка только по слэш-команде в начале
сообщения; свободный текст «продолжи работу над БФТ» оставляет модель без
конвейера — она ищет `SKILL.md` по диску и импровизирует. Поэтому подкоманда
`handoff` (`src/handoff.ts`) открывает черновик командой следующего навыка **по
составу артефактов**, а не по стадии доски: нет документа — `/bft-fast <id>
<slug>`; fast без страницы — `/bft-html`; fast со страницей — `/bft-deep
<slug>`; deep без страницы — `/bft-html`; deep со страницей, но без ссылок на
Confluence и эпик — `/bft-deliver <slug>`; `DEEP-DONE` — `/bft-deep <slug>`
(доработка); `NEED-CUSTDEV` без скрипта интервью — `/bft-custdev <slug>`.
Дальше в черновике — стадии доски и диска (обе, когда расходятся), нехватка,
итог последнего закрытого отрезка и ветка контекста.

Пути в черновике — от рабочего пространства чата (`sessionPath`, по умолчанию
родитель `docsPath`: `documentation/...`, не `bft/documentation/...`), потому что
чат идёт оттуда и путь от корня раздела в нём никуда не ведёт.

Для задачи без документа тот же `handoff` отдаёт черновик создания:
`/bft-fast <id> <slug>` с источником прямо в тексте — описание, критерии приёмки
и заметки задачи из `task view --json`, дословно, — названием для H1 и
`epic_slug` = идентификатор задачи строчными (`po-11`). Так модель ничего не
ищет и не додумывает, а каталог документа заранее известен разделу. Заодно в
журнале открывается отрезок, который сверка закрывает итогом «FAST-DONE,
страница …», когда документ появляется.

«Создать документ» и мини-промт на детальной странице, «Работать в чате» в
превью зовут один и тот же `handoff`; шаблонов черновика клиент не держит.
Текст из мини-промта уходит в `handoff` полем `note` и попадает в черновик
правкой PO к документу: для deep-документа — под `/bft-deep <slug>` (режим
доработки; даже когда по составу артефактов дальше стояла бы отгрузка —
правка не должна уезжать в Confluence), для fast-документа — без команды
навыка, с указанием внести правку в `{slug}-fast.md` и прогнать линтер и
пересборку страницы (повторный `/bft-fast` по одному описанию задачи потерял
бы то, что PO диктовал в прошлый раз), для задачи без документа —
дополнением к диктовке в `/bft-fast`.

Черновик заканчивается форматом итога (`RESPONSE_FORMAT`): ответ в чат —
коротко, «Внесены правки:» списком, «Ссылки:» (JIRA, Confluence — если
публиковал или менял) и «Открытые вопросы:», если есть, без описания процесса;
вопрос PO задаётся прямо в ответе — ответ придёт следующим сообщением в тот же
чат. Формат живёт в плагине, а не в навыках: навыки общие для любого чата, а
короткий итог нужен именно рядом с документом.

### Чат с Claude Code на детальной странице

С issue #41 мини-промт на детальной странице не уходит в композер харнесса, а
идёт через **Claude Code CLI** прямо на странице. Узел (`src/claude-chat.ts`)
запускает `claude -p --output-format stream-json --verbose
--include-partial-messages` из рабочего пространства чатов (`sessionWorkspace`,
там `bft-config.md`; навыки `/bft-*` CLI находит сам по дереву выше, корень
воркспейса открыт через `--add-dir`), черновик отдаёт в stdin, а NDJSON-поток
переводит в события раздела (`src/chat-events.ts`: `user`, `delta`, `assistant`,
`tool-start`/`tool-end`, `result`, `stderr`, `exit`). Браузер опрашивает хвост
событий (`chatPoll`, раз в 700 мс) и рисует транскрипт (`DetailChat.tsx`): свои
сообщения, ответ по мере набора, строки инструментов, итог. Пока ход идёт,
документ накрыт анимацией проработки; когда CLI завершился — задача и документ
перечитываются, доска сверяется на узле (как после хода агента харнесса —
`agent/status` у внешнего процесса нет), а в чате остаётся итог и кнопка
«Открыть детальную страницу» (перечитать страницу заново).

Сессия Claude Code известна до запуска: новая — `--session-id <uuid>`, прошлая
по требованию — `--resume` из журнала работы (`sessionKind: 'claude'`), так что
повторные правки продолжают тот же диалог. Состояние сессии в журнале ведёт
узел сам: `running` при запуске, `idle`/`failed` по коду выхода и `result`.
«Открыть чат» для такой сессии в харнессе не показывается — её чат на
детальной странице.

Что уходит CLI. Новая сессия — черновик навыка (`handoff`), текст PO в нём —
правка к документу. Продолжаемая сессия — текст PO **как есть**: это ответ в
тот же диалог («ок» на сухой прогон `/bft-deliver`, значения на уточняющие
вопросы, следующая правка), и заворачивать его в черновик значило бы задавать
модели вопрос заново вместо ответа. Пустое поле в продолжаемой сессии —
черновик следующего шага по артефактам (после deep с недостающими ссылками —
`/bft-deliver <slug>`). Команду навыка PO может назвать и сам: `/bft-… ` в
начале текста.

`/bft-deliver` из чата. Черновикам навыков, которые ходят в Jira/Confluence
(`/bft-deliver`, `/bft-deep`), дописывается блок среды (`MCP_ENVIRONMENT`):
инструменты `jira_*`/`confluence_*` — MCP-инструменты, искать через ToolSearch,
сервер подключается с задержкой (подождать и повторить), `.mcp.json` их не
перечисляет — EN002/EN003 от `bft-env-lint` при найденных инструментах не
препятствие; значения `wiki_space`/`bft_parent_page_id`/`tracker_projects`,
названные PO в чате, пишутся в корневой `bft-config.md`. Без этого блока модель
заключала «публиковать нечем» и не искала инструменты. Два условия среды:
профиль разрешает CLI инструменты сервера (`claudeArgs` с `mcp__<сервер>`,
иначе неинтерактивный прогон их не получит) и PATH — узел дописывает
спавну `/opt/homebrew/bin`, `/usr/local/bin`, `~/.local/bin` (под launchd PATH
голый, и `docker mcp gateway` молча не стартовал). После отгрузки frontmatter
получает `pageId` и `jira`, сверка поднимает доску до `DEEP-DONE` и дописывает
задаче ссылки на эпик и страницу (`--add-ref`), а в чате под итогом — те же
ссылки из перечитанной задачи; URL в тексте ответа кликабельны.

Копия `bft-config.md` в рабочем пространстве чатов — производная от корневого
конфига и перечитывается из него на каждый ход: править `wiki_space`,
`tracker_projects` и прочее нужно в корне воркспейса. Корневого конфига нет —
копия один раз собирается из шаблона и дальше не трогается.

Подкоманды канала: `chatStatus {id}` → `{available, run}` (есть ли CLI в этой
среде и последний ход — страница, открытая заново, подхватывает идущий);
`chatStart {id, note?}` → `{runId, status, sessionId}` (второй ход по тому же
требованию, пока идёт первый, — `chat-busy`); `chatPoll {runId, since}` →
`{status, events, total}` (`chat-run-not-found` — узел перезапускался);
`chatStop {runId}`.

Настройки: `claudeBin` (умолчание `claude` из PATH; под launchd — абсолютный
путь; `off` — выключить: «В чат» тогда кладёт черновик в композер харнесса, как
раньше) и `claudeArgs` (умолчание `--permission-mode acceptEdits --allowedTools
Bash(python3:*) Bash(backlog:*)` — спросить PO из неинтерактивного прогона
некому, поэтому всё, что навык делает штатно, разрешено заранее; остальное CLI
откажет сам, и отказ виден в чате). Те же ключи из окружения — `BFT_CLAUDE_BIN`,
`BFT_CLAUDE_ARGS` (через пробел).

### «Добавить в OKR»

У карточки в колонке `DEEP-DONE` на доске есть кнопка «Добавить в OKR». Она
открывает окно с полями карточки KR плагина OKR: ссылки на Confluence и эпик
(подставлены из требования, обязательны), квартал (`2026-Q3`, `2026-Q4`, …;
обязателен), планирование по фазам `research/analyze/dev/qa/release` — спринт и
плановые ресурсы, команды исполнения, ответственные техлиды и исполнители,
свободный комментарий.

Подкоманда `addToOkr` (`src/okr-handoff.ts`) пишет всё одной командой в задачу
Backlog.md: `task edit <id> -s OKR-ADDED --plan <блок> --append-notes "OKR: …"
--add-ref <ссылки, которых ещё нет>`. Блок плана — тот же формат, что у карточки
KR плагина OKR (`research: спринт 3 / SA`, `teams: …`, `techLeads: …`,
`executors: …`) плюс строка `quarter: 2026-Q4`: задача, переведённая в KR,
читается тем плагином без конвертации. Передаётся только `DEEP-DONE` и только
задача доски; из `OKR-ADDED` повторно — нет, иначе перезаписался бы план, который
PO мог уже править в OKR. В журнале закрывается отрезок итогом «OKR-ADDED,
квартал …». Карточка после этого уезжает в колонку `OKR-ADDED`, в очередь панели
не попадает.

## Контекст работы: entire.io и локальный журнал

Модель, начиная работу над требованием, раньше стартовала с нуля: что уже
разбирали, какие развилки закрыли и чем кончился прошлый заход, знал только PO
и переносил руками. Теперь отрезки работы записаны.

**Локальный журнал** — `{indexPath}/bft-worklog.json`. У каждого отрезка есть
эпик, стадия, когда начался, чем закончился и ссылка на ветку контекстного чата
в entire.io. Журнал рабочий и локальный: он не часть БФТ-документа и в Confluence
не едет. Поэтому и живёт рядом с индексом, а не во frontmatter — состав
frontmatter фиксирован стандартом, и класть туда состояние процесса значило бы
менять документ на каждый заход модели.

**Продолжение вместо начала.** Кнопка «Работать в чате» строит черновик по
последнему **закрытому** отрезку: его итог и ссылка на ветку идут в текст прямым
указанием «подними её и продолжи оттуда, а не с нуля». Брошенный посередине
отрезок контекстом не считается — незакрытая работа не итог.

**entire.io обязателен.** Без `BFT_ENTIRE_BASE_URL` раздел не стартует: «не
настроено» здесь означает молчаливую потерю истории, а это ровно то, ради чего
журнал заводился. Отказаться можно только явно — `BFT_ENTIRE_REQUIRED=0`, и
тогда в разборе конфига прямо написано, что истории не будет.

## Сессия по требованию: где работали и что с ней

Стадия говорит о документе, не о работе: при пяти параллельных требованиях PO не
видит, где агент ходит прямо сейчас, где ждёт его, а где сессия оборвалась два дня
назад. Поэтому у каждой строки очереди и карточки доски — точка состояния
последней сессии харнесса и давность («сегодня», «2 д.»), а в превью и на
детальной странице — блок «Последняя сессия» с кнопкой «Открыть чат»: тот же
чат, та же история, продолжение вместо начала заново.

| Состояние | Когда | Точка |
|---|---|---|
| `running` — агент работает | агент сессии в `running` | закрашенная, info |
| `idle` — ждёт вас | сессия в `idle`: ответить, отправить следующий шаг | контур, warn |
| `failed` — прервалась | агент упал (`agent/error`) или сессия была `running` в момент перезапуска харнесса | закрашенная, error |
| `gone` — чат удалён | сессии больше нет в списке харнесса | бледная |

Откуда это берётся. Каждый чат, открытый из раздела по требованию, записывается
в журнал работы (`attachSession`: сессия → отрезок по эпику) с видом сессии
(`sessionKind`): `harness` — чат самого харнесса («Работать в чате» из превью),
`claude` — сессия Claude Code с детальной страницы («В чат», «Создать
документ»). Для харнесса узел подписан на его события `agent/status`,
`agent/error`, `session/disposed` и обновляет состояние и время последнего
движения; на старте узла всё, что числилось `running`, становится `failed` —
харнесс перезапустили посреди хода. Браузер сверху кладёт живое из списка
сессий (`sessions.list`): существует ли сессия, ходит ли агент сейчас, когда
менялась; живое сильнее записи (`src/client/session-view.ts`). Для Claude Code
состояние ведёт сам узел по процессу CLI (`running` при запуске, `idle`/`failed`
по выходу); список харнесса такой сессии не знает и не при чём, «Открыть чат»
для неё не показывается — её чат на детальной странице. Чужие сессии журнал не
отслеживает.

Сессия удалена — блок говорит об этом и предлагает «Работать в чате»: новая сессия
с черновиком из журнала, как раньше. Ветка entire.io (`Ветка контекста`) остаётся
отдельным полем и от сессии харнесса не зависит.

## Рабочее пространство чатов

Чат, открытый из раздела, живёт не в текущем рабочем пространстве харнесса, а в
каталоге рядом с документами: при `bft/documentation` это `bft/` (настройка
`sessionPath`, умолчание — родитель каталога документов; пустая строка — не
привязывать). Агент стартует там, где лежат `documentation/` и `index/`, а
сессии по требованиям собираются в одну группу списка.

Рабочее пространство раздел регистрирует сам (`workspaces.create()` по пути —
идемпотентно: хост сперва ищет уже зарегистрированное) и кладёт в каталог
`bft-config.md`: копия конфига корня воркспейса с путями, пересчитанными
относительно каталога (`docs_path: documentation`, `index_path: index`,
`skills_path: ../.claude/skills`). Без него навыки в cwd `bft/` не нашли бы ни
документов, ни линтеров. Копия производная и перечитывается из корневого
конфига при каждом обращении (в том числе на каждый ход Claude Code): PO
дописал `wiki_space` или `tracker_projects` в корне — следующий ход их видит.
Править нужно корневой файл; копию не редактируют. Корневого конфига нет —
копия один раз собирается из шаблона и дальше не трогается. `skills_path`
пишется только когда раздел знает skill-root воркспейса — настройка
`skillsPath`; умолчания у неё нет намеренно: раскладку IDE-агента плагин не
угадывает (`test-dual-mode.sh`), а навык без `skills_path` ищет корень сам, в
cwd и родительских каталогах. Из того же каталога стартует и Claude Code CLI
(cwd), корень воркспейса ему открыт через `--add-dir`.

Каталог недоступен или канал молчит — чат откроется в текущем рабочем
пространстве, причина — в консоли браузера; раздел не ломается.

## Каталог документов

Умолчание — `.bft/documentation`, как объявляет `bft-config.template.md` в корне
репозитория. Воркспейсы, где каталог переименовали в `bft/documentation`,
подхватываются запасным путём. Заданный явно `BFT_DOCS_PATH` запасных не имеет:
если PO назвал каталог, искать где-то ещё — значит молча показать не тот
воркспейс.

## Настройка

```sh
cd plugin
pnpm install
pnpm test       # тесты ядра
pnpm build      # обе половины: tsc в lib/ + браузерный бандл lib/client.js
```

Единственная обязательная переменная — `BFT_WORKSPACE_ROOT`; остальное имеет
умолчания, полный список — в `.env.example`. Чат на детальной странице —
`BFT_CLAUDE_BIN` (умолчание `claude` из PATH, `off` — выключить) и
`BFT_CLAUDE_ARGS` (права и модель CLI через пробел); в профиле харнесса — те же
`claudeBin` и `claudeArgs`.

### Настройки раздела в интерфейсе харнесса

Три вещи PO правит сам, из «Настройки → Плагины → Требования», без доступа к
профилю и без перезапуска:

| Ключ | Поле | Пусто значит |
|---|---|---|
| `formUrl` | Ссылка на форму сбора требований | кнопка «+» в шапке панели и «Добавить» на доске неактивны |
| `sheetUrl` | Ссылка на таблицу требований | берётся `BFT_INITIATIVES_SHEET_URL` из окружения |
| `syncPrompt` | Промт работы с требованиями | `/bft-needed-list {sheet}` |

Пространство имён настроек — `bft`, документ — `$DSH_HOME/settings.yaml`.

**Настройка выше окружения, и это не ветка в коде.** Пространство имён
регистрируется со слоем композиции, в котором лежит `BFT_INITIATIVES_SHEET_URL`;
служба настроек сама слоит пользовательское значение поверх него. Поэтому очистка
поля возвращает адрес из окружения, а уже настроенные установки не ломаются в
момент обновления.

**Секретов здесь нет и быть не может.** Документ настроек лежит файлом и
синхронизируется между поверхностями — токены остаются в окружении.

`{sheet}` в промте заменяется адресом таблицы. Адреса нет — плейсхолдер
вырезается вместе с прилипшими пробелами; плейсхолдера нет вовсе — промт уходит
как написан. Кнопка «Обновить» кладёт результат в композер и ничего не
отправляет.

### Форма сбора инициативы

Кнопка «+» слева от «Обновить» открывает `formUrl` айфреймом прямо в панели;
«Добавить» на доске — ту же форму на всю страницу. Ширину панели можно тянуть за
левую кромку, значение переживает перезагрузку.

Две границы, о которых стоит знать заранее:

- **Плагин не узнаёт, что форму отправили.** Страница чужая, событий она не
  шлёт. Финал сценария — кнопка «Готово»: возврат к списку и обновление.
- **Отказ во встраивании браузер не даёт отличить от успеха.** Страница с
  `frame-ancestors 'none'` присылает родителю такой же `load` и остаётся так же
  кросс-доменной, как успешно загруженная форма. Поэтому «Открыть в браузере»
  стоит в подвале всегда, а не всплывает по догадке. У Google Forms адрес с
  `?embedded=true` встраивается штатно.

Пошаговые сценарии со скриншотами —
[`docs/guides/plugin-playbooks/`](../docs/guides/plugin-playbooks/README.md).

## Проверки

```sh
pnpm test                        # ядро: конфиг, разбор, стадии, очередь, сборка, чат (события CLI, прогоны)
bash plugin/test-contract.sh     # контракт с экспортёром на настоящих эталонах
bash plugin/test-dual-mode.sh    # режим скиллов и режим плагина не мешают друг другу
pnpm test:e2e                    # сценарии плейбуков против живого харнесса (см. e2e/README.md)
pnpm playbook:shots              # то же + перегенерация скриншотов плейбуков
```

`test-contract.sh` — не про логику плагина, а про стык: он строит воркспейс из
эталонов репозитория, гоняет по нему настоящий `bft-html-export.py` и убеждается,
что плагин находит те же файлы, которые тот записал. Подделки портов такой
проверки не заменяют — они проверяют код, а не договорённость между двумя
половинами.

## Клиентская часть

Раздел в браузере перенесён из `dsh-plugin-bft` (репозиторий `poh-harness`) и
адаптирован: кнопка в подвале сайдбара, панель очереди с поиском и группами по
стадиям, превью требования, детальная страница с документом и чатом с Claude
Code (`DetailChat.tsx`), доска. Обвязка харнесса — регистрация слотов, общий стор кнопки и панели,
цепочка ухода в чат — перенесена как есть: она проверена в работе, и переписывать
её заново значило бы потерять записанные в ней находки.

Адаптировано под этот репозиторий:

- **черновик для чата приходит с сервера** (подкоманда `handoff`), потому что
  опирается на журнал работы — клиенту он не виден. Канал не ответил — уходим с
  коротким черновиком: уйти в чат вообще без него хуже;
- в превью добавлены **ветка контекста** entire.io и **список нехватки** до
  следующей стадии: сама стадия не говорит, что делать;
- мелкая правка на детальной странице тоже несёт ссылку на ветку контекста —
  это тот же заход по требованию, начинать его с нуля незачем; сама правка идёт
  не в композер, а ходом Claude Code прямо на странице (см. выше);
- **доска Backlog.md дополняет очередь, а не заменяет её**: стадия документа
  доской не переписывается — она выведена из того, что лежит на диске.
  Объединение идёт по идентификатору, задачи доски без документа приходят с
  `missing: ['документ БФТ']`.

**Браузерный бандл собирается tsdown, а не tsc.** `exports["./client"]` смотрит
на `lib/client.js` — один файл, который зовёт `window.__ModuleLoader__.load` и
разрешает внешние пакеты через переданный `require`, то есть таблицу модулей
оболочки. Вывод tsc туда не годится: в нём остаются голые спецификаторы вроде
`react`, а браузер их не разрешает. Рецепт повторяет тот, которым харнесс
собирает свои клиенты (`packages/client/tsdown.client.ts`); сторож чистоты в
`tsdown.config.ts` роняет сборку, если в бандл попадает value-импорт пакета
харнесса вне таблицы модулей — такой `require` был бы гарантированным падением
в рантайме.

Серверная половина от UI-кита не зависит: тесты ядра гоняются отдельно
(`pnpm test`).

## Установка в харнесс

Пошагово — [`docs/guides/dsh-plugin-setup.md`](../docs/guides/dsh-plugin-setup.md):
версия харнесса, два файла профиля, запуск и разбор того, что делать, если не
поднялось. Обновление уже установленного до последнего `main` — `bash update.sh`
из корня репозитория ([`docs/guides/dsh-plugin-update.md`](../docs/guides/dsh-plugin-update.md)):
чекаут, сборка, навыки воркспейса, перезапуск и проверка HTTP 200 одной командой.

Одно следствие стоит держать в голове при чтении кода: **слой профиля заменяет
конфигурацию пакета целиком, а не дополняет её.** Профиль обязан задать
`workspaceRoot` — и в этот момент всё, что объявлено в `cordis.patch.yml` пакета
(`docsPath`, `indexPath`, `taskType`, `backlogBin`), из конфигурации пропадает.
Поэтому умолчания живут в `config.ts`, а патч пакета остаётся удобством, а не
источником правды.

## Что ещё не сделано

Про чат с Claude Code: реестр прогонов живёт в памяти узла — перезапуск
харнесса обрывает идущий ход и очищает транскрипт на странице (сессия Claude
Code на диске остаётся, следующее сообщение продолжает её `--resume`).
«Работать в чате» из превью и «Обновить» по-прежнему ведут в композер харнесса.
e2e `03-detail-page` — от прототипа, не обновлён.

Про entire.io: реализовано то, что от него не зависит, — журнал,
ссылка на ветку в требовании и продолжение работы с последнего контекста.
Не подтверждены три вещи, и до ответа они вынесены в конфиг, а не зашиты в
код: точная форма адреса ветки (`BFT_ENTIRE_BRANCH_URL`, умолчание подобрано),
способ убедиться, что entire.io действительно установлен, а не только настроен,
и способ прочитать содержимое ветки, чтобы модель поднимала контекст сама, а не
по ссылке в тексте.
